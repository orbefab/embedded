# ESP32-S3 SoC

`crates/esp32`, package `sim-esp32`, is the ESP32-S3 around the `sim-xtensa` core. Its `s3` module is the chip. The circuit crate holds it behind the active chip seam, and each `esp32s3` part of a netlist runs one. [netlist.md](netlist.md#esp32-s3) describes the part.

The register addresses and bit positions come from IDF's `soc/esp32s3` headers, IDF v5.5.5. The electrical values in `examples/esp32s3-blink` come from the ESP32-S3 Series Datasheet v2.2, Table 5-4.

## How it starts

A part with `firmware.elf` starts as a bare-metal ELF leaves it. Every loadable segment is in SRAM, the PC is at the entry, and the rest of the core is in its reset state. There is no ROM and no flash. The CPU runs on the 40 MHz crystal, so a cycle is 25 ns, and `SYSTEM_SYSCLK_CONF_REG` and `SYSTEM_CPU_PER_CONF_REG` read that clock: 0, and the reset value `0xc`.

A part with `firmware.flash` boots an ESP-IDF app, as [Booting from flash](#booting-from-flash) says. It starts as the board's second-stage bootloader leaves the app at its entry, `call_start_cpu0`, with the CPU on the 80 MHz PLL.

## The two cores

The PRO CPU, core 0, starts at the entry. The APP CPU, core 1, starts from its own reset when firmware releases it: a store that clears `RESETING` in `SYSTEM_CORE_1_CONTROL_0_REG` while it was set, or a store of `RTC_CNTL_SW_APPCPU_RST` to `RTC_CNTL_OPTIONS0_REG`. It then runs from the reset vector at `0x4000_0400` with `CCOUNT` 0. The ROM's reset path polls `SYSTEM_CORE_1_CONTROL_1_REG` and calls the address `ets_set_appcpu_boot_addr` stored there. A part with `firmware.elf` has no ROM, so an APP CPU it releases ends the run with `chip.unmapped_fetch` at the reset vector.

The APP CPU runs while `CLKGATE_EN` is set and `RUNSTALL` and `RESETING` are clear in `SYSTEM_CORE_1_CONTROL_0_REG`, and the RTC stall is off. The RTC stall is on while `RTC_CNTL_SW_STALL_APPCPU_C0` is 2 and `RTC_CNTL_SW_STALL_APPCPU_C1` is `0x21`. A bare-metal chip starts with `SYSTEM_CORE_1_CONTROL_0_REG` at its reset value, `RESETING` set. A chip booted from flash takes the captured `0x1`, `RUNSTALL` set and the reset clear, so ESP-IDF's single-core start-up leaves the APP CPU unstarted. A store that would let an APP CPU run that has not been reset in this run holds it unstarted. ESP-IDF's dual-core start, `cpu_utility_ll_enable_clock_and_reset_app_cpu`, sets `CLKGATE_EN`, clears `RUNSTALL`, then sets `RESETING` and clears it. The APP CPU stays unstarted from the store that clears `RUNSTALL` and starts from its reset at the store that clears `RESETING`. The run ends with `chip.unsupported_setting`, `SYSTEM` `app_cpu_without_reset`, when a store to `SYSTEM_CORE_1_CONTROL_0_REG` that does not set `RESETING` comes first, or when 1,000 PRO CPU cycles pass with no reset, because the model cannot know the state such an APP CPU would run from. The 1,000 cycles are the model's bound, not a chip figure. When `CLKGATE_EN` is already set, the function skips the reset, and the store that later lets the APP CPU run is held the same way.

A store that sets the PRO CPU's own stall fields, `RTC_CNTL_SW_STALL_PROCPU_C0` to 2 and `RTC_CNTL_SW_STALL_PROCPU_C1` to `0x21`, ends the run with `chip.unsupported_setting`, `RTC_CNTL` `pro_cpu_stall`, because the model does not stall the PRO CPU. ESP-IDF's `esp_cpu_stall(0)` writes that pattern, in four stores, a clear and then a set of each field. So code on the APP CPU that stalls the PRO CPU ends the run at its last store, the one that sets `RTC_CNTL_SW_STALL_PROCPU_C1`. Every chip keeps `RTC_CNTL_OPTIONS0_REG` and `RTC_CNTL_SW_CPU_STALL_REG` as words, and a bare-metal chip starts them at 0. Apart from the stall fields and the reset bits, a write to them is kept and runs nothing, and the run does not list it as `chip.unmodeled_register`.

While `CLKGATE_EN` is clear the APP CPU's clock is stopped, and its `CCOUNT` does not count. While `RUNSTALL` or the RTC stall holds it with its clock on, `CCOUNT` counts. A gate edge during a stall splits the hold there. These two rules are inferred from what the gate and the stall are, and no board capture checks them yet.

Both cores count the one CPU clock. The next instruction to run is the one that starts on the earliest cycle, the PRO CPU's at a tie. A store that starts, holds or releases the APP CPU takes effect before either core runs another instruction. A store that the run stops at, to list it with its PC, runs again before the other core runs any instruction, whatever their cycles. If an interrupt falls due on the cycle the store would run again, its core takes the interrupt first, and the other core may run before the store does. So a run split at any cycles runs the same instructions in the same order. A core in `WAITI` sleeps while the other core runs, until its next timer match, SYSTIMER alarm, SPI2 end or I2C0's next event, until the other core stores outside SRAM and RTC memory, or until the chip stops or the engine step ends, as [engine.md](engine.md#active-chips) says, and then polls on the cycle it would have reached polling after each of the other core's instructions. So no core sleeps between engine steps, and an input from the seam never meets one. A core in `WAITI` polls on the first cycle after the input's tick, which is where a core polling after each instruction reads the input, so a pad edge wakes it on the same cycle however the run is split. A change that keeps a core asleep across engine steps must wake it at an input, with a test that pins that cycle. With both cores started, a clock switch lands at the start of the instruction that stores it, a cycle before its store on an instruction that straddles a word. When the other core's straddling access on the same start cycle has already landed a cycle later, the switch lands on that later cycle instead. Neither core sees time go back, and time keeps moving across the switch. Loads and stores are sequentially consistent at instruction granularity, so `s32c1i` is atomic across the cores, and nothing models bus contention between them. `PRID` reads `0xcdcd` on the PRO CPU and `0xabab` on the APP CPU.

Each core keeps the instructions it has decoded, keyed by the address and the bytes the fetch read, and it fetches before it looks. The kept decode changes no output.

A core reads its interrupt lines only when they could have changed. After a read, it keeps those lines until the bus reports its next event, until a load or a store outside SRAM, RTC memory, the ROM and the flash windows, or until the next run of that core. A skipped read changes no output. A build with `poll-skip-check` reads the lines on each skipped step and panics if they moved. That read settles and stamps the way a poll does. It does not run the stamp a skipped poll uses.

## The timeline and the clock

Every peripheral counts ticks of 480 MHz, the least common multiple of the clocks the CPU runs on. The core counts its own cycles, and each maps to ticks from the last change of the CPU clock. The CPU runs on the crystal divided by `SYSTEM_PRE_DIV_CNT` + 1, or on the PLL at 80, 160 or 240 MHz as `SYSTEM_CPUPERIOD_SEL` picks. 240 MHz needs the 480 MHz PLL, which `SYSTEM_PLL_FREQ_SEL` set picks, so `SYSTEM_CPUPERIOD_SEL` 2 with the 320 MHz PLL is a reserved value. After a store to either register, the next cycle runs on the clock it picks, and the watchdogs keep their counts across the change. The APB clock is 80 MHz while the CPU runs on the PLL, and the CPU's own clock while it runs on the crystal. A store that picks the RC fast clock, or a reserved value, ends the run with `chip.unsupported_clock`.

## What it models

- **SRAM.** 512 KB, seen through two windows. From `0x4037_0000` to `0x403e_0000` on the instruction bus it is SRAM from byte 0. From `0x3fc8_8000` to `0x3fd0_0000` on the data bus it is SRAM from byte `0x8000`. So `0x4037_8000` and `0x3fc8_8000` are one byte. The core fetches only through the instruction window, and loads and stores through either. Through the instruction window only an aligned word goes, as on the board. A byte or halfword access, and an `l32ai`, `s32ri` or `s32c1i`, raises `LoadStoreError`, cause 3. An unaligned access raises `LoadStoreAlignment`, cause 9. The access's address goes to `EXCVADDR`, and a store writes nothing.
- **GPIO, IO_MUX, the GPIO matrix and the GPIO interrupt.** A pad drives from the matrix when its IO_MUX function is the GPIO one. That is function 1 on every pad, or function 0 on a pad whose function 0 is its GPIO: GPIO0 to GPIO21, GPIO33 to GPIO38, GPIO45 and GPIO46. Signal 256 in `GPIO_FUNCn_OUT_SEL_CFG` is the pad's own `GPIO_OUT` bit, enabled by its `GPIO_ENABLE` bit. `OUT_INV_SEL`, `OEN_SEL` and `OEN_INV_SEL` act as the headers say, and with `OEN_SEL` clear the peripheral enables the pad, as SPI2 does each of its outputs. A pad routed to an SPI2 output drives that signal's idle level, as the SPI2 entry below says. A pad routed to I2C0's SCL or SDA, signals 89 and 90, drives that signal open drain while a transfer runs, as the I2C0 entry below says. A pad routed to another signal drives nothing, because no other peripheral output is modelled. A pad whose `GPIO_PINn` sets `PAD_DRIVER` is open drain, and drives nothing for a high level. A pad that does not drive pulls up while its `FUN_WPU` is set. `FUN_WPD` is kept and not stamped, since the seam has no pull-down. `GPIO_IN` and `GPIO_IN1` read 0 on a pad whose `FUN_IE` is clear. A pad with a net reads its net, a pad with no net reads what it drives, or its pull-up. The input matrix's `GPIO_FUNCn_IN_SEL_CFG_REG` words are kept. I2C0 reads signals 89 and 90 through them while a transfer samples the bus, and no other modelled peripheral reads an input signal through them. `INT_TYPE` in `GPIO_PINn` picks what interrupts: 1 a rising edge, 2 a falling edge, 3 either edge, 4 a low level and 5 a high level. Each change of a pad's `GPIO_IN` bit, from its net, its own drive or a write that moves either, latches an edge its type takes into `GPIO_STATUS_REG` or `GPIO_STATUS1_REG`, whether its interrupt is enabled or not, and `GPIO_STATUS_W1TC_REG` and `GPIO_STATUS1_W1TC_REG` clear it. A level type reads set there while its level holds, so a clear does not clear it. `GPIO_PCPU_INT_REG` and `GPIO_PCPU_INT1_REG` read those bits of the pads whose `INT_ENA` bit 0 is set, and source 16, the GPIO interrupt, is high while either is nonzero. The model takes a pad's level at the time it lands, with no synchronizer, so `SYNC1_BYPASS`, `SYNC2_BYPASS` and `CONFIG` are kept and not run, and every write that changes one is listed with `chip.unmodeled_register`, as [Unmodeled registers](#unmodeled-registers) says. A `GPIO_PINn` write ends the run with `chip.unsupported_setting` and writes nothing when it sets another `INT_ENA` bit, the NMI or an SDIO interrupt, as `GPIO` `pin_int_ena`, when it sets the reserved `INT_TYPE` 6 or 7, as `pin_int_type`, and when it sets `WAKEUP_ENABLE`, as `pin_wakeup`. `GPIO_STATUS_W1TS_REG`, the NMI and SDIO interrupt words and `GPIO_STATUS_NEXT_REG` are not kept. GPIO26 to GPIO32 are the flash's pads, `SPICS1`, `SPIHD`, `SPIWP`, `SPICS0`, `SPICLK`, `SPIQ` and `SPID`, which IO_MUX function 0 gives SPI0 and SPI1. Firmware that took one could send the flash any command through the matrix. So a write that gives one of them another function, sets its `GPIO_ENABLE` bit, or moves its `GPIO_FUNCn_OUT_SEL_CFG_REG` from its reset value ends the run with `chip.flash_command` and writes nothing. IDF's start-up sets their drive and pulls in function 0, and those writes are kept.
- **RTC memory.** RTC fast memory, 8 KB at `0x600f_e000` on both buses, and RTC slow memory, 8 KB at `0x5000_0000` on the data bus. The core fetches from RTC fast memory too.
- **SYSTIMER.** It counts at 16 MHz, the crystal times 2 over 5, whatever clock the CPU runs on. Unit 0 works from power-on and unit 1 does not, as `SYSTIMER_CONF` resets. `UPDATE`, the value registers, `VALUE_VALID`, the load registers and the load strobes work. Each of the three alarms compares its unit with its target while its `WORK_EN` bit is set. A load through `COMPn_LOAD` takes the target, or in period mode the unit's count plus the period. A write of `TARGETn_CONF` that sets period mode on an alarm with no fire pending, as a fired target alarm is, arms it at the unit's count plus the period. A write that sets period mode on an alarm still pending keeps its count. ESP-IDF's dual-core start loads alarm 1 in target mode, where it fires at once, and then sets period mode, so core 1's tick runs from that write, half a period after core 0's, as `port_systick.c` intends. No source shows what the chip does at that write. The rule follows ESP-IDF's comment. A target alarm fires once its unit reaches the target, and a period alarm fires each period after the load. A firing alarm sets its `INT_RAW` bit, and its interrupt line is that bit and its `INT_ENA` bit. A core in `WAITI` skips to the next alarm.
- **The interrupt matrix.** Each core has a map. Source n's map register, at offset 4 × n of `INTERRUPT_CORE0` for the PRO CPU and of `INTERRUPT_CORE1`, `0x800` above it, for the APP CPU, names the CPU interrupt it drives on that core. The APP CPU's map starts at 16, a core timer interrupt, as the chip resets it. A CPU interrupt's line is high while any source mapped to it on that core is high. A source mapped to one of the core's internal interrupts, such as a timer, drives nothing. The status registers of both halves show each source's level. The sources are the GPIO interrupt, 16, SPI2's, 21, I2C0's, 42, the watchdogs of timer groups 0 and 1, 52 and 55, the three SYSTIMER alarms, 57 to 59, the four `FROM_CPU` registers of the SYSTEM block, 79 to 82, which firmware raises and clears by writing bit 0, and the USB Serial/JTAG interrupt, 96. Every other source stays low. So a write that enables an interrupt the model never raises ends the run with `chip.unsupported_setting`. Those writes set a bit of SPI2's `SPI_DMA_INT_ENA_REG` other than `SPI_TRANS_DONE_INT_ENA`, of GDMA's `GDMA_IN_INT_ENA_CHn_REG` or `GDMA_OUT_INT_ENA_CHn_REG`, of `USB_SERIAL_JTAG_INT_ENA_REG` other than `SERIAL_OUT_RECV_PKT`, `SERIAL_IN_EMPTY` and `USB_BUS_RESET`, of `SHA_INT_ENA_REG` or `LEDC_INT_ENA_REG`, or the `T0` or `T1` bit of a timer group's `TIMG_INT_ENA_TIMERS_REG`. The map registers take any source, since IDF maps the watchdog, cache error and permission sources at start-up. A cache access the MMU does not map ends the run before its interrupt would rise. No access is checked against the permission controls, so their sources never rise. The model has no brownout detector, so `RTC_CNTL_BROWN_OUT_INT_ENA`, which IDF sets at start-up, is kept and raises nothing.
- **The watchdogs.** The RTC watchdog and the main watchdog of each timer group. Each runs while its `EN` bit is set and a stage acts, or while its flash boot bit is set. That bit is set at power-on on the RTC watchdog and on timer group 0's, as the boot ROM leaves them, and in flash boot mode stage 0 resets the system, or on the RTC watchdog the RTC domain. A running watchdog counts each stage's hold in turn from stage 0, and after stage 3 stage 0 again. A timer group's stage n holds its `TIMG_WDTCONFIG` word n + 2. A timer group's watchdog counts the APB clock through its prescaler. On a bare-metal chip, timer group 0's first stage runs out at 26,000,000 cycles, 0.65 s, and the RTC watchdog's at 400,000 cycles of a 136 kHz slow clock, about 2.94 s. That is its `WDTCONFIG1`, 200,000 at power-on, times 2, the multiplier for eFuse `WDT_DELAY_SEL` 0, which the eFuse set holds. The RTC watchdog's later stages hold `WDTCONFIG2` to `WDTCONFIG4`. A stage that runs out does what its field of `CONFIG0` says. One that does nothing or interrupts leads to the next stage. A timer group's watchdog interrupt sets bit 2 of the group's `TIMG_INT_RAW_TIMERS_REG` until `TIMG_INT_CLR_TIMERS_REG` clears it, and its source is high while that bit and bit 2 of `TIMG_INT_ENA_TIMERS_REG` are set. A stage that resets the CPU, the system or the RTC domain ends the run with `chip.watchdog`, which names the watchdog, the stage and the reset. ESP-IDF's interrupt watchdog on timer group 1 and its task watchdog on timer group 0 interrupt at stage 0 and reset the system at stage 1, and the RTC watchdog its bootloader leaves running resets the RTC domain at stage 0. A write that leaves a running watchdog a stage the model does not run, at or before its first stage that resets, ends the run with `chip.unsupported_setting`: an interrupt of the RTC watchdog, a CPU reset while `PROCPU_RESET_EN` is clear, or a field that names no action. Every write but the one to the write-protect register needs `0x50d83aa1` there, and the key is in place at power-on. A write takes effect at once, so `TIMG_WDT_CONF_UPDATE_EN` is not needed, and a hold written below the count runs out at the write. A write to the feed register, or one that starts the watchdog, counts stage 0 again. The super watchdog's two registers are kept, and start unlocked with `SWD_SIGNAL_WIDTH` 300 as on the chip. ESP-IDF's bootloader sets `SWD_AUTO_FEED_EN`, which the captured state holds, and the bare-metal examples set `SWD_DISABLE`. Neither IDF nor the TRM's register list gives the time the super watchdog runs out, so a write that leaves both bits clear ends the run with `chip.unsupported_setting`, and the super watchdog never runs out. A bare-metal chip starts with both clear, as at power-on, and it does not run out there either. The refusal stays because that time is unknown, so a program that feeds the super watchdog by hand ends the run, while one that never writes `RTC_CNTL_SWD_CONF_REG` runs on where a board could reset.
- **SPI2 as a master that sends.** The firmware writes up to 64 bytes into `SPI_W0` to `SPI_W15`, or points a GDMA OUT channel at them and sets `SPI_DMA_TX_ENA`, and sets `SPI_USR`. SPI2 then sends a command phase of `SPI_USR_COMMAND_BITLEN` + 1 bits, from bit 7 of `SPI_USR_COMMAND_VALUE` down to bit 0 and then from bit 15 down to bit 8, an address phase of the top `SPI_USR_ADDR_BITLEN` + 1 bits of `SPI_ADDR`, and `SPI_MS_DATA_BITLEN` + 1 bits of data, each when its `SPI_USR_*` bit is set and each on one, two or four lanes as `SPI_FCMD_*`, `SPI_FADDR_*` and `SPI_FWRITE_*` say. It lasts `SPI_CS_SETUP_TIME` + 1 clocks when `SPI_CS_SETUP` is set, each phase's bits over its lanes, rounded up, and `SPI_CS_HOLD_TIME` clocks when `SPI_CS_HOLD` is set. Each of those counts is 0 when its enable is clear. CS setup and hold follow IDF's whole-clock reading, not the TRM's extra half clock, until a capture settles it. SPI2 has a clock only while `SPI_CLK_EN` and `SPI_MST_CLK_ACTIVE` are set in `SPI_CLK_GATE`. `spi_ll_master_init` sets `SPI_MST_CLK_ACTIVE`, and `spi_ll_enable_clock`, which `spi_bus_initialize` calls, sets `SPI_CLK_EN`. A clock is the source `SPI_MST_CLK_SEL` picks, the 80 MHz `PLL_F80M` or the 40 MHz crystal, divided as `SPI_CLOCK` says, and the length is rounded up to whole core cycles. With `SPI_DMA_TX_ENA` the data is the bytes of the one GDMA OUT channel started on SPI2, read from its descriptor list when `SPI_USR` is written, up to 2^18 bits. `SPI_USR` reads 1 until the transfer ends, and `SPI_TRANS_DONE_INT_RAW` sets at its end. SPI2's interrupt source is high while that bit and `SPI_TRANS_DONE_INT_ENA` are set, which `esp_lcd`'s queued transfers wait on. `SPI_DMA_INT_CLR_REG` and `SPI_DMA_INT_SET_REG` clear and set the raw bits, and `SPI_DMA_INT_ST_REG` reads them under the enables. A write of `SPI_USR` while a transfer runs starts nothing. `SPI_UPDATE` reads 0 at once and syncs `SPI_ADDR` to `SPI_DOUT_MODE` into SPI2's clock domain, the registers IDF's `spi_ll.h` has a segmented transfer's CONF phase reload. A transfer runs on the synced registers, so a start while one of them differs from its value at the last update is refused. A store that sets both `SPI_USR` and `SPI_UPDATE` starts on the registers the update before it synced. `SPI_CS_KEEP_ACTIVE` keeps CS asserted after the transfer. CS changes only at a transfer, so clearing `SPI_CS_KEEP_ACTIVE` with no transfer after it leaves the last record held. A pad routed to `FSPICS0`, `FSPICLK`, `FSPID`, `FSPIQ`, `FSPIWP` or `FSPIHD` drives that signal's idle level for as long as it is routed, never the bits: CS deasserted, SCLK at `SPI_CK_IDLE_EDGE`, and each data line at its `SPI_*_POL` bit, which resets to 1. So a pad with a net reads its idle level in `GPIO_IN` during a transfer too, where the chip reads its CS low. A transfer started with slave mode, `SPI_DMA_RX_ENA` or the segmented transfer `SPI_USR_CONF` starts, `SPI_DMA_TX_ENA` with no GDMA OUT channel started on SPI2 or more than one, a descriptor list GDMA refuses or one that does not hold the data phase's bytes, LSB-first bit order, QPI, an octal phase, DTR, a dummy phase, a read phase, `SPI_USR_MOSI_HIGHPART`, the 3-line mode of `SPI_SIO`, the full duplex of `SPI_DOUTDIN`, `SPI_CK_OUT_EDGE`, `SPI_CS0_DIS`, data that is not whole bytes, over 64 bytes from the buffer or over 2^18 bits from DMA, its clock off, or a synced register not yet updated, ends the run with `chip.unsupported_setting` at its store. `SPI_CK_OUT_EDGE` gives clock mode 1 or 2, which samples on the falling edge of SCLK, and a record holds only the bits. `SPI_CONF_BITLEN` times the CONF state of a segmented transfer, so it changes no transfer the model runs. `SPI_CLK_MODE` is kept and not run. Its extra SCLK edges come after CS rises, so they change no record. SPI2 raises no other interrupt, and a write that enables one ends the run, as the interrupt matrix entry says. SPI2's reset bit puts its registers back to their reset values and drops a pending `SPI_TRANS_DONE_INT_RAW`, as the gates entry below says.
- **GDMA, as far as SPI2 and the SHA accelerator send from it.** Each of the five OUT channels keeps its registers. A write of `GDMA_OUTLINK_START` starts the channel's list at the descriptor `GDMA_OUTLINK_ADDR` names in the data-bus SRAM window, and `GDMA_OUTLINK_STOP` or the channel's reset drops it. `GDMA_PERI_OUT_SEL` names the peripheral it feeds, 0 for SPI2 and 7 for the SHA accelerator. A descriptor is three words: `length` in bits 12 to 23, `suc_eof` in bit 30 and `owner` in bit 31, then the buffer's address, then the next descriptor's. When its peripheral starts, the channel reads the whole list at once, each buffer's `length` bytes in turn through the one with `suc_eof`, and its link is then spent, so `GDMA_OUTLINK_PARK` reads 1. On the board GDMA reads the list as the transfer runs, so a store into a byte of an SPI2 transfer's descriptors or buffers before the transfer ends ends the run with `chip.unsupported_setting`, since the model cannot tell which bytes the board had sent. `GDMA_OUT_CHECK_OWNER` refuses a descriptor whose `owner` is clear, and the model writes no descriptor back. A descriptor or a buffer outside the data-bus SRAM, or a list that goes round a loop with no `suc_eof`, is refused too. An IN channel's link is kept and runs nothing. It may name a descriptor in SRAM only for SPI2, which refuses every transfer that would fill it. IDF's shared crypto DMA starts the AES accelerator's IN link at address 0 beside each SHA hash, and a link with no descriptor in SRAM fills nothing. A start of an OUT link for another peripheral than SPI2 or the SHA accelerator, or of an IN link at a descriptor in SRAM for another peripheral than SPI2, ends the run with `chip.unsupported_setting`, and so does a change of a channel's peri_sel while its link is started. GDMA raises no interrupt, and a write of `GDMA_MEM_TRANS_EN`, `GDMA_OUT_AUTO_WRBACK`, `GDMA_INLINK_RESTART` or `GDMA_OUTLINK_RESTART` ends the run with `chip.unsupported_setting`.
- **The SHA accelerator, as far as SHA-256 runs on it.** `SHA_MODE_REG` 2 picks SHA-256. `SHA_START_REG` hashes the block in `SHA_M_MEM` from the SHA-256 initial value, and `SHA_CONTINUE_REG` from the digest in `SHA_H_MEM`. `SHA_DMA_START_REG` and `SHA_DMA_CONTINUE_REG` hash `SHA_BLOCK_NUM_REG` blocks from the GDMA OUT channel started on the accelerator, which ESP-IDF's `mbedtls` uses for more than 256 bytes. A hash ends at the write that starts it, so `SHA_BUSY_REG` reads 0. `SHA_H_MEM` and `SHA_M_MEM` hold their bytes in memory order. A start in another mode, or a DMA hash whose channel or list GDMA refuses, ends the run with `chip.unsupported_setting`, and so does a write that enables its interrupt.
- **LEDC, with the fixed duties ESP-IDF's `ledc` driver sets.** The eight channels' and four timers' registers, the interrupt registers and `LEDC_CONF_REG` keep what is written, from their reset values, and the self-clearing update bits read 0. A timer counts from the store that leaves its `LEDC_LSTIMERn_RST` and `LEDC_LSTIMERn_PAUSE` bits clear. Its period is `LEDC_CLK_DIV_LSTIMERn` over 256, times 2 to the power `LEDC_LSTIMERn_DUTY_RES`, cycles of the clock `LEDC_APB_CLK_SEL` picks: 1, the APB clock, which ESP-IDF's `LEDC_AUTO_CLK` picks, or 3, the 40 MHz crystal. A store that sets `LEDC_PARA_UP_LSCHn` takes channel n's duty and settings as they are then. That update takes effect at the next overflow of the timer the channel names, the next PWM cycle, as ESP-IDF's `ledc_update_duty` says, and a later update before that overflow replaces it. An update on a timer that does not count waits until it does. The duty is `LEDC_DUTY_LSCHn`, bits 18 to 0, whose low 4 bits are a fraction. With `LEDC_DUTY_START_LSCHn` clear the update keeps the duty the last one took. That bit does not clear itself, so the update `ledc_stop` sends after `ledc_update_duty` takes the duty register again. While `LEDC_SIG_OUT_EN_LSCHn` is clear the channel sends its idle level `LEDC_IDLE_LV_LSCHn` as a duty of 0 or of every step. An update that takes effect sends a `Duty` record on each pin with a net whose pad carries the channel through the matrix, with the duty, the resolution and the frequency, the 480 MHz tick rate over the period, rounded. On a pad whose `OUT_INV_SEL` is set the record holds the duty the pad drives, the steps the channel does not send. A store that puts a pad with a net on a channel that has a duty, or that changes that pad's `OUT_INV_SEL`, sends the pad a record at the store, and a store that takes a pad off a channel sends nothing. Channel n's signal, matrix output 73 + n, is high while its duty is above 0 and low at 0, and low at power-on. An inverted pad drives low while the channel's duty is above 0, so it is high only while its record is every step. The signal sends no PWM edges. When an update moves a pad's drive, the move is a stop of its own 1 ps after the record's end, and an update that keeps the drive moves nothing. `LEDC_LSCHn_DUTY_R_REG` and `LEDC_LSTIMERn_VALUE_REG` are not kept. These end the run with `chip.unsupported_setting`: a write that enables an LEDC interrupt, as ESP-IDF's fades do; an update with a fade's `LEDC_DUTY_SCALE_LSCHn`, a nonzero `LEDC_HPOINT_LSCHn` or a duty with a fraction; a counting timer on another clock, on `LEDC_TICK_SEL_LSTIMERn`, at a divider below 256, at a resolution of 0 or above 14, or with a period that is not whole ticks; a duty above its timer's steps, or of every step at 14 bits, which ESP-IDF's `ledc_channel_config` says the hardware does not reach; a change of a counting timer's resolution, divider or tick source, or a pause of it; a change of `LEDC_APB_CLK_SEL`, a cleared LEDC clock gate, or a change of the APB clock under a timer that counts it, while a timer counts; and a store that sets LEDC's reset bit while a pad with a net carries a channel, while an update has yet to take effect, or while an update takes effect at that store, since that pad's last record or that update would outlast the reset. A store that leaves the bit set is not refused. A reset with no such pad or update puts LEDC and its signals back to power-on.
- **The USB Serial/JTAG console.** The firmware writes bytes to `USB_SERIAL_JTAG_EP1_REG`. The unit sends them as one packet when the firmware writes `WR_DONE` to `USB_SERIAL_JTAG_EP1_CONF_REG`, or when the FIFO holds its 64th byte. The host takes each packet at once, so `SERIAL_IN_EP_DATA_FREE` always reads 1. The host sends the bytes of the part's `console` events, as [netlist.md](netlist.md#esp32-s3) says. Each byte is readable from the first tick at or after its time, in the order sent. `SERIAL_OUT_EP_DATA_AVAIL` reads 1 while one is, and a load of `USB_SERIAL_JTAG_EP1_REG` takes it. That load reads 0 while none is. The bytes reach `serial.csv` as usart `USB_SERIAL_JTAG`. Every byte of one packet starts and ends at the cycle the packet went. `USB_SERIAL_JTAG_INT_RAW_REG` reads the latched bits, and SOF, bit 1, when a 1 ms frame of 480,000 ticks has started since that bit was last cleared. Only that read divides. `USB_SERIAL_JTAG_INT_ST_REG` reads the latched bits under `USB_SERIAL_JTAG_INT_ENA_REG`. `SERIAL_IN_EMPTY`, bit 3, is set from reset and at each flush, an empty `WR_DONE` included. `SERIAL_OUT_RECV_PKT`, bit 2, sets when a queued byte's time is at or before now. A clear of that bit drops it, and a byte still queued does not set it again. A byte that arrives after the clear does. `USB_BUS_RESET`, bit 9, never rises. `USB_SERIAL_JTAG_INT_CLR_REG` reads 0 and clears the latched bits named in the word. A clear of `SERIAL_OUT_RECV_PKT` moves the mark a later byte is compared with, and a clear of SOF moves the frame mark. A clear of another bit moves neither. `USB_SERIAL_JTAG_INT_ENA_REG` keeps `SERIAL_OUT_RECV_PKT`, `SERIAL_IN_EMPTY` and `USB_BUS_RESET`. A write that sets any other bit, SOF included, ends the run with `chip.unsupported_setting`, `USB_SERIAL_JTAG` `interrupt`, as the interrupt matrix entry says. Source 96 is high while a latched bit and its enable are both set. While `INT_ENA` is 0 the poll returns low and latches nothing. A read or a write of the unit, and the load of EP1 that takes a byte, latches `SERIAL_OUT_RECV_PKT` once that byte is due. Enabling that bit then raises the level. A clear of another bit leaves the latch. A core in `WAITI` wakes at that byte while the bit is enabled. A store to any register of `USB_WRAP` ends the run with `chip.unsupported_setting`, `USB_WRAP` `otg`. A load of one stays unmodeled.

- **The eFuses.** A fixed synthetic set: a revision 0.2 chip with 8 MB of PSRAM in its package and no flash in it, block version 1.3, the MAC `02:00:00:00:00:01`, and every other bit 0, the calibration and the unique ID among them. The read registers hold it from power-on. A read command finishes at once. A store of `EFUSE_PGM_CMD` to `EFUSE_CMD_REG` would burn eFuses, so it ends the run with `chip.efuse_program` and writes nothing. The other registers keep what is written.
- **SPI1 and the flash.** A write of `SPI_MEM_CMD_REG` runs its one command at once and clears its bits. A write that starts more than one, such as `WREN` with a sector erase, runs none and ends the run with `chip.flash_command`. A user command sends its command byte and the address when `SPI_MEM_USR_ADDR` is set, and leaves the MISO bytes from `SPI_MEM_W0_REG` on. No command the flash runs takes MOSI bytes, and dummy cycles have no effect. The fixed commands `RDSR`, `WREN`, `WRDI` and `RDID` run as their flash commands do. The flash is 16 MB, JEDEC ID `68 40 18`, with its quad enable bit set. It reads, and reports its ID and its three status registers. A status write, the fixed `WRSR` or a user `0x01`, `0x31` or `0x11`, can set the status registers' protect and one-time lock bits, so it ends the run before any status bit changes, with or without `WREN`. The flash has no program or erase, so those end the run too, and so do a read that reaches past its end, an address phase longer than 32 bits, and every command it does not know. A chip with no flash refuses every read, and `RDID` reads `ff ff ff` there. A user command while `SPI_MEM_MISC_REG` has `CS0_DIS` set or `CS1_DIS` clear ends the run with `chip.flash_command`, reason `cs`. The register resets to `0x2`, so CS0 is on and CS1 is off, and the fixed commands do not look at those bits. The controller's other registers keep what is written.
- **The MMU and the cache.** The MMU's 512 entries, at `0x600c_5000`, each map one 64 KB page of the 32 MB space that the instruction bus sees at `0x4200_0000` and the data bus at `0x3c00_0000`. An entry holds a flash page number, bit 14 marks it invalid, and an entry with bit 15, PSRAM, maps nothing. The cache is functional: every access reads the flash through the MMU at once, and a store into either window raises `LoadStoreError`. A load from either window that the MMU maps to no flash, through an invalid entry, a PSRAM entry or a page past the flash's end, ends the run with `chip.unmapped_load`, and a fetch there with `chip.unmapped_fetch`. A chip with no flash maps no page. The cache controller's lock, unlock, sync, occupy and preload operations finish at the write that starts them, autoload reads done, and a freeze reads done while it is on. Its other registers keep what is written.
- **I2C0 as a master.** Port 0, at `0x6001_3000`, runs a command list on SCL and SDA, signals 89 and 90, open drain. Its clock is the 40 MHz crystal over `I2C_SCLK_DIV_NUM` + 1 while `I2C_SCLK_ACTIVE` is set. `I2C_CONF_UPGATE` copies the timing registers into the timing a transfer runs with. SCL low, the SDA hold, the SDA sample and the start and stop setups and holds count their register plus one. `I2C_SCL_WAIT_HIGH_PERIOD` and `I2C_SCL_HIGH_PERIOD` count as stored, so a bit is `low + wait_high + high` cycles. `I2C_TRANS_START` starts the list one cycle of that clock after the store. No source gives that delay, so it is inferred. A bit drives SDA at the hold after SCL falls and releases SCL at the end of the low. The master reads SCL through the input matrix. A pad with no net reads its own output at once. A netted pad reads high at the first input that brings it high, and a target that holds SCL stretches the bit from that input. The sample is the sample length after that input, and SCL falls at the later of the release plus the wait and that input, plus the high period. A wait that reaches `2^I2C_TIME_OUT_VALUE` cycles of that clock ends the run with `I2C0` `timeout`. The register header says APB cycles, and IDF's `i2c_ll_calculate_timeout_us_to_reg_val` counts the I2C clock, so the clock the wait counts is inferred from the driver. An event that moves a netted pad waits for its `Moved` halt before the next event, so each event reads the inputs of the edges before it. A write's ninth bit with the ACK check set and no ACK raises `I2C_NACK_INT_RAW`, makes the stop and clears `I2C_BUS_BUSY` without `I2C_TRANS_COMPLETE_INT_RAW`. A read command sends its `ack_val` bit as the ACK of every byte it reads, as IDF's `I2C_MASTER_NACK`, "nack for each byte read", says. A list's stop raises `I2C_TRANS_COMPLETE_INT_RAW`, source 42. A STOP in the first command makes the stop from the levels the pins already read. When both already read high it waits the setup and the hold and raises the transfer-complete interrupt with no edge. `I2C_CLK_EN` in `I2C_CTR_REG` is kept and not run. A start while `I2C_SCLK_ACTIVE` is clear ends the run with `clock_off`. A start whose SDA hold is at least the SCL low, or whose SDA sample is at least `I2C_SCL_HIGH_PERIOD`, ends it with `timing`. `FILTER_CFG` is kept. The master does not delay a pulse it would filter, and a pulse shorter than the threshold while a transfer runs ends the run with `glitch`. A write of port 1 ends the run with `I2C1` `port`. These also end the run with `chip.unsupported_setting`: slave mode, a pad that is not open drain or not routed to the signal in both directions, LSB first, arbitration, sampling SCL's own level, the RC fast clock, a fractional divider, the non-FIFO mode, an FSM reset, a bus clear, power down, an interrupt enable outside the master's end, arbitration-lost, transfer-complete, timeout and NACK bits, an END command, an opcode the master does not run, a byte count of 0 on a read or a write, a FIFO that underflows or overflows, and a timing or command write while a transfer runs.
- **The analog I2C master.** A write of either control register runs one transaction at once, on the analog block and register it names. A write keeps the byte, and a read leaves the byte last written there, or 0. The analog blocks have no effect, and the PLL's calibration reads done.
- **The RTC clock calibration.** A timer group's calibration finishes the moment `TIMG_RTC_CALI_START` rises, with the count of 40 MHz cycles its slow clock would give at its nominal rate: the 136 kHz RC slow clock, the 17.5 MHz RC fast clock over 256, or the 32.768 kHz crystal. A cycling calibration always reads ready, and none times out.
- **The rest of the boot path.** The permission controls of `SENSITIVE` start at 0 and keep what is written, and no access is checked against them. On a chip booted from flash, every register the captured state names and no model owns keeps what is written, from its captured value.
- **The peripheral clock gates and resets.** `SYSTEM_PERIP_CLK_EN0_REG`, `SYSTEM_PERIP_CLK_EN1_REG`, `SYSTEM_PERIP_RST_EN0_REG` and `SYSTEM_PERIP_RST_EN1_REG` start at their reset values on a bare-metal chip, and at the captured ones on a chip booted from flash. SPI2, LEDC, GDMA, the SHA accelerator and I2C0 run their bits. Each runs while its clock bit is set and its reset bits are clear. A write that leaves one of its reset bits set puts it back to its reset values, and it stays there until they clear. The SHA accelerator is held by the digital signature and HMAC reset bits too, as IDF's `sha_ll_reset_register` says. A load or a store to one of those blocks while its clock is off, or while a reset holds it, ends the run with `chip.unsupported_setting`. So does a write that sets SPI2's reset or clears its clock while a transfer runs, or does that to GDMA while an SPI2 transfer sends from it, or sets I2C0's reset or clears its clock while a transfer runs, and a transfer started from GDMA while its clock is off. Both of those I2C0 writes end as `I2C0` `reset_while_sending`. SPI2's cleared clock stays `clock_off_while_sending`. IDF's restart and panic paths set `SYSTEM_DMA_RST`, GDMA's reset, in `esp_system_reset_modules_on_exit`, so an `esp_restart()` or a panic while SPI2 sends from GDMA ends the run with `GDMA` `reset_while_sending`, in place of `chip.restart` or `chip.halted`. The console holds a panic's text, which IDF prints before that store. The model cannot tell where the board cut the transfer short, so the run does not go on. The bits of SYSTIMER, TIMG0, TIMG1, SPI0 and SPI1, the eFuse controller and the USB Serial/JTAG unit are kept and not run: the block keeps counting and keeps its registers. So are bit 0 and bit 3 of the clock and reset words, which IDF names `SYSTEM_TIMERS_*` and `SYSTEM_WDG_*`. IDF's headers leave them undescribed and no IDF driver gates a block with them, so the model does not know what they gate, and reports a change in case it is a timer or a watchdog the model runs. From the captured state, IDF's `esp_perip_clk_init` sets `SYSTEM_WDG_RST`, since `SYSTEM_WDG_CLK_EN` is clear there, and that write is listed. Every write that changes one of them is listed with `chip.unmodeled_register`, as [Unmodeled registers](#unmodeled-registers) says. Every other bit gates or resets a peripheral the model does not keep, so it has no effect.
- **Writes the model keeps and does not run.** `RTC_CNTL_CLK_CONF_REG` picks the slow clock, and SPI0's `SPI_MEM_USER_REG` to `SPI_MEM_USER2_REG` set the command the cache reads the flash with. A write keeps its word, and the RTC watchdog keeps its 136 kHz slow clock, and the cache reads the flash as before. Every write that changes one of them is listed with `chip.unmodeled_register`, as [Unmodeled registers](#unmodeled-registers) says. A write of SPI0's `SPI_MEM_CMD_REG` that starts a command ends the run with `chip.flash_command`, and `RTC_CNTL_SLEEP_EN` in `RTC_CNTL_STATE0_REG` ends it with `chip.unsupported_setting`.
- **A reset.** A store of `RTC_CNTL_SW_PROCPU_RST` or `RTC_CNTL_SW_SYS_RST` to `RTC_CNTL_OPTIONS0_REG` resets the chip. Before IDF resets after a panic or a watchdog, it records why in `RTC_CNTL_STORE6_REG` as `hint | hint << 16 | 1 << 31`, and `esp_restart` leaves that register 0. A reset with the register 0, or holding the hint `ESP_RST_SW`, is one from `esp_restart`. The model does not run the boot ROM, so the chip stays in reset from that cycle. The core runs no further, each pad drives as at power-on, and the run reports `chip.restart`, a warning, and goes on to `stop_ps`. Any other reset ends the run with `chip.fault_restart`: a hint of a panic, a watchdog or a brownout, another value, or no register at all, as on a bare-metal chip, which keeps none. `RTC_CNTL_SW_APPCPU_RST` resets the APP CPU, as [The two cores](#the-two-cores) says, and reads 0.

The core's own timer interrupts, `CCOMPARE0` to `CCOMPARE2`, and `WAITI` work as `sim-xtensa` models them. A core in `WAITI` skips to its next timer match, the next SYSTIMER alarm, the end of a watchdog's stage, I2C0's next event or the run's limit. A pad edge that raises the GPIO interrupt, and I2C0's transfer-complete interrupt, each wake it at the first cycle after the event.

A `j` to its own address while every interrupt `INTENABLE` enables is at or below the current interrupt level is a loop only an NMI or a watchdog leaves. When the interrupt matrix maps no source to that core's CPU interrupt 14, the NMI, and no watchdog runs, the run ends with `chip.halted` there. While the other core may run, the core waits at the loop instead, and the other core's next store outside SRAM and RTC memory that leaves a source mapped to its NMI lets it run on from the start of that store's instruction. The run ends with `chip.halted` once no core may run and no watchdog runs. ESP-IDF's panic handler ends in such a loop when the app is built to print and halt, after it disables the watchdogs, so such a panic does not run on to `stop_ps` with status `ok`. The panic text the handler printed last can still be in the console's FIFO, because the handler writes no `WR_DONE`, and those bytes are not in `serial.csv`.

The core runs the base ops `sim-xtensa` models, the single-precision FPU, MAC16, the Boolean registers and `s32c1i`, and holds the `q` registers and the `cop_ai` user registers as plain state. `PRID` reads `0xcdcd` on the PRO CPU and `0xabab` on the APP CPU. `witlb` and `wdtlb` keep each 512 MB region's attribute for `ritlb1` and `rdtlb1` to read back, and no access is checked against it. `rer` reads 0 and `wer` writes nothing. An FPU op with `CPENABLE` bit 0 clear raises cause 32, and a `cop_ai` op with bit 3 clear raises cause 35, at the exception vector. `DBREAKA0`, `DBREAKA1`, `DBREAKC0` and `DBREAKC1` read back what was written. `DBREAKCn` bits 0 to 5 are the address mask, a set bit compared and a clear bit ignored, and bits 6 to 31 of the address are always compared. Bit 30 arms the watch for a load and bit 31 for a store. A load or a store that reaches a byte of that window ends the run with `chip.unsupported_setting`, `CPU` `watchpoint`, before the access. An `ee.*` vector op, or any other instruction the core does not model, ends the run with `chip.unsupported_instruction`.

## Booting from flash

The boot ROM and the bootloader do not run. The chip starts with their result.

1. The ROM's sections land by address. The ROM is 384 KB at `0x4000_0000` on the instruction bus, and its last 128 KB also show at `0x3ff0_0000` on the data bus. A section the boot ROM copies into SRAM, its `.data`, lands in SRAM. The ROM is `rom`'s ELF, the one Espressif publishes for revision 0.
2. The captured state applies. It is `crates/esp32/src/s3/boot/state.txt`: the core registers, 612 peripheral registers and 7,234 words of RAM, as a board's bootloader left them at `call_start_cpu0` after a software restart. `WINDOWSTART` keeps only the current frame, because the frames below it are the bootloader's, whose registers outside the window the state lacks, and the app never returns to them. The MMU's entries come from the captured table. Each watchdog's protect word applies as captured, so a watchdog the capture left locked stays locked until the firmware writes the key.
3. The app's segments load. A segment in a cache window is mapped by the MMU from its flash offset, rounded down to a page as the bootloader maps it, over the captured entries. Every other segment is copied into SRAM or RTC memory.
4. The PC is at the image's entry.

So the app runs from its first instruction on the board's clocks, watchdogs and cache state. SYSTIMER's count starts at its latched value registers, which this capture holds at 0, so the app's log times are not the board's. The state's volatile values, such as `CCOUNT` and the RTC time, are one boot's. The bootloader's own console lines and the ROM's are not in the run, which starts at the app's entry.

The capture followed a CPU reset, not a power-on: `RTC_CNTL_RESET_STATE_REG` holds reset reason `0x0c`, `RESET_REASON_CPU0_SW`. A CPU reset leaves the peripherals as the app before it set them. So the state holds that app's interrupt map, such as SYSTIMER's alarm 0 on CPU interrupt 2 and timer group 1's watchdog on 24, its timer group interrupt enables and its peripheral clock gates, where a power-on would hold reset values. IDF also branches on the reason. After `0x0c`, `esp_perip_clk_init` leaves the unused peripheral clocks as they were, where after a power-on it gates them, `rtc_init` skips the calibration it runs only at power-on, and `esp_reset_reason()` returns `ESP_RST_SW`. `hello_world` prints none of this, so its console matches the board's. An app that reads its reset reason, or relies on a peripheral at its reset value, runs a path the board runs only after a CPU reset. A capture after a power-on would remove the difference, and needs the board.

## Unmodeled registers

Peripheral space runs from `0x6000_0000` to `0x600d_1000`. A register there that the model does not keep reads 0, and a write to it is dropped. The run reports each such register once, at its first access, with `chip.unmodeled_register`. It reports the registers the model keeps without running their effect, which [What it models](#what-it-models) lists, at every write that changes one. The warning names the address, the register as its block and offset, such as `UART0+0x0`, whether that access was a write, the PC, and the ELF symbol at or below the PC, or `null` for an app booted from flash. The blocks and their bases are IDF's `reg_base.h`. A byte or halfword access to a kept register reads, or merges into, its word.

A load from a cache window that the MMU maps to no flash ends the run with `chip.unmapped_load`. Any other load outside the chip's memories and peripheral space, or a store outside SRAM, RTC memory and peripheral space, raises `LoadStoreError`. The core takes the exception at its vector. A fetch outside the instruction-bus SRAM window, RTC fast memory, the ROM and the instruction cache window ends the run with `chip.unmapped_fetch`. An instruction the core does not model ends it with `chip.unsupported_instruction`.

## Behind the seam

Each GPIO with a net is one output and one watch, in [`Esp32s3::PINS`](netlist.md#esp32-s3) order. A store that changes the drive of a pad with a net stops the core before its next instruction. That stop is at the store's cycle, and the run lands there, as [engine.md](engine.md#active-chips) says. The drive of a pad with no net is never stamped. A watch flip sets the level that pad's `GPIO_IN` bit reads from the flip's time on, and latches the edge its `INT_TYPE` takes. The run converts ticks to picoseconds by the clocked-core rule in [engine.md](engine.md#active-chips), at 480 MHz.

Each SPI2 transfer is a `Spi` record, as [engine.md](engine.md#records) says, that starts at the store of `SPI_USR` and ends at the transfer's end, a stop of the core. Its phases, lanes, data, clock and CS are the transfer's. Its nets are those of the pads the matrix routed CS, SCLK and D0 to D3 to when the transfer started, the lowest-numbered pad for a signal routed to several, and none for a signal on no pad with a net. In `link.csv` its `pin` is the name of the CS pad, such as `GPIO12`, or `SPI2` when CS is routed to none of the part's [pins](netlist.md#esp32-s3). A store that starts a transfer bounds the core at the transfer's end, and the run lands there. A store that SPI2 refuses stops the core before the store writes.

A fault ends the run at the stop that reports it. The run keeps every row and every byte before that time, and the diagnostic is the error that ends it.

## The examples

`examples/esp32s3-blink` runs `firmware/esp32s3/blink.c` and `firmware/esp32s3/start.S`. The program disables the watchdogs, routes GPIO21 to its `GPIO_OUT` bit, and prints its pin and its period. It then sleeps in `WAITI` while the `CCOMPARE1` interrupt toggles GPIO21 every 4,000,000 cycles, 100 ms, eight times. The interrupt notes the level `GPIO_IN` read before each edge and SYSTIMER after it. The program prints those, and the SYSTIMER span from the first edge to the last. The text it prints is in a comment at the top of `blink.c`.

`scripts/esp32s3-firmware.sh` rebuilds the ELF from those sources with `xtensa-esp32s3-elf-gcc`, GCC 14.2.0 from crosstool-NG esp-14.2.0_20260121. Another compiler builds other bytes. The script files the ELF in `examples/esp32s3-blink/blobs/` under its SHA-256 and writes that hash and its length into the netlist. With `--check` it compares a fresh build with the committed blob.

`scripts/esp32s3_blink.py --check <run>` checks a run folder apart from the engine. The expected text comes from `blink.c`, and the check first holds it to the program's closed form: edge k reads the level edge k - 1 left, and the SYSTIMER span is 7 × 4,000,000 × 2 / 5 counts. `traces/serial.csv` must hold that text byte for byte, as `u1`'s `USB_SERIAL_JTAG`, each line at one time on a cycle boundary. In `traces/logic.vcd`, GPIO21 must change eight times, rising first and alternating. Edge k must sit at cycle k × 4,000,000 + 18. The 18 is the cycles from the `CCOMPARE1` match to the store that changes the pin. It follows from the core's cycle costs and from the run landing each edge on its store's cycle, so the check fails when either moves. `scripts/check.sh` runs the check.

`examples/esp32s3-pattern` runs `firmware/esp32s3/pattern.c` and `firmware/esp32s3/pattern_start.S` on an `st77916` panel wired to GPIO11 to GPIO18 and GPIO21. The program disables the watchdogs, routes SCLK, CS and D0 to D3 to GPIO11 to GPIO16 through the matrix, and drives RST on GPIO17 and the backlight on GPIO21 as plain outputs. SPI2 runs at 10 MHz, the crystal divided by 4. The program resets the panel, sends its init commands, turns the backlight on, and draws five rectangles. Each command is an 8-bit command phase holding the opcode and a 24-bit address phase holding the command shifted left by 8, on one lane. Register parameters follow on one lane, and pixels follow on four lanes in transfers of 64 bytes, with CS kept between them. Its waits sleep in `WAITI` until a `CCOMPARE1` match. It prints `BEGIN pattern` and `END pattern`.

`firmware/esp32s3/pattern.json` holds the init commands, each with its parameters and the milliseconds the program waits after it, and the five rectangles, each with its inclusive corners and a fill rule. `scripts/pattern_header.py` writes `firmware/esp32s3/pattern.h` from it, and `--check` fails unless the committed header is a fresh write. `scripts/esp32s3-firmware.sh` builds this ELF beside the blink one and files it in `examples/esp32s3-pattern/blobs/`.

`scripts/render_st77916.py --pattern firmware/esp32s3/pattern.json --check <run>` checks a run folder apart from the engine. It builds the transfers `pattern.c` sends from `pattern.json` alone, and plays them into its own model of the panel. Each row of `traces/link.csv` must be its expected transfer, each row of `traces/display.csv` its expected pixel write, and `traces/display-lcd1.rgb565` the expected frame byte for byte. It refuses a pattern with a rectangle of one value. `scripts/check.sh` runs both checks, as [reference.md](reference.md) says.

`firmware/esp32s3/watchdog.c` and `firmware/esp32s3/watchdog_start.S` are a test image with no example yet. The program disables the other watchdogs and arms timer group 0's with a prescaler of 40000, a count each millisecond on the 40 MHz crystal. Stage 0 interrupts after 100 counts and stage 1 resets the system 50 counts later, and the program never feeds it. It prints the CPU and APB clock registers, then the microseconds from the arm to stage 0's `INT_RAW` bit, and from 148 ms on the microseconds every 100 us, until the reset. The text it prints is in a comment at the top of `watchdog.c`, and the build command beside it. A run ends with `chip.watchdog` at stage 1, `system`, 150 ms after the store that arms the watchdog, after `us 149900`. No board capture of it is committed, so that time comes from the prescaler and the holds alone.

`examples/esp32s3-hello` boots ESP-IDF v5.5.5's `hello_world` example from its flash, with nothing but the supply on its pins. The app and its components are in `firmware/esp32s3/idf`: one core, the console on USB Serial/JTAG, virtual eFuses, and the board's partition table, which puts the app at `0x10000`. A console task beside the example polls the console for the board's restart commands, and receives none here. The app prints IDF's start-up log, the chip's description and a countdown of eleven lines one second apart, and then resets the chip. That ends the console at about 11.01 s, and the run reaches its stop at 11.1 s.

`scripts/esp32s3-firmware.sh idf` rebuilds the app and the partition table with ESP-IDF v5.5.5 and its toolchain esp-14.2.0_20260121, from a tree where IDF's `export.sh` has run. The build is reproducible, so it does not depend on where the tree lies, and the committed blobs are its bytes. They are the bytes a board ran to print the console the check compares with. `firmware/esp32s3/idf/NOTICE` names the licences of the code the app links. No example commits the ROM, and `scripts/blobs.sh` puts it into its cache folder, as [netlist.md](netlist.md#esp32-s3) says.

`scripts/esp32s3_hello.py --check <run>` checks a run folder apart from the engine. `examples/esp32s3-hello/console.json` holds the console text a board printed for the same app, from its first log line through `Restarting now.`, with each log time masked, since the board's count from its power-on. `traces/serial.csv` must hold that text byte for byte, once its own log times are masked, as `u1`'s `USB_SERIAL_JTAG`. Every adjacent pair of countdown lines, the first pair included, must lie one second apart, within a 10 ms FreeRTOS tick, and the run's last diagnostic must be `chip.restart`, one second after the last countdown line, within a tick. The run must hold no error, and `manifest.json` must list the ROM, then each flash region with its offset. `scripts/check.sh` runs the check.

`examples/esp32s3-screen` boots the app of `firmware/esp32s3/idf/screen` from its flash, on an `st77916` wired as `examples/esp32s3-pattern` wires it. The app runs LVGL 9.3.0 on `esp_lcd_st77916` 2.0.2 with the panel maker's init sequence, over QSPI at 40 MHz. Its colour writes go as queued SPI2 transfers fed by GDMA, which wait on SPI2's interrupt. The backlight is LEDC channel 0 on GPIO21, at 5 kHz and 12 bits, so `traces/link.csv` holds two `Duty` rows on GPIO21: duty 0 when the app configures the channel, and 4095 of 4096 steps when it turns the backlight on, which is the panel's `brightness` at the end. The app waits for `g` on the console, which the netlist sends at 100 ms. It then draws an arc and a label, and ten fixed updates of both, and nothing it draws depends on time. Its `screen/main/wrap.c` prints a line for each panel transfer, each of its SPI transactions and each flush, with the transfer's bytes and a hash the SHA accelerator computes. The app prints `LCD DONE` at about 1.19 s, and the run reaches its stop at 1.2 s.

`scripts/esp32s3-firmware.sh idf` builds this app and its partition table beside `hello_world`'s, with the three components its `dependencies.lock` pins, and files them in `examples/esp32s3-screen/blobs/`. The board ran an image of the same sources with another word in nine of its marker strings, so the two images differ only in those strings and in the two hashes the build writes into an image.

`scripts/esp32s3_screen.py --check <run>` checks a run folder apart from the engine. `examples/esp32s3-screen/board.txt` holds the transfer lines the board printed for that image, in order: 263 transfers, their 529 SPI transactions, and 25 flushes. From those lines alone the check builds each transaction the panel must see, with the command word as four bytes on one lane. Each `spi` row of `traces/link.csv` must be one, in order, with its `CS` state, no phases, its byte count and hash, and its data lanes. Its `duty` rows must be the two the app's source sets on GPIO21, 0 and then 4095 of 4096 steps, at 5 kHz. Each row of `traces/display.csv` one flush, with its rectangle, byte count and hash. `traces/display-lcd1.rgb565` must be the frame memory the board's flushes leave, SHA-256 `882493174920b5371c1e0013545197195abee6055ad2288c35c716aedbc51dfd`, and the console must hold the board's lines with their times left out, since the board's count from its power-on. The run must hold no error, no `chip.protocol` and no `chip.link_miswired`. No time is checked. `--self-test` builds a run folder from `board.txt` and checks that it passes, and that a zeroed or changed frame, an error, either warning, a missing, extra or reordered duty, a duty on another pin, a missing, extra or reordered transaction or flush, a transaction on other lanes or with phases, a moved rectangle and a short console each fail. `scripts/check.sh` runs the check.

`examples/esp32s3-encoder` boots the app of `firmware/esp32s3/idf/encoder` from its flash, with a knob's two contacts on GPIO2 and GPIO1, `sw_a` and `sw_b`, each pulled up by 10 kΩ and closed to ground for one detent. The contacts close and open at the times of `examples/atmega-board-knob`, 200 ms later, so `sw_a` closes four times and `sw_b` three. The app waits for `g` on the console, which the netlist sends at 100 ms, and prints `encoder ready`. A falling-edge interrupt on each pin counts that contact's closings and takes the `esp_timer` time, and a 3 ms `esp_timer` polls both pins and counts a press after two equal reads. The app prints `edge a=<n> b=<m> t=<us>` for each edge and `poll a=<n> b=<m>` for each press, and sleeps in `WAITI` between them. The run reaches its stop at 1.4 s. `scripts/esp32s3-firmware.sh idf` builds the app and its partition table beside `hello_world`'s and files them in `examples/esp32s3-encoder/blobs/`. The partition table is `hello_world`'s, byte for byte.

`scripts/esp32s3_encoder.py --check <run>` checks a run folder apart from the engine. It reads the closings from the example's netlist. `traces/serial.csv` must hold `encoder ready` before the first closing, then one `edge` line for each closing, in time order, with each contact's count after it, and a time from the closing's microsecond to 10 µs after it, since SYSTIMER counts from the run's start. The `poll` lines must hold the same counts in the same order. The run must hold no error, and `manifest.json` must list the ROM, then each flash region with its offset. `--self-test` checks that a good console passes, and that a late, early, lost or miscounted edge, a lost or miscounted poll, a console without `encoder ready`, an error and a region without its offset each fail. `scripts/check.sh` runs the check.

`examples/esp32s3-touch` boots the app of `firmware/esp32s3/idf/touch` from its flash, with a `cst816` on `scl` (GPIO10), `sda` (GPIO9), `tp_int` (GPIO7) and `tp_rst` (GPIO8), and 2.2 kΩ pull-ups to 3.3 V on `scl` and `sda`. The app waits for `g` on the console, which the netlist sends at 100 ms. It holds `tp_rst` low for 10 ms and then high, opens I2C0 at 400 kHz and prints `id b4` for register `0xA7`. It then reads register `0x02` ten times, waiting 33 ms after each of the first nine, and prints `poll f=0` for each. Two touches land after that window, at 1.5 s and 2.0 s, the points (291, 69) and (16, 32). Each pulls `tp_int` low, and the app prints `touch f=1 x=291 y=69` and `touch f=1 x=16 y=32`. The run reaches its stop at 2.6 s. `scripts/esp32s3-firmware.sh idf` builds the app and its partition table beside `hello_world`'s and files them in `examples/esp32s3-touch/blobs/`. The partition table is `hello_world`'s, byte for byte.

`examples/esp32s3-dualcore` boots the app of `firmware/esp32s3/idf/dualcore` from its flash, with nothing but the supply on its pins. The app runs both cores. It pins one task to each, and each task prints `core <c> tick <k>` every 10 ms, twenty times, then `done`. The two tasks may interleave. The run reaches its stop at 0.5 s. The last `done` line is at about 0.21 s. `scripts/esp32s3-firmware.sh idf` builds the app and its partition table beside `hello_world`'s and files them in `examples/esp32s3-dualcore/blobs/`. The partition table is `hello_world`'s, byte for byte.

`scripts/esp32s3_dualcore.py --check <run>` checks a run folder apart from the engine. `traces/serial.csv` must hold each core's twenty `core <c> tick <k>` lines in order, `k` from 0, and a `done` line after that core's last tick. A `done` line names no core, so the check gives it to a core that has already printed tick 19 and has no `done` yet. Other console lines may sit between them. The run must hold no error, and `manifest.json` must list the ROM, then each flash region with its offset. `--self-test` checks that a good console passes, with either line ending, and that a lost tick, a tick out of order, one `done` line, a `done` line before the last tick, an error, another port and a region without its offset each fail. A core that prints its own `done` before the other core's last tick still passes. `scripts/check.sh` runs the check.

`examples/esp32s3-echo` boots the app of `firmware/esp32s3/idf/echo` from its flash, with nothing but the supply on its pins. The app runs one core, with the FreeRTOS tick at 1 ms. It installs the USB Serial/JTAG driver, waits one tick, reads `esp_timer_get_time` as `t` and prints `ready <t>`. It then echoes each console byte as `got <b>`. The netlist sends three bytes, at `t + n·1000 + 500` µs for `n` of 2, 4 and 6, so each sits 500 µs after a millisecond and at least 400 µs before the next tick. The ready line is at about 10.7 ms, and each echo is within 100 µs of its byte. The run reaches its stop at 0.1 s. `scripts/esp32s3-firmware.sh idf` builds the app and its partition table beside `hello_world`'s and files them in `examples/esp32s3-echo/blobs/`. The partition table is `hello_world`'s, byte for byte.

`scripts/esp32s3_echo.py --check <run>` checks a run folder apart from the engine. It reads `t` from `ready <t>` and each byte's time from the run's own `netlist.json`. With `n` the whole thousands in that time minus `t`, the rest must lie from 100 to 700 µs, so a later change that moves `ready` fails as a misplaced byte. Each `got <b>` must be that byte, within 100 µs of the time it was sent, and before the earliest the next tick can be. The run must hold no error, and `manifest.json` must list the ROM, then each flash region with its offset. `--self-test` checks that a good console passes, and that a `got` 1 µs after the next tick and a byte 900 µs past its millisecond each fail. `scripts/check.sh` runs the check.

`firmware/esp32s3/arduino/console` is a sketch. It calls `Serial.begin`, then prints `tick <k> core <c>` from `loop` every 100 ms and echoes each console byte as `got <b>`. `scripts/esp32s3-arduino.sh console` builds it with arduino-cli 1.5.1 and the `esp32:esp32` core 3.3.12. The compile runs in its temporary folder, so the image does not record the directory the script was started from. The script files the app and the partition table in the blob cache by SHA-256. The built files are not committed. `firmware/esp32s3/arduino/checks/console/netlist.json` names those hashes and the ROM. `scripts/esp32s3-arduino.sh --check console` rebuilds the sketch, runs that netlist and runs `scripts/esp32s3_arduino_console.py --check`. The checker wants `tick 0 core 1` through `tick 10 core 1` and each `got` line. The run reaches its stop at 1.1 s, after tick 10. `scripts/check.sh` runs the checker's `--self-test` and does not build the sketch. `firmware/esp32s3/arduino/NOTICE` names the core's licence.

`firmware/esp32s3/arduino/knob` is a sketch. It waits for `g`, brings up an ST77916, draws a screen and ten updates, and prints `KNOB READY`. `loop` prints `K a=<n> b=<m>` for each contact count from a core-0 task, prints `T down <n>` and `T up` for a touch, and prints `KNOB DONE` when it reads `x`. After that line it prints no further `K` line. A touch still prints `T down <n>` and `T up`. `R` prints `KNOB REBOOT APP` and restarts the app. `D` prints `KNOB REBOOT DOWNLOAD` and restarts into the ROM loader. Both work while the sketch waits for `g` and after `KNOB DONE`. `scripts/esp32s3-arduino.sh knob LVGL_DIR` builds it. The caller names an LVGL 9.3.0 tree made by keeping only `library.properties`, `LICENCE.txt`, `lvgl.h`, `lvgl_private.h`, `lv_version.h` and `src/`, and removing every other top-level file and directory. Nothing under those six entries is removed. The script checks that tree, 1017 files hashing to `5734ad146cf77713982329c7712d30b765c761207b3caf5d55a431cf7ea3dc18`, and the ELF `cadfaa8b24a34ebfbb04e4ba36ee74e4104de31ef98220a2c94ec68dd2a176b8`. The app is `7a7e0eb9c0023e052ff40e21ffd222b363d339d23fbf5b4cae61325a741d643f`, 731984 bytes, and the partition table is `148b959cbff1c38aa8e1d5c0ba9d612c54997b945e56a63f41223eef650653a1`, 3072 bytes. The script files the app, the ELF and the partition table in the blob cache by SHA-256, then deletes its temporary folder. That folder is the caller-set `TMPDIR`, or `.scratch/arduino` in the repo when `TMPDIR` is unset or is `/tmp`. The built files are not committed. `firmware/esp32s3/arduino/checks/knob/refs.json` comes from a board session of three agreeing captures. Clockwise drives contact B. `firmware/esp32s3/arduino/checks/knob/netlist.json` names those hashes and the ROM. `scripts/esp32s3_knob.py script` wrote its contact closings and touches from the refs. The netlist sends `g` at 100 ms, an 80 ms closing for each new count from 2.0 s, and `x` at 5580000000000 ps. The run stops at 6080000000000 ps. In that run `KNOB READY` is at 990523775000 ps, and the backlight duties are `0/4096@5000` then `4096/4096@5000`. `scripts/esp32s3_knob.py panel` compares transfers, flushes, `traces/display.csv` and the frame. `--shape` drops the colour hashes and the frame. `marks` compares the other lines from the start line through the done line, and `events` compares the K and T lines. `--check` runs all three and also wants only `chip.unmodeled_register`, `KNOB READY` before 2.0 s, and those two duties. `refs --write` keeps one capture when exactly three different captures agree. It refuses a destination that already exists, a destination that is one of the captures, and two paths that are the same file. A 12-hex address token on a mark line, a K line or a T line is refused. `script` writes an 80 ms closing for each new count and a 300 ms touch for each `T down`. It writes `x` 500 ms after the last touch starts, or 500 ms after the last contact opens when there is no touch, or at 2.5 s when there is neither. `scripts/esp32s3-arduino.sh --check knob LVGL_DIR` rebuilds the sketch, runs that netlist and runs `scripts/esp32s3_knob.py --check` against the refs. `scripts/check.sh` runs `--self-test` and does not build the sketch. Its compare of `script` with the committed netlist catches a moved or removed closing or touch, while a later stop time or an extra console byte other than `x` still matches. `firmware/esp32s3/arduino/NOTICE` names LVGL and the panel port.

`scripts/esp32s3_touch.py --check <run>` checks a run folder apart from the engine. `traces/serial.csv` must hold `id b4`, then ten `poll f=0` lines, then one `touch` line for each point the run's own `netlist.json` holds down, with `f=1` and that point's X and Y. `scripts/i2c_decode.py --timing-s3 400000` must accept the run, and the bytes on the chip's pins must be those reads. The run must hold no error and no `chip.unmodeled_register` for `FILTER_CFG`, and `manifest.json` must list the ROM, then each flash region with its offset. `--self-test` checks that a good console and bus pass, and that a wrong id, a short poll list, a moved point, a touch line with `f=0`, an error, a `FILTER_CFG` warning and a region without its offset each fail. `scripts/check.sh` runs the check.
