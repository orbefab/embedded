# ESP32-S3 SoC

`packages/socs/espressif`, package `orbe-espressif`, is the ESP32-S3 around the `orbe-xtensa` core. Its `s3` module is the chip. `orbe-engine` holds it behind the active chip seam, and each `esp32s3` part of a netlist runs one. [netlist.md](netlist.md#esp32-s3) describes the part.

The register addresses and bit positions come from IDF's `soc/esp32s3` headers, IDF v5.5.5. The electrical values in `packages/engine/tests/circuits/esp32s3-blink` come from the ESP32-S3 Series Datasheet v2.2, Table 5-4.

## How it starts

A part with `firmware.elf` starts as a bare-metal ELF leaves it. Every loadable segment is in SRAM, the PC is at the entry, and the rest of the core is in its reset state. There is no ROM and no flash. The CPU runs on the 40 MHz crystal, so a cycle is 25 ns, and `SYSTEM_SYSCLK_CONF_REG` and `SYSTEM_CPU_PER_CONF_REG` read that clock: 0, and the reset value `0xc`.

A part with `firmware.flash` boots an ESP-IDF app, as [Booting from flash](#booting-from-flash) says. It starts as the board's second-stage bootloader leaves the app at its entry, `call_start_cpu0`, with the CPU on the 80 MHz PLL.

## The two cores

The PRO CPU, core 0, starts at the entry. The APP CPU, core 1, starts from its own reset when firmware releases it: a store that clears `RESETING` in `SYSTEM_CORE_1_CONTROL_0_REG` while it was set, or a store of `RTC_CNTL_SW_APPCPU_RST` to `RTC_CNTL_OPTIONS0_REG`. It then runs from the reset vector at `0x4000_0400` with `CCOUNT` 0. The ROM's reset path polls `SYSTEM_CORE_1_CONTROL_1_REG` and calls the address `ets_set_appcpu_boot_addr` stored there. A part with `firmware.elf` has no ROM, so an APP CPU it releases ends the run with `chip.unmapped_fetch` at the reset vector.

The APP CPU runs while `CLKGATE_EN` is set and `RUNSTALL` and `RESETING` are clear in `SYSTEM_CORE_1_CONTROL_0_REG`, and the RTC stall is off. The RTC stall is on while `RTC_CNTL_SW_STALL_APPCPU_C0` is 2 and `RTC_CNTL_SW_STALL_APPCPU_C1` is `0x21`. A bare-metal chip starts with `SYSTEM_CORE_1_CONTROL_0_REG` at its reset value, `RESETING` set. A chip booted from flash takes the captured `0x1`, `RUNSTALL` set and the reset clear, so ESP-IDF's single-core start-up leaves the APP CPU unstarted. A store that would let an APP CPU run that has not been reset in this run holds it unstarted. ESP-IDF's dual-core start, `cpu_utility_ll_enable_clock_and_reset_app_cpu`, sets `CLKGATE_EN`, clears `RUNSTALL`, then sets `RESETING` and clears it. The APP CPU stays unstarted from the store that clears `RUNSTALL` and starts from its reset at the store that clears `RESETING`. The run ends with `chip.unsupported_setting`, `SYSTEM` `app_cpu_without_reset`, when a store to `SYSTEM_CORE_1_CONTROL_0_REG` that does not set `RESETING` comes first, or when 1,000 PRO CPU cycles pass with no reset, because the model cannot know the state such an APP CPU would run from. The 1,000 cycles are the model's bound, not a chip figure. When `CLKGATE_EN` is already set, the function skips the reset, and the store that later lets the APP CPU run is held the same way.

A store that sets the PRO CPU's own stall fields, `RTC_CNTL_SW_STALL_PROCPU_C0` to 2 and `RTC_CNTL_SW_STALL_PROCPU_C1` to `0x21`, ends the run with `chip.unsupported_setting`, `RTC_CNTL` `pro_cpu_stall`, because the model does not stall the PRO CPU. ESP-IDF's `esp_cpu_stall(0)` writes that pattern, in four stores, a clear and then a set of each field. So code on the APP CPU that stalls the PRO CPU ends the run at its last store, the one that sets `RTC_CNTL_SW_STALL_PROCPU_C1`. Every chip keeps `RTC_CNTL_OPTIONS0_REG` and `RTC_CNTL_SW_CPU_STALL_REG` as words, and a bare-metal chip starts them at 0. Apart from the stall fields and the reset bits, a write to them is kept and runs nothing, and the run does not list it as `chip.unmodeled_register`.

While `CLKGATE_EN` is clear the APP CPU's clock is stopped, and its `CCOUNT` does not count. While `RUNSTALL` or the RTC stall holds it with its clock on, `CCOUNT` counts. A gate edge during a stall splits the hold there. These two rules are inferred from what the gate and the stall are, and no board capture checks them yet.

Both cores count the one CPU clock. The next instruction to run is the one that starts on the earliest cycle, the PRO CPU's at a tie. A store that starts, holds or releases the APP CPU takes effect before either core runs another instruction. A store that the run stops at, to list it with its PC, runs again before the other core runs any instruction, whatever their cycles. If an interrupt falls due on the cycle the store would run again, its core takes the interrupt first, and the other core may run before the store does. So a run split at any cycles runs the same instructions in the same order. A core in `WAITI` sleeps while the other core runs, until its next timer match, SYSTIMER alarm, general-timer alarm, SPI2 or SPI3 end, I2C0 or I2C1's next event, LEDC's next overflow or fade-end interrupt, RMT's next threshold or end, PCNT's next glitch-filter commit, AES or RSA completion, or a UART's next edge, sample or timeout, until the other core stores outside SRAM and RTC memory (other than a SYSTIMER unit's `OP` word while LEDC has no output waiting), or until the chip stops or the engine step ends, as [engine.md](engine.md#active-chips) says, and then polls on the cycle it would have reached polling after each of the other core's instructions. So no core sleeps between engine steps, and an input from the seam never meets one. A core in `WAITI` polls on the first cycle after the input's tick, which is where a core polling after each instruction reads the input, so a pad edge wakes it on the same cycle however the run is split. A change that keeps a core asleep across engine steps must wake it at an input, with a test that pins that cycle. With both cores started, a clock switch lands at the start of the instruction that stores it, a cycle before its store on an instruction that straddles a word. When the other core's straddling access on the same start cycle has already landed a cycle later, the switch lands on that later cycle instead. Neither core sees time go back, and time keeps moving across the switch. Loads and stores are sequentially consistent at instruction granularity, so `s32c1i` is atomic across the cores, and nothing models bus contention between them. `PRID` reads `0xcdcd` on the PRO CPU and `0xabab` on the APP CPU.
Each core keeps the instructions it has decoded, keyed by the address and the chip's code version, and it looks before it fetches. The bytes are checked when an instruction is kept. A store into a 64-byte line of SRAM or RTC fast memory that a fetch has read, a flash program or erase, a loader write, attaching flash, or an MMU entry that changes moves the code version, so the next instruction is fetched and decoded again. A rewound core keeps no decodes. After a step that takes no interrupt, does not wait or count `ICOUNT`, and runs an op that writes none of `PS`, `INTENABLE`, the pending interrupts, `ICOUNT`, `ICOUNTLEVEL`, `CCOUNT` and the `CCOMPAREn`, a core runs its kept decodes back to back as a straight run. Before each op it only marks the step's start and compares the cycle with the slice's end, its next timer match and the cycle its lines can next move at. The run ends at an op that writes one of those registers, at an exception, at a load or a store that can move the lines, at an instruction it keeps no decode of at the current version, or at that cycle. In a straight run, an op whose window overflow, coprocessor, loop end and jump-to-itself checks find nothing runs in line when it is one the firmware runs most: the integer arithmetic, logic, shift, move and multiply ops, `rsr.ccount`, `memw`, the loads, `l32r`, the stores of a byte, a half or a word, the branches and jumps, the calls, `entry` and the returns. Every other op, and an op a check stops, runs the full way. The kept decode, the straight run and the ops run in line change no output.

A core reads its interrupt lines only when they could have changed. After a read, it keeps those lines until the bus reports its next event, until a load or a store outside SRAM, RTC memory, the ROM and the flash windows, or until the next run of that core. A load of a UART's `STATUS` word, of USB Serial/JTAG's `EP1_CONF` or of any system timer register keeps the lines, because none of those reads changes a line. A store to a system timer unit's `OP` word (`SYSTIMER_UNIT0_OP_REG` or `SYSTIMER_UNIT1_OP_REG`) keeps the lines too while LEDC has no output waiting, because it only latches the count and sets `VALUE_VALID`; while LEDC has output waiting it rearms the run, so it ends the straight run and moves the lines then. A store to any other system timer register, a store to a UART's `STATUS` word or `EP1_CONF`, and a FIFO load still move them. A slice with one cycle of room does not ask, and its next slice reads again. A longer slice asks while it reads. A slice asks each of the system timer, the general timers, SPI2 and SPI3, USB Serial/JTAG, RMT, the UARTs, LEDC, PCNT, AES and RSA at its first read. After that it asks a block again only after an access to that block, or once the block's last answer has come, and keeps the other answers. An access to SPI2, SPI3, RMT, a UART or `USB_SERIAL_JTAG_CONF0_REG`, which can drive a pad a UART or PCNT samples, also makes the UARTs and PCNT answer again, and an access to any other peripheral makes every block answer again. A build with debug assertions asks every block on each read and panics if a kept answer differs. A skipped read and a kept answer change no output. A build with `poll-skip-check` reads the lines on each skipped step and panics if they moved. That read settles and stamps the way a poll does. It does not run the stamp a skipped poll uses. Before each op of a straight run, that build also panics if a full step there would take an interrupt, wait, count `ICOUNT`, yield or find the fetch held. It also runs each op a straight run takes in line with no load or store again, the full way, on a copy of the core, and panics if the two cores differ.

## The timeline and the clock

Every peripheral counts ticks of 480 MHz, the least common multiple of the clocks the CPU runs on. The core counts its own cycles, and each maps to ticks from the last change of the CPU clock. The CPU runs on the crystal divided by `SYSTEM_PRE_DIV_CNT` + 1, or on the PLL at 80, 160 or 240 MHz as `SYSTEM_CPUPERIOD_SEL` picks. 240 MHz needs the 480 MHz PLL, which `SYSTEM_PLL_FREQ_SEL` set picks, so `SYSTEM_CPUPERIOD_SEL` 2 with the 320 MHz PLL is a reserved value. After a store to either register, the next cycle runs on the clock it picks. The watchdogs keep their counts across the change. A general timer keeps the counts it has taken and drops a partial divider period. The RNG keeps the APB cycles it has already counted. The APB clock is 80 MHz while the CPU runs on the PLL, and the CPU's own clock while it runs on the crystal. A store that picks the RC fast clock, or a reserved value, ends the run with `chip.unsupported_clock`.

## What it models

- **SRAM.** 512 KB, seen through two windows. From `0x4037_0000` to `0x403e_0000` on the instruction bus it is SRAM from byte 0. From `0x3fc8_8000` to `0x3fd0_0000` on the data bus it is SRAM from byte `0x8000`. So `0x4037_8000` and `0x3fc8_8000` are one byte. The core fetches only through the instruction window, and loads and stores through either. Through the instruction window only an aligned word goes, as on the board. A byte or halfword access, and an `l32ai`, `s32ri` or `s32c1i`, raises `LoadStoreError`, cause 3. An unaligned access raises `LoadStoreAlignment`, cause 9. The access's address goes to `EXCVADDR`, and a store writes nothing.
- **GPIO, IO_MUX, the GPIO matrix and the GPIO interrupt.** A pad drives from the matrix when its IO_MUX function is the GPIO one. That is function 1 on every pad, or function 0 on a pad whose function 0 is its GPIO: GPIO0 to GPIO21, GPIO33 to GPIO38, GPIO45 and GPIO46. Signal 256 in `GPIO_FUNCn_OUT_SEL_CFG` is the pad's own `GPIO_OUT` bit, enabled by its `GPIO_ENABLE` bit. `OUT_INV_SEL`, `OEN_SEL` and `OEN_INV_SEL` act as the headers say, and with `OEN_SEL` clear the peripheral enables the pad, as SPI2 and SPI3 do each of their outputs. A pad routed to an SPI2 or SPI3 output drives that signal's idle level, as the SPI2 and SPI3 entry below says. A pad routed to I2C0's SCL or SDA, signals 89 and 90, or I2C1's, signals 91 and 92, drives that signal open drain while a transfer runs, as the I2C0 and I2C1 entry below says. A pad routed to signal 81, RMT channel 0, drives `IDLE_OUT_LV` while `IDLE_OUT_EN` is set, and low while it is clear, as the RMT entry below says. A pad routed to UART0, UART1 or UART2 TXD, signals 12, 15 and 18, drives that signal. It is high at power-on, the idle mark, as the UART entry below says. GPIO43 in IO_MUX function 0 drives UART0 TXD, and GPIO17 in function 2 drives UART1 TXD. The peripheral enables the pad, and `OUT_INV_SEL` does not apply. UART2 has no such pin. A pad on any other function, or routed to another signal, drives nothing, because no other peripheral output is modelled. While `USB_SERIAL_JTAG_USB_PAD_ENABLE` is set (as at reset), the USB PHY owns GPIO19 and GPIO20, so the GPIO matrix does not drive them until software clears that bit, and GPIO20 pulls up through the USB PHY's 2.4 kohm D+ pull-up while the D+ pull-up is on (ESP-IDF v5.5.5 `soc/esp32s3/register/soc/usb_wrap_struct.h` and `hal/esp32s3/include/hal/usb_serial_jtag_ll.h`, `PULLUP_VALUE = 0`). A pad whose `GPIO_PINn` sets `PAD_DRIVER` is open drain, and drives nothing for a high level. A pad that does not drive pulls up while its `FUN_WPU` is set and pulls down while its `FUN_WPD` is set. With both set it pulls to both rails, each through its own resistor, as the pad's two resistors do. A pad with a net stamps its pull-down only when the part names `pull_down_resistance`, as [netlist.md](netlist.md#esp32-s3) says. A store that sets `FUN_WPD` on a pad with a net, while the part names none, ends the run with `chip.unsupported_setting`, `IO_MUX` `pull_down`, and writes nothing: the model has no resistor to stamp, and a silent open pin would read wrong. A pad with no net is never stamped, so the bit is kept and the pad still reads 0 under the pull-down alone. ESP-IDF's `gpio_config` sets `FUN_IE`, clears `FUN_WPU` and sets `FUN_WPD` for `GPIO_PULLDOWN_ENABLE`, and arduino-esp32 3.3.12's `pinMode(pin, INPUT_PULLDOWN)` calls it so. `GPIO_IN` and `GPIO_IN1` read 0 on a pad whose `FUN_IE` is clear. A pad with a net reads its net. A pad with no net reads what it drives, else its pull: 1 under the pull-up alone, 0 under the pull-down alone or neither, and its last level under both, since two equal pulls hold it at half the supply, between the input thresholds. The input matrix's `GPIO_FUNCn_IN_SEL_CFG_REG` words are kept. I2C0 reads signals 89 and 90 and I2C1 reads signals 91 and 92 through them while a transfer samples the bus, PCNT reads its 16 pulse and control signals (33 to 48) through them, and each UART reads its RXD signal through them, signals 12, 15 and 18, while `SIG_IN_SEL` is set, as the UART entry below says. With `SIG_IN_SEL` clear, UART0 RXD reads GPIO44 while that pad's function is 0 and `FUN_IE` is set, and UART1 RXD reads GPIO18 while its function is 2 and `FUN_IE` is set. A clear `SIG_IN_SEL` with no such pad reads the idle mark. `INT_TYPE` in `GPIO_PINn` picks what interrupts: 1 a rising edge, 2 a falling edge, 3 either edge, 4 a low level and 5 a high level. Each change of a pad's `GPIO_IN` bit, from its net, its own drive or a write that moves either, latches an edge its type takes into `GPIO_STATUS_REG` or `GPIO_STATUS1_REG`, whether its interrupt is enabled or not, and `GPIO_STATUS_W1TC_REG` and `GPIO_STATUS1_W1TC_REG` clear it. A level type reads set there while its level holds, so a clear does not clear it. `GPIO_PCPU_INT_REG` and `GPIO_PCPU_INT1_REG` read those bits of the pads whose `INT_ENA` bit 0 is set, and source 16, the GPIO interrupt, is high while either is nonzero. The model takes a pad's level at the time it lands, with no synchronizer, so `SYNC1_BYPASS`, `SYNC2_BYPASS` and `CONFIG` are kept and not run, and every write that changes one is listed with `chip.unmodeled_register`, as [Unmodeled registers](#unmodeled-registers) says. A `GPIO_PINn` write ends the run with `chip.unsupported_setting` and writes nothing when it sets another `INT_ENA` bit, the NMI or an SDIO interrupt, as `GPIO` `pin_int_ena`, when it sets the reserved `INT_TYPE` 6 or 7, as `pin_int_type`, and when it sets `WAKEUP_ENABLE`, as `pin_wakeup`. `GPIO_STATUS_W1TS_REG`, the NMI and SDIO interrupt words and `GPIO_STATUS_NEXT_REG` are not kept. GPIO26 to GPIO32 are the flash's pads, `SPICS1`, `SPIHD`, `SPIWP`, `SPICS0`, `SPICLK`, `SPIQ` and `SPID`, which IO_MUX function 0 gives SPI0 and SPI1. Firmware that took one could send the flash any command through the matrix. So a write that gives one of them another function, sets its `GPIO_ENABLE` bit, or moves its `GPIO_FUNCn_OUT_SEL_CFG_REG` from its reset value ends the run with `chip.flash_command` and writes nothing. IDF's start-up sets their drive and pulls in function 0, and those writes are kept.
- **RTC memory.** RTC fast memory, 8 KB at `0x600f_e000` on both buses, and RTC slow memory, 8 KB at `0x5000_0000` on the data bus. The core fetches from RTC fast memory too.
- **SYSTIMER.** It counts at 16 MHz, the crystal times 2 over 5, whatever clock the CPU runs on. Unit 0 works from power-on and unit 1 does not, as `SYSTIMER_CONF` resets. `SYSTEM_SYSTIMER_RST` puts the timer back to those registers, count and alarms included, and it stays there while the bit is set. `UPDATE`, the value registers, `VALUE_VALID`, the load registers and the load strobes work. Each of the three alarms compares its unit with its target while its `WORK_EN` bit is set. A load through `COMPn_LOAD` takes the target, or in period mode the unit's count plus the period. A write of `TARGETn_CONF` that sets period mode on an alarm with no fire pending, as a fired target alarm is, arms it at the unit's count plus the period. A write that sets period mode on an alarm still pending keeps its count. ESP-IDF's dual-core start loads alarm 1 in target mode, where it fires at once, and then sets period mode, so core 1's tick runs from that write, half a period after core 0's, as `port_systick.c` intends. No source shows what the chip does at that write. The rule follows ESP-IDF's comment. A target alarm fires once its unit reaches the target, and a period alarm fires each period after the load. A firing alarm sets its `INT_RAW` bit, and its interrupt line is that bit and its `INT_ENA` bit. A core in `WAITI` skips to the next alarm.
- **The interrupt matrix.** Each core has a map. Source n's map register, at offset 4 × n of `INTERRUPT_CORE0` for the PRO CPU and of `INTERRUPT_CORE1`, `0x800` above it, for the APP CPU, names the CPU interrupt it drives on that core. The APP CPU's map starts at 16, a core timer interrupt, as the chip resets it. A CPU interrupt's line is high while any source mapped to it on that core is high. A source mapped to one of the core's internal interrupts, such as a timer, drives nothing. The status registers of both halves show each source's level. The sources are the GPIO interrupt, 16, SPI2's and SPI3's, 21 and 22, UART0's, UART1's and UART2's, 27 to 29, LEDC's, 35, RMT's, 40, PCNT's, 41, I2C0's and I2C1's, 42 and 43, the general timers T0 and T1 of timer groups 0 and 1, 50, 51, 53 and 54, the watchdogs of those groups, 52 and 55, the three SYSTIMER alarms, 57 to 59, GDMA IN channels 0 to 4, 66 to 70, GDMA OUT channels 0 to 4, 71 to 75, RSA's, 76, AES's, 77, SHA's, 78, the four `FROM_CPU` registers of the SYSTEM block, 79 to 82, which firmware raises and clears by writing bit 0, and the USB Serial/JTAG interrupt, 96. Every other source stays low. So a write that enables an interrupt the model never raises ends the run with `chip.unsupported_setting`. Those writes set a bit of SPI2's or SPI3's `SPI_DMA_INT_ENA_REG` other than `SPI_TRANS_DONE_INT_ENA`, of GDMA's `GDMA_IN_INT_ENA_CHn_REG` other than `IN_DONE`, `IN_SUC_EOF` and `IN_ERR_EOF`, of GDMA's `GDMA_OUT_INT_ENA_CHn_REG` other than `OUT_DONE`, `OUT_EOF` and `OUT_TOTAL_EOF`, of `USB_SERIAL_JTAG_INT_ENA_REG` other than `SERIAL_OUT_RECV_PKT`, `SERIAL_IN_EMPTY`, `IN_TOKEN_REC_IN_EP1` and `USB_BUS_RESET`, of `SHA_INT_ENA_REG` other than bit 0, of `AES_INT_ENA_REG` other than bit 0, of `RSA_INTERRUPT_REG` other than bit 0, of `LEDC_INT_ENA_REG` other than the timer overflow and channel duty-change-end bits (bits 0 to 11), of `PCNT_INT_ENA_REG` other than unit bits 0 to 3, of `RMT_INT_ENA_REG` other than the channel 0 end, threshold and loop bits, or of a UART's `UART_INT_ENA_REG` other than the RX FIFO full, TX FIFO empty, parity error, frame error, overflow, break, RX timeout, TX done and wakeup bits. Wakeup is kept and never raised. The map registers take any source, since IDF maps the watchdog, cache error and permission sources at start-up. A cache access the MMU does not map ends the run before its interrupt would rise. No access is checked against the permission controls, so their sources never rise. The model has no brownout detector, so `RTC_CNTL_BROWN_OUT_INT_ENA`, which IDF sets at start-up, is kept and raises nothing.- **The watchdogs.** The RTC watchdog and the main watchdog of each timer group. Each runs while its `EN` bit is set and a stage acts, or while its flash boot bit is set. That bit is set at power-on on the RTC watchdog and on timer group 0's, as the boot ROM leaves them, and in flash boot mode stage 0 resets the system, or on the RTC watchdog the RTC domain. A running watchdog counts each stage's hold in turn from stage 0, and after stage 3 stage 0 again. A timer group's stage n holds its `TIMG_WDTCONFIG` word n + 2. A timer group's watchdog counts the APB clock through its prescaler. On a bare-metal chip, timer group 0's first stage runs out at 26,000,000 cycles, 0.65 s, and the RTC watchdog's at 400,000 cycles of a 136 kHz slow clock, about 2.94 s. That is its `WDTCONFIG1`, 200,000 at power-on, times 2, the multiplier for eFuse `WDT_DELAY_SEL` 0, which the eFuse set holds. The RTC watchdog's later stages hold `WDTCONFIG2` to `WDTCONFIG4`. A stage that runs out does what its field of `CONFIG0` says. One that does nothing or interrupts leads to the next stage. A timer group's watchdog interrupt sets bit 2 of the group's `TIMG_INT_RAW_TIMERS_REG` until `TIMG_INT_CLR_TIMERS_REG` clears it, and its source is high while that bit and bit 2 of `TIMG_INT_ENA_TIMERS_REG` are set. A stage that resets the CPU, the system or the RTC domain ends the run with `chip.watchdog`, which names the watchdog, the stage and the reset. ESP-IDF's interrupt watchdog on timer group 1 and its task watchdog on timer group 0 interrupt at stage 0 and reset the system at stage 1, and the RTC watchdog its bootloader leaves running resets the RTC domain at stage 0. A write that leaves a running watchdog a stage the model does not run, at or before its first stage that resets, ends the run with `chip.unsupported_setting`: an interrupt of the RTC watchdog, a CPU reset while `PROCPU_RESET_EN` is clear, or a field that names no action. Every write but the one to the write-protect register needs `0x50d83aa1` there, and the key is in place at power-on. A write takes effect at once, so `TIMG_WDT_CONF_UPDATE_EN` is not needed, and a hold written below the count runs out at the write. A write to the feed register, or one that starts the watchdog, counts stage 0 again. The super watchdog's two registers are kept, and start unlocked with `SWD_SIGNAL_WIDTH` 300 as on the chip. ESP-IDF's bootloader sets `SWD_AUTO_FEED_EN`, which the captured state holds, and the bare-metal examples set `SWD_DISABLE`. Neither IDF nor the TRM's register list gives the time the super watchdog runs out, so a write that leaves both bits clear ends the run with `chip.unsupported_setting`, and the super watchdog never runs out. A bare-metal chip starts with both clear, as at power-on, and it does not run out there either. The refusal stays because that time is unknown, so a program that feeds the super watchdog by hand ends the run, while one that never writes `RTC_CNTL_SWD_CONF_REG` runs on where a board could reset.
- **The general timers.** T0 and T1 of timer groups 0 and 1. Each counts a 54-bit value while its `EN` bit is set, the group's clock bit is set and its reset bit is clear. The divider is `TIMG_Tx_DIVIDER`. A field of 0 divides by 65536 and a field of 1 divides by 2, as the technical reference §12.2.1 says, and the reset field is 1. A store that changes that field while `EN` is set ends the run with `chip.unsupported_setting`, `TIMG0` or `TIMG1` `divider`, and writes nothing. The manual says to disable the timer before changing the prescaler, and otherwise the result is unpredictable. A `TIMG_Tx_DIVCNT_RST`, a change of `TIMG_Tx_INCREASE` and a change of `TIMG_Tx_USE_XTAL` while `EN` is set are kept. `USE_XTAL` selects the clock, and the prescaler warning does not cover it. The clock is the APB clock, or the undivided 40 MHz crystal while `TIMG_Tx_USE_XTAL` is set, not the divided CPU clock. The counter steps up or down, one step per divider period. The first step is a whole period after it is enabled, reloaded, or `TIMG_Tx_DIVCNT_RST` is written, and that bit reads 0. A load copies `TIMG_TxLOADHI_REG` and `TIMG_TxLOADLO_REG` at that write. `TIMG_TxUPDATE_REG` latches the count into `TIMG_TxHI_REG` and `TIMG_TxLO_REG`, which read the latch, and a write of those value registers is kept and ignored. While `TIMG_Tx_ALARM_EN` is set, the alarm fires when the count reaches `TIMG_TxALARMHI_REG` and `TIMG_TxALARMLO_REG`, except when the alarm is enabled, or the count or the alarm changes while it is enabled, and the pair is one of the immediate cases in §12.2.3. Counting up, those cases are `0 ≤ count − alarm < 2^53`, which includes an equal alarm, and `alarm − count > 2^53`. Counting down, they are the mirror: `0 ≤ alarm − count < 2^53` and `count − alarm > 2^53`. An immediate alarm fires at that write. A difference of exactly `2^53` waits half a turn and then fires as the count reaches the alarm. The fire sets that timer's bit of `TIMG_INT_RAW_TIMERS_REG`, clears `TIMG_Tx_ALARM_EN`, and with `TIMG_Tx_AUTORELOAD` copies the load value into the count. A one-shot leaves the count where it is. It is at the alarm when the count reached it, and it is the count the timer already held when the alarm was immediate. ESP-IDF's `gptimer` re-enables `ALARM_EN` in the alarm interrupt after an auto-reload, so a reload above the alarm, within `2^53` counts, fires again at that store. Sources 50, 51, 53 and 54 are high while that raw bit and its `TIMG_INT_ENA_TIMERS_REG` bit are set. `TIMG_INT_ST_TIMERS_REG` reads the raw bits under the enables. A write of 1 to a bit of `TIMG_INT_RAW_TIMERS_REG` clears that raw bit, and `TIMG_INT_CLR_TIMERS_REG` clears the bits named in the word. Both clear T0, T1 and the watchdog. A write of the status register changes nothing. A core in `WAITI` skips to the next alarm. A distance whose product does not fit in the tick range is not scheduled. A half turn at divider 2 is scheduled, and a half turn at divider 65536 is not. `TIMG_REGCLK_REG` and `TIMG_NTIMERS_DATE_REG` are not kept. While the group's reset bit is set the two timers, the group's watchdog and `TIMG_INT_ENA_TIMERS_REG` sit at their reset values and a store to them does not stick. While the clock bit is clear they keep the count they have taken and do not advance. A load or a store is not refused while the group is gated.
- **The hardware RNG.** `WDEV_RND_REG`, `0x6003_507c`, returns the next word of a 32-bit shift register. Each whole APB cycle shifts two bits in at the bottom, a splitmix of the fixed seed `0xE532_5A17_C0DE_0001` and the APB-cycle index. The word at cycle 0, before any cycle has shifted, is `0xA5C3_3C5A`. A read in the same APB cycle returns the same word, and after 16 APB cycles the word holds only bits shifted in since then. On the ESP32-S3, IDF's `esp_random`, in `components/esp_hw_support/hw_random.c`, waits `APB_CYCLE_WAIT_NUM` APB cycles, 1778, and XORs the reads it takes while it waits. The comment in that function still says 16. The model does not insert that wait. The firmware does. The word, the tick it is settled through and the cycle count are part of the chip, so a rewind replays the stream, and a second run of the same netlist starts from the same seed. Nothing in the netlist and nothing on the host changes the seed. A board's register is truly random, so no capture of its words can match this stream. The model promises a deterministic, non-zero, well-mixed stream while `SYSTEM_WIFI_CLK_RNG_EN` is set. That is bit 15 of `SYSTEM_WIFI_CLK_EN_REG`, `0x6002_6014`. A read while the bit is clear ends the run with `chip.unsupported_setting`, `RNG` `clock_off`. The technical reference says only that a read with no entropy source returns pseudo-random numbers. A board capture on 2026-11-18 read `WDEV_RND_REG` with `SYSTEM_WIFI_CLK_RNG_EN` clear, once on each of three boots, and got `399b27b6`, `eb4ad9a5` and `d13ad83e`. The words are non-zero and different on every boot, so no fixed value can stand in for the register. The bit is set in the register's reset value `0xfffce030` and in the captured boot word `ffffdfdf`. A bare-metal chip has not kept the register, so it reads the stream, and a write the boot did not leave in the capture cannot gate it. The stream is indexed by APB cycles, including cycles the bit was clear, so a chip that turns the bit back on reads the word an always-on chip reads at that cycle. A write of `WDEV_RND_REG` is not kept. A write of the clock register is kept when the boot left it, and the model does not refuse it: `esp_perip_clk_init` writes it while IDF starts.
- **SPI2 and SPI3 as masters.** Two instances of one model: SPI2 at `0x6002_4000` (signals `FSPICLK` 101, `FSPIQ` 102, `FSPID` 103, `FSPIHD` 104, `FSPIWP` 105, `FSPICS0` 110; interrupt source 21; GDMA peripheral 0) and SPI3 at `0x6002_5000` (signals `SPI3_CLK` 66, `SPI3_Q` 67, `SPI3_D` 68, `SPI3_HD` 69, `SPI3_WP` 70, `SPI3_CS0` 71; interrupt source 22; GDMA peripheral 1). The firmware writes up to 64 bytes into `SPI_W0` to `SPI_W15`, or points a GDMA OUT channel at them and sets `SPI_DMA_TX_ENA`, and sets `SPI_USR`. The controller then sends a command phase of `SPI_USR_COMMAND_BITLEN` + 1 bits, from bit 7 of `SPI_USR_COMMAND_VALUE` down to bit 0 and then from bit 15 down to bit 8, an address phase of the top `SPI_USR_ADDR_BITLEN` + 1 bits of `SPI_ADDR`, and `SPI_MS_DATA_BITLEN` + 1 bits of data, each when its `SPI_USR_*` bit is set and each on one, two or four lanes as `SPI_FCMD_*`, `SPI_FADDR_*` and `SPI_FWRITE_*` say. It lasts `SPI_CS_SETUP_TIME` + 1 clocks when `SPI_CS_SETUP` is set, each phase's bits over its lanes, rounded up, and `SPI_CS_HOLD_TIME` clocks when `SPI_CS_HOLD` is set. Each of those counts is 0 when its enable is clear. With `SPI_USR_MISO` it reads on MISO, on one lane: `SPI_MS_DATA_BITLEN` + 1 bits after the data, which add their clocks, or with `SPI_DOUTDIN` one byte beside each byte it sends. The record's D1 is the pad `FSPIQ` or `SPI3_Q` drives, or on a read the pad its input reads. The bytes the target answers land in `SPI_W0` on, the first in the low byte of `SPI_W0`, at the transfer's end, before the firmware can read `SPI_USR` as 0. A byte no target answers reads `0xFF`. CS setup and hold follow IDF's whole-clock reading, not the TRM's extra half clock, until a capture settles it. The controller has a clock only while `SPI_CLK_EN` and `SPI_MST_CLK_ACTIVE` are set in `SPI_CLK_GATE`. `spi_ll_master_init` sets `SPI_MST_CLK_ACTIVE`, and `spi_ll_enable_clock`, which `spi_bus_initialize` calls, sets `SPI_CLK_EN`. A clock is the source `SPI_MST_CLK_SEL` picks, the 80 MHz `PLL_F80M` or the 40 MHz crystal, divided as `SPI_CLOCK` says, and the length is rounded up to whole core cycles. With `SPI_DMA_TX_ENA` the data is the bytes of the one GDMA OUT channel started on that controller, read from its descriptor list when `SPI_USR` is written, up to 2^18 bits. `SPI_USR` reads 1 until the transfer ends, and `SPI_TRANS_DONE_INT_RAW` sets at its end. Its interrupt source is high while that bit and `SPI_TRANS_DONE_INT_ENA` are set, which `esp_lcd`'s queued transfers wait on. `SPI_DMA_INT_CLR_REG` and `SPI_DMA_INT_SET_REG` clear and set the raw bits, and `SPI_DMA_INT_ST_REG` reads them under the enables. A write of `SPI_USR` while a transfer runs starts nothing. `SPI_UPDATE` reads 0 at once and syncs `SPI_ADDR` to `SPI_DOUT_MODE` into the controller's clock domain, the registers IDF's `spi_ll.h` has a segmented transfer's CONF phase reload. A transfer runs on the synced registers, so a start while one of them differs from its value at the last update is refused. A store that sets both `SPI_USR` and `SPI_UPDATE` starts on the registers the update before it synced. `SPI_CS_KEEP_ACTIVE` keeps CS asserted after the transfer. CS changes only at a transfer, so clearing `SPI_CS_KEEP_ACTIVE` with no transfer after it leaves the last record held. A pad routed to CS0, CLK, D, Q, WP or HD drives that signal's idle level for as long as it is routed, never the bits: CS deasserted, SCLK at `SPI_CK_IDLE_EDGE`, and each data line at its `SPI_*_POL` bit, which resets to 1. So a pad with a net reads its idle level in `GPIO_IN` during a transfer too, where the chip reads its CS low. A transfer started with slave mode, `SPI_DMA_RX_ENA` or the segmented transfer `SPI_USR_CONF` starts, `SPI_DMA_TX_ENA` with no GDMA OUT channel started on that controller or more than one, a descriptor list GDMA refuses or one that does not hold the data phase's bytes, LSB-first bit order on a write or on a read, QPI, an octal phase, DTR, a dummy phase, a read on two or four lanes, `SPI_USR_MOSI_HIGHPART` or `SPI_USR_MISO_HIGHPART`, the 3-line mode of `SPI_SIO`, full duplex with the data on more than one lane, `SPI_CK_OUT_EDGE`, `SPI_CS0_DIS`, data that is not whole bytes, over 64 bytes from the buffer or with a read, or over 2^18 bits from DMA, its clock off, or a synced register not yet updated, ends the run with `chip.unsupported_setting` at its store. `SPI_CK_OUT_EDGE` gives clock mode 1 or 2, which samples on the falling edge of SCLK, and a record holds only the bits. `SPI_CONF_BITLEN` times the CONF state of a segmented transfer, so it changes no transfer the model runs. `SPI_CLK_MODE` is kept and not run. Its extra SCLK edges come after CS rises, so they change no record. Neither controller raises any other interrupt, and a write that enables one ends the run, as the interrupt matrix entry says. Each controller's reset bit puts its registers back to their reset values and drops a pending `SPI_TRANS_DONE_INT_RAW`, as the gates entry below says.
- **GDMA, five OUT and IN channel pairs with descriptor writeback and interrupts.** Each of the five channel pairs keeps its registers. A write of `GDMA_OUTLINK_START` starts the OUT channel's list at the descriptor `GDMA_OUTLINK_ADDR` names in the data-bus SRAM window, and `GDMA_OUTLINK_STOP` or the channel's reset drops it. `GDMA_PERI_OUT_SEL` names the peripheral it feeds: 0 for SPI2, 1 for SPI3, 6 for AES and 7 for SHA. A descriptor is three words: `size` in bits 0 to 11, `length` in bits 12 to 23, `suc_eof` in bit 30 and `owner` in bit 31, then the buffer's address, then the next descriptor's. When its peripheral starts, the OUT channel reads the list through the descriptor with `suc_eof`, updates `GDMA_OUT_EOF_DES_ADDR_CHn_REG` and `GDMA_OUT_DSCR_CHn_REG`, parks (`GDMA_OUTLINK_PARK` reads 1), and latches `OUT_DONE`, `OUT_EOF` and `OUT_TOTAL_EOF` into `GDMA_OUT_INT_RAW_CHn_REG` when the transfer completes. On the board GDMA reads the list as an SPI2 or SPI3 transfer runs, so a store into a byte of an SPI2 or SPI3 transfer's descriptors or buffers before the transfer ends ends the run with `chip.unsupported_setting`. `GDMA_OUT_CHECK_OWNER` and `GDMA_IN_CHECK_OWNER` refuse a descriptor whose `owner` is clear. A write of `GDMA_INLINK_START` at an SRAM descriptor starts the IN channel for peripheral 6 (AES), 0 (SPI2) or 1 (SPI3). SPI2 and SPI3 refuse RX transfers. When a DMA-AES transfer finishes, the IN channel writes output bytes into the SRAM descriptor buffers, writes each consumed descriptor's header back in SRAM with `owner` cleared, `length` filled and `suc_eof` set on the last descriptor, records `GDMA_IN_SUC_EOF_DES_ADDR_CHn_REG`, parks (`GDMA_INLINK_PARK` reads 1), and latches `IN_DONE` and `IN_SUC_EOF` into `GDMA_IN_INT_RAW_CHn_REG`. IDF's shared crypto DMA starts the AES IN link at address 0 beside each SHA hash, and an IN link at a non-SRAM address parks without error. Sources 66 to 70 (IN channels 0 to 4) and 71 to 75 (OUT channels 0 to 4) are high while `INT_RAW & INT_ENA` is nonzero, and `INT_CLR` clears the raw bits. `IN_ERR_EOF` is accepted in `GDMA_IN_INT_ENA_CHn_REG` (IDF enables it alongside `IN_SUC_EOF`) and never rises. A descriptor or buffer outside data-bus SRAM, a looping list, a start for an unmodeled peripheral, a `peri_sel` change while started, an unsupported interrupt bit, or a write of `GDMA_MEM_TRANS_EN`, `GDMA_OUT_AUTO_WRBACK`, `GDMA_INLINK_RESTART` or `GDMA_OUTLINK_RESTART` ends the run with `chip.unsupported_setting`.
- **The SHA accelerator.** All eight ESP32-S3 modes run in `SHA_MODE_REG`: SHA-1 (0), SHA-224 (1), SHA-256 (2), SHA-384 (3), SHA-512 (4), SHA-512/224 (5), SHA-512/256 (6) and SHA-512/t (7, whose initial value is computed from `SHA_T_STRING_REG` and `SHA_T_LENGTH_REG` on `SHA_START_REG`). `SHA_START_REG` hashes the 64-byte or 128-byte block in `SHA_M_MEM` from the mode's initial value (or computes the SHA-512/t initial value), and `SHA_CONTINUE_REG` continues from `SHA_H_MEM`. `SHA_DMA_START_REG` and `SHA_DMA_CONTINUE_REG` hash `SHA_BLOCK_NUM_REG` blocks from the GDMA OUT channel started on peripheral 7. The TRM gives no cycle-count table for SHA; each hash finishes at the write that starts it (`SHA_BUSY_REG` reads 0) and latches the SHA completion interrupt (`ETS_SHA_INTR_SOURCE`, source 78) when `SHA_INT_ENA_REG` bit 0 is set, cleared by `SHA_CLEAR_IRQ_REG`. `SHA_H_MEM` and `SHA_M_MEM` hold their words in memory order (64-bit words for SHA-384/512 are big-endian word pairs as IDF reads them). An unsupported mode, an invalid `T_LENGTH` (zero or > 63), a DMA hash whose channel or list GDMA refuses, or an unsupported bit in `SHA_INT_ENA_REG` ends the run with `chip.unsupported_setting`.
- **The AES accelerator.** `0x6003_a000` runs AES-128 and AES-256 (`AES_MODE_REG` 0, 2, 4, 6) in Typical AES mode (`AES_DMA_ENABLE_REG` 0, transforming `AES_TEXT_IN_0..3` into `AES_TEXT_OUT_0..3`) and DMA-AES mode (`AES_DMA_ENABLE_REG` 1, running `AES_BLOCK_NUM_REG` 16-byte blocks in ECB, CBC, OFB, CTR with `INC32`/`INC128` via `AES_INC_SEL_REG`, CFB8 or CFB128 over GDMA OUT and IN channels on peripheral 6). Typical AES takes 15 APB cycles for AES-128 and 19 APB cycles for AES-256 (the upper bound of TRM §19.3.1's 11 to 15 and 15 to 19 cycle ranges). The TRM gives no cycle table for DMA-AES; the model estimates 15 APB cycles per cipher call for AES-128 and 19 for AES-256 (one call per 16-byte block for ECB/CBC/OFB/CTR/CFB128, 16 calls per block for CFB8). `AES_STATE_REG` reads `BUSY` (1) while running, `IDLE` (0) after Typical AES, and `DONE` (2) after DMA-AES until any write to `AES_DMA_EXIT_REG` returns it to `IDLE`. Completing a DMA-AES transfer updates `AES_IV_MEM`, commits the GDMA IN buffers and descriptor writebacks, latches the GDMA IN/OUT interrupts, and latches `ETS_AES_INTR_SOURCE` (source 77) when `AES_INT_ENA_REG` bit 0 is set, cleared by `AES_INT_CLEAR_REG`. Reserved modes (including AES-192, which the S3 lacks), non-zero `AES_ENDIAN_REG`, `AES_CONTINUE_REG` (GCM hardware mode, absent on S3; mbedTLS AES-GCM uses hardware ECB and CTR), zero `AES_BLOCK_NUM_REG`, reserved `AES_BLOCK_MODE_REG`, invalid GDMA lists, or an unsupported interrupt enable end the run with `chip.unsupported_setting`.
- **The RSA accelerator.** `0x6003_c000` runs modular exponentiation (`RSA_MODEXP_START_REG`), modular multiplication (`RSA_MOD_MULT_START_REG`) and plain multiplication (`RSA_MULT_START_REG`) over 32-bit little-endian word arrays in `RSA_M_MEM`, `RSA_Z_MEM`, `RSA_Y_MEM` and `RSA_X_MEM` up to 4096 bits (128 words; 2048-bit factors for `MULT`, where `Y` lives in `RSA_Z_MEM[n..2n]` and `RSA_LENGTH_REG` is `2n - 1`). `SYSTEM_RSA_PD_CTRL_REG` (`SYSTEM+0x40`, reset to `MEM_PD = 1`) controls RSA memory power. Powering up or releasing reset while clocked zeroes the memories and starts an estimated 104 APB cycle initialization (~1.3 us at 80 MHz, matching IDF's `mpi_hal.c`), after which `RSA_QUERY_CLEAN_REG` reads 1. The TRM gives no exact cycle table for RSA operations; the model estimates `n^2 + 2n` APB cycles per Montgomery MAC stage (`MULT`: 1 stage, `MOD_MULT`: 2 stages, `MODEXP`: `3 + bits + mults` stages honoring `RSA_CONSTANT_TIME_REG`, `RSA_SEARCH_OPEN_REG` and `RSA_SEARCH_POS_REG`). `RSA_QUERY_IDLE_REG` (`0x818`, aliased as `RSA_QUERY_INTERRUPT_REG` in IDF) reads 0 while an operation runs and 1 when idle; `RSA_CLEAR_INTERRUPT_REG` (`0x81c`) clears only the interrupt latch (`ETS_RSA_INTR_SOURCE`, source 76, enabled by `RSA_INTERRUPT_REG` bit 0) and leaves `0x818` reading 1. Starting an operation while powered down (`power_down`) or before `QUERY_CLEAN` (`not_clean`), an invalid `LENGTH`, powering down RSA memory while running (`power_down_while_running`), or an unsupported interrupt enable end the run with `chip.unsupported_setting`.
- **LEDC, with fixed duties, timer reset, pause and runtime reconfiguration, and hardware duty fade.** The eight channels' and four timers' registers, the interrupt registers and `LEDC_CONF_REG` keep what is written, from their reset values, and the self-clearing update bits read 0. A timer counts from the store that leaves its `LEDC_LSTIMERn_RST` and `LEDC_LSTIMERn_PAUSE` bits clear. Setting `LEDC_LSTIMERn_PAUSE` freezes the timer counter and holds its channels' output levels; clearing it resumes from the saved phase. Setting `LEDC_LSTIMERn_RST` resets the timer counter to 0 and holds it at 0 regardless of `PAUSE` (TRM v1.8, 35.3.2.3 and Register 35.7): no overflows occur while `RST` is set, so pending updates wait and active fades pause, and each enabled channel on that timer with nonzero duty sees `Timerx_cnt == Hpoint` (0) and drives high (TRM 35.3.3). Clearing `RST` with `PAUSE` clear starts counting from 0 at that store, restarting PWM cycles and remaining fade overflow counts on the timer's current period; clearing `RST` with `PAUSE` set leaves the counter suspended at 0. Its period is `LEDC_CLK_DIV_LSTIMERn` over 256, times 2 to the power `LEDC_LSTIMERn_DUTY_RES`, cycles of the clock `LEDC_APB_CLK_SEL` picks: 1, the APB clock, which ESP-IDF's `LEDC_AUTO_CLK` picks, or 3, the 40 MHz crystal. While a timer counts or is paused, writing `LEDC_CLK_DIV_LSTIMERn` or `LEDC_LSTIMERn_DUTY_RES` stages the new fields without changing the active period; setting `LEDC_LSTIMERn_PARA_UP` latches them to take effect at the timer's next overflow (TRM v1.8, 35.3.2.2, 35.3.2.3 and Register 35.7), or on a reset before that overflow, updating every active channel and re-anchoring active fades on that timer. A store that sets `LEDC_PARA_UP_LSCHn` takes channel n's duty and settings as they are then. That update takes effect at the next overflow of the timer the channel names, the next PWM cycle, as ESP-IDF's `ledc_update_duty` says, and a later update before that overflow replaces it. An update on a timer that does not count waits until it does. The duty is `LEDC_DUTY_LSCHn`, bits 18 to 0, whose low 4 bits are a fraction. With `LEDC_DUTY_START_LSCHn` clear the update keeps the duty the last one took and stops any active fade. That bit does not clear itself, so the update `ledc_stop` sends after `ledc_update_duty` takes the duty register again. With `LEDC_DUTY_START_LSCHn` set and both `LEDC_DUTY_NUM_LSCHn` and `LEDC_DUTY_CYCLE_LSCHn` nonzero, after the initial duty takes effect at the first overflow, the channel steps its duty by `LEDC_DUTY_SCALE_LSCHn` (up with `LEDC_DUTY_INC_LSCHn` set, down with it clear) every `LEDC_DUTY_CYCLE_LSCHn` overflows for `LEDC_DUTY_NUM_LSCHn` steps (TRM v1.8, 35.3.4), and sets `LEDC_DUTY_CHNG_END_LSCHn_INT_RAW` after the final step. Each timer overflow sets `LEDC_LSTIMERn_OVF_INT_RAW`. `LEDC_INT_ST_REG` reads the raw bits under `LEDC_INT_ENA_REG`, `LEDC_INT_CLR_REG` clears them, and source 35 is high while `LEDC_INT_ST_REG` is nonzero. While `LEDC_SIG_OUT_EN_LSCHn` is clear the channel sends its idle level `LEDC_IDLE_LV_LSCHn` as a duty of 0 or of every step. An update, fade step with a nonzero scale, or timer period or resolution change that takes effect sends a `Duty` record on each pin with a net whose pad carries the channel through the matrix, with the duty, the resolution and the frequency, the 480 MHz tick rate over the period, rounded. On a pad whose `OUT_INV_SEL` is set the record holds the duty the pad drives, the steps the channel does not send. A store that puts a pad with a net on a channel that has a duty, or that changes that pad's `OUT_INV_SEL`, sends the pad a record at the store, and a store that takes a pad off a channel sends nothing. Channel n's signal, matrix output 73 + n, is low at power-on. From each overflow of its timer it is the PWM of the ESP32-S3 TRM (v1.8, 35.3.3): high where the counter is `LEDC_HPOINT_LSCHn`, which is 0, and low where it reaches the duty. So it is high for the duty's steps of each period and low for the rest, a duty of 0 is low throughout and a duty at or above `2^DUTY_RES` (and below `2^14`) is high throughout. A step that is not whole ticks of 480 MHz rounds the high time to the nearest tick. An inverted pad drives the inverse. When an update moves a pad's drive, the move is a stop of its own 1 ps after the record's end, and an update that keeps the drive moves nothing. Every later edge that moves a pad's drive is a stop of its own too. A channel's PWM runs whether or not a pad carries it, so the core stops at each of its edges. `LEDC_LSCHn_DUTY_R_REG` reads the duty in force, from the last update or fade step that took effect, as `LEDC_DUTY_LSCHn` holds it with its fraction bits clear, and 0 before the first (TRM Register 35.6). ESP-IDF's `ledc_get_duty` reads it, and arduino-esp32's `ledcAttach` keeps the duty it reads. A store to it keeps nothing. `LEDC_LSTIMERn_VALUE_REG` is not kept. These end the run with `chip.unsupported_setting`: a write that enables an LEDC interrupt outside the timer overflow and duty-change-end bits (`LEDC_OVF_CNT_LSCHn_INT_ENA` or reserved bits); an update with a nonzero `LEDC_HPOINT_LSCHn` or a duty with a fraction; a counting timer on another clock, on `LEDC_TICK_SEL_LSTIMERn`, at a divider below 256, at a resolution of 0 or above 14, or with a period that is not whole ticks; a duty or fade target at or above `2^14` or below 0, or of `2^14` at 14 bits, which ESP-IDF's `ledc_channel_config` says the hardware does not reach; a change of `LEDC_APB_CLK_SEL`, a cleared LEDC clock gate, or a change of the APB clock under a timer that counts it, while a timer counts; and a store that sets LEDC's reset bit while a pad with a net carries a channel, while an update or fade has yet to finish, or while an update takes effect at that store, since that pad's last record or that update would outlast the reset. A store that leaves the bit set is not refused. A reset with no such pad or update puts LEDC and its signals back to power-on.
- **The USB Serial/JTAG console.** The firmware writes bytes to `USB_SERIAL_JTAG_EP1_REG` and commits a packet by writing `WR_DONE` to `USB_SERIAL_JTAG_EP1_CONF_REG` or by writing the FIFO's 64th byte. While attached, the host reads each committed packet in 30,000 ticks (62.5 us at 480 MHz), a rate of 16 packets per 1 ms Full-Speed frame (1,024 B/ms, within USB 2.0 §5.8.4 Table 5-9's 19-transfer ceiling for 64-byte bulk packets and matching §5.11.3 worst-case bit-stuffing of 59.23 us plus host delay). `SERIAL_IN_EP_DATA_FREE` reads 0 from commit until the host finishes reading the packet (TRM `USB_SERIAL_JTAG_EP1_CONF_REG`), and a `WR_DONE` written while a packet is already pending (as after a 64th byte) is a no-op. The host sends the bytes of the part's `console` events, as [netlist.md](netlist.md#esp32-s3) says. Each byte is readable from the first tick at or after its time while attached, in the order sent. `SERIAL_OUT_EP_DATA_AVAIL` reads 1 while one is, and a load of `USB_SERIAL_JTAG_EP1_REG` takes it. That load reads 0 while none is. The bytes reach `serial.csv` as usart `USB_SERIAL_JTAG`. Every byte of one packet starts and ends at the tick the host finished reading the packet. `USB_SERIAL_JTAG_CONF0_REG` resets to `0x4200` (`DP_PULLUP` and `USB_PAD_ENABLE` set). The host sees the device attached while `USB_PAD_ENABLE` is set and the Full-Speed D+ pull-up is on (`PAD_PULL_OVERRIDE` clear, or `PAD_PULL_OVERRIDE` and `DP_PULLUP` both set). While `USB_PAD_ENABLE` is set, the USB PHY claims GPIO19 and GPIO20, so the GPIO matrix does not drive them, and GPIO20 pulls up to `VCC` through the PHY's 2.4 kohm D+ pull-up (`PULLUP_VALUE = 0`, IDF `usb_wrap_struct.h` and `usb_serial_jtag_ll.h`) while the D+ pull-up is on; clearing `USB_PAD_ENABLE` frees both pads and releases the D+ pull-up for GPIO, and detaches the USB host. While detached, SOF, `IN_TOKEN_REC_IN_EP1` and host OUT bytes do not arrive, and a committed packet stays pending in the FIFO (`SERIAL_IN_EP_DATA_FREE` reads 0) until re-attach starts the 62.5 us host read. A write to `USB_SERIAL_JTAG_CONF0_REG` that sets `PHY_SEL`, `EXCHG_PINS_OVERRIDE` or `EXCHG_PINS`, `VREF_OVERRIDE`, `VREFH` or `VREFL`, `DP_PULLDOWN`, `DM_PULLUP` or `DM_PULLDOWN`, `PULLUP_VALUE`, `PHY_TX_EDGE_SEL`, or `USB_JTAG_BRIDGE_EN` ends the run with `chip.unsupported_setting`, `USB_SERIAL_JTAG`, as `phy_sel`, `exchg_pins`, `vref`, `pad_pull`, `pullup_value`, `phy_tx_edge` or `jtag_bridge`, and writes nothing. `USB_SERIAL_JTAG_INT_RAW_REG` reads the latched bits, and SOF, bit 1, when a 1 ms frame of 480,000 ticks has started since that bit was last cleared while attached. Only that read divides. `USB_SERIAL_JTAG_INT_ST_REG` reads the latched bits under `USB_SERIAL_JTAG_INT_ENA_REG`. `SERIAL_IN_EMPTY`, bit 3, is set from reset and when the host finishes reading each committed packet, an empty `WR_DONE` included. `IN_TOKEN_REC_IN_EP1`, bit 8, latches when the host finishes reading each committed packet and when a 1 ms frame of 480,000 ticks has started since that bit was last cleared while attached. `SERIAL_OUT_RECV_PKT`, bit 2, sets when a queued byte's time is at or before now while attached. A clear of that bit drops it, and a byte still queued does not set it again. A byte that arrives after the clear does. `USB_BUS_RESET`, bit 9, never rises. `USB_SERIAL_JTAG_INT_CLR_REG` reads 0 and clears the latched bits named in the word. A clear of `SERIAL_OUT_RECV_PKT` moves the mark a later byte is compared with, a clear of SOF moves the SOF frame mark, and a clear of `IN_TOKEN_REC_IN_EP1` moves the IN-token frame mark. A clear of another bit moves none of them. `USB_SERIAL_JTAG_INT_ENA_REG` keeps `SERIAL_OUT_RECV_PKT`, `SERIAL_IN_EMPTY`, `IN_TOKEN_REC_IN_EP1` and `USB_BUS_RESET`. A write that sets any other bit, SOF included, ends the run with `chip.unsupported_setting`, `USB_SERIAL_JTAG` `interrupt`, as the interrupt matrix entry says. Source 96 is high while a latched bit and its enable are both set. While `INT_ENA` is 0 the poll returns low and latches nothing. A read or a write of the unit, and the load of EP1 that takes a byte, latches due `SERIAL_OUT_RECV_PKT`, `IN_TOKEN_REC_IN_EP1` and completed TX packets. Enabling a bit then raises the level. A clear of another bit leaves the latch. A core in `WAITI` wakes at a due byte while `SERIAL_OUT_RECV_PKT` is enabled, when the host finishes reading a committed packet while `SERIAL_IN_EMPTY` or `IN_TOKEN_REC_IN_EP1` is enabled, and at the next 1 ms USB frame while `IN_TOKEN_REC_IN_EP1` is enabled and attached. An access to `USB_WRAP` ends the run, as [Unmodeled registers](#unmodeled-registers) says for every block the model does not simulate.

- **UART0, UART1 and UART2.** The ports sit at `0x6000_0000`, `0x6001_0000` and `0x6002_e000`. Each shifts bytes out of its TX FIFO onto its TXD signal, 12, 15 or 18, and samples its RXD input, the same signal number, into its RX FIFO. The baud clock is the APB clock when `sclk_sel` is 1 and the 40 MHz crystal when it is 3, divided by `sclk_div_num` + 1. A bit lasts `clkdiv` of those clocks, plus one more on the bits where a fractional accumulator that starts at 0 for that frame crosses 16. The TRM states the average bit length and not which bits are the long ones, so the accumulator is this model's rule. It also omits the APB-to-baud synchronizer, so a start bit is not delayed past the write that starts it. With `tx_idle_num` 0 and the shifter idle, the start bit begins on the FIFO write's tick. The next queued byte's start bit begins when the previous stop bit ends, and that edge is driven onto TXD at that tick. After the FIFO empties, the next write waits `tx_idle_num` bit times of idle mark. Data bits are `bit_num` + 5. Parity follows `parity` and `parity_en`, even when `parity` is clear. Stop bits are 1, 1.5 or 2 as `stop_bit_num` is 1, 2 or 3. The extra half of a 1.5-stop frame is the exact average `(clkdiv + frag/16) / 2` on the same fractional accumulator, not half of one stepped bit. `txd_inv` inverts the wire the pad drives, and `rxd_inv` inverts the level the port samples. With `UART_LOOPBACK` set the port samples its own wire and ignores the pad. Otherwise it samples the RXD signal. With `SIG_IN_SEL` set that is the pad `IN_SEL` names. With `SIG_IN_SEL` clear, UART0 reads GPIO44 in function 0 and UART1 reads GPIO18 in function 2, each while `FUN_IE` is set, and UART2 reads the idle mark. A pad with no net and `FUN_IE` set reads what it drives, so a pad routed to TXD and back to RXD returns each byte. GPIO43 in function 0 and GPIO17 in function 2 drive TXD with the peripheral enabling them, so a net on that pad records the bits. Each finished byte, sent or received, reaches `serial.csv` as usart `UART0`, `UART1` or `UART2`. `t_ps` is the start bit, and the row is ordered by the stop bit. `UART_STATUS_REG` reads the FIFO counts, not the byte in the shifter, `RXD` as the level last sampled and `TXD` as the wire. `UART_MEM_TX_STATUS_REG` and `UART_MEM_RX_STATUS_REG` read the write and read offsets. `UART_FSM_STATUS_REG` bit 0 reads a receive in progress and bit 4 a transmit. The RX FIFO-full raw bit is set while the count is above `rxfifo_full_thrhd`. The TX FIFO-empty raw bit is set while the count is below `txfifo_empty_thrhd`. With `rx_tout_en` set, `RXFIFO_TOUT` sets `rx_tout_thrhd` bit times after a stop bit when the FIFO still holds a byte and no frame is in progress. `TX_DONE` sets when a frame ends with the TX FIFO empty. A parity error, a framing error, an overflow and a break latch as that frame ends. While `err_wr_mask` is set a bad byte stays out of the RX FIFO, and the byte on the wire is still logged. Source 27, 28 or 29 is high while a raw bit and its enable are both set, apart from wakeup, bit 19, which is kept and never raised. A core in `WAITI` skips to the port's next edge, sample or timeout. The FIFO the model runs is 128 bytes: `rx_size` and `tx_size` of 1. Any other size ends the run as `fifo_size` before the store. The RX FIFO bases are `0x200`, `0x280` and `0x300`. A write past a full TX FIFO is dropped. A load of the FIFO pops one RX byte. `UART_REG_UPDATE` reads 0 at once. Clearing `high_speed`, bit 30 of `UART_ID_REG`, ends the run as `high_speed` before the store: a clear needs `UART_REG_UPDATE` to sync the divider and the frame format, and the model does not run that barrier. The bit resets set. At reset, `UART_SWFC_CONF0_REG` reads `xoff_threshold` 224 and `xoff_char` 19, `UART_SWFC_CONF1_REG` reads `xon_threshold` 0 and `xon_char` 17, and the AT-command registers read `pre_idle_num` 2305, `post_idle_num` 2305, `rx_gap_tout` 11, `at_cmd_char` 43 and `char_num` 3. Turning `sclk_en` or that direction's baud-clock enable off drops a frame that has not finished, and that byte is not logged. The module clock and the peripheral reset are the SYSTEM bits, as the gates entry says. With the module clock off or the reset held, a load or a store still completes and nothing shifts. A peripheral reset returns the port to power-on and keeps bytes already logged, apart from the FIFO pointers. Neither that reset nor a core reset, `rst_core`, `tx_rst_core` or `rx_rst_core`, moves them. Each empties its FIFO and leaves `UART_MEM_TX_STATUS_REG` and `UART_MEM_RX_STATUS_REG` where they were. Only `txfifo_rst` and `rxfifo_rst` in CONF0 zero them, the TX pointers to 0 and the RX pointers to the port's base. A board capture on 2026-11-18 showed this for UART0's TX pointers; it did not read RX, which takes the same resets and the same status register, so the model treats it the same. After the reset sequence of TRM §26.5.2.1, which is `uart_ll_reset_register`'s, UART0's TX pointers read 109 and 111, and the port sent the RAM's old bytes, not the ones written. A second such reset left them where traffic had moved them. The pulse IDF's `uart_param_config` gives, `rxfifo_rst` and then `txfifo_rst` (`uart.c:1052-1053`, TRM §26.4.2), set both to 0, and every byte then came back as written. The TRM gives both fields a reset value of 0 and does not say what a reset keeps. So after a reset that follows traffic, since power-on or that FIFO's last reset bit, the model cannot source the pointers or what the RAM holds at them. Until the matching FIFO reset bit, a TX FIFO write or an RX FIFO load ends the run as `fifo_pointers`. A reset with no traffic since power-on or that FIFO's last reset bit leaves its pointers where that bit or power-on put them, TX at 0 and RX at the port's base, and the port runs. `SYSTEM_UART_MEM_RST` is not run. A flash boot is narrower. The capture names no UART register, and the board showed UART0's TX pointers two apart after the app's start-up, so the pointers the app starts with are not sourced either. The model starts them where power-on puts them, TX at 0 and RX at the port's base, and does not refuse the app's early log, so those `UART0` rows are the bytes the app wrote, and the board's pad may carry others. When the app's console is not on UART0 (`CONFIG_ESP_CONSOLE_UART_NUM` other than 0, as in this tree's IDF apps, whose console is USB Serial/JTAG), its `esp_perip_clk_init` then holds UART0 in reset after that log, so a later UART0 TX write needs the FIFO reset that IDF's UART driver gives. An app whose console is UART0, such as one built on the Arduino core 3.3.12's libraries, is not held, and its UART0 writes after the early log are accepted. The model runs neither the boot ROM's PRO CPU path nor the bootloader after any reset it makes, so their UART0 log never follows one. The capture of a flash boot names no UART register, and its `UartDev.baut_rate` at `0x3fcef134` is 115200. ROM `Uart_Init` programs UART0 from that baud on the 40 MHz crystal before the app runs, so the port starts at `clkdiv` 347, fractional part 3 and `sclk_div_num` 0. UART1 and UART2 stay at the silicon divider, `clkdiv` 694 and `sclk_div_num` 1. A flash app's early log can write UART0 before its console moves to USB Serial/JTAG, and those bytes are `UART0` rows beside the console's. UHCI is not modelled, so an access of it stays `chip.unmodeled_register`. These end the run with `chip.unsupported_setting`, peripheral `UART0`, `UART1` or `UART2`: hardware flow control, as `hw_flow`; software flow control, as `sw_flow` (except `UART_SW_FLOW_CON_EN` with `UART_FORCE_XOFF` alone, which ESP-IDF's `uart_ll_force_xoff` sets while suspending a UART for light sleep; a TX FIFO write while `UART_FORCE_XOFF` stays set still ends the run as `sw_flow`); `sw_rts` or `sw_dtr` set, as `sw_rts` or `sw_dtr` (`UART_STATUS_REG` keeps `RTSN` and `DTRN` at 1); RS485; IrDA, which is CONF0 bits 9 to 13 and bit 16 (`UART_LOOPBACK`, bit 14, is run); autobaud; a break; `mem_force_pd`, as `power_down`; the glitch filter, as `glitch`; a stop-bit field of 0, as `stop_bits`; a divider of 0 when a frame would start, as `divider`; `sclk_sel` other than 1 or 3, as `clock`; a nonzero `sclk_div_a` or `sclk_div_b`, as `sclk_frac`; a FIFO write while the baud clock is off and the module still runs, as `clock_off`; a FIFO read, a FIFO write, or a frame that would start while the module is running and CONF0 `mem_clk_en` or `SYSTEM_UART_MEM_CLK_EN` is clear, as `mem_clock` (writing either clock bit is kept; IDF's boot and the UART driver leave both set); a FIFO reset or a core reset while a frame is shifting, as `reset_while_sending`; a TX FIFO write or an RX FIFO load after a reset that followed traffic and before that FIFO's reset bit, as `fifo_pointers`, as above; a change, while a frame is shifting, of the divider, the frame format, the idle count, `txd_inv`, `rxd_inv`, loopback, the TX FIFO-empty threshold, `rx_tout_en` or the baud-clock divider or source, as `baud_while_sending`; a change of the APB rate while an APB-clocked port is shifting, as `clock_change_while_sending`; and an interrupt enable outside the bits named above, as `interrupt`.

- **The eFuses.** The read registers hold the set the part's `efuse` names from power-on, as [netlist.md](netlist.md#esp32-s3) says. `packages/socs/espressif/src/s3/efuse.txt` holds the sets. Each line names one field of IDF's `esp_efuse_table.csv` and the raw unsigned value to write. `PSRAM_CAP` is the two bits at 131 and `PSRAM_CAP_3` is the bit at 179, the two lines `espefuse summary` prints. `PSRAM_CAPACITY` is calculated from them, and `WAFER_VERSION_MINOR` from `WAFER_VERSION_MINOR_LO` and `WAFER_VERSION_MINOR_HI`. Neither is a field, so a section that names one is `netlist.syntax`, as is any other name that is not in the csv. An ADC field is the unsigned token summary prints in parentheses: raw `0x81` is 129, which IDF adds, and not the sign-and-magnitude `-4` that `adc_info` prints. A field a set does not name is 0, and so is all of block 0. The default, `synthetic`, is a revision 0.2 chip with 8 MB of PSRAM in its package and no flash in it, block version 1.3, the MAC `02:00:00:00:00:01`, and every other bit 0, the calibration and the unique ID among them. A read command finishes at once. A store of `EFUSE_PGM_CMD` to `EFUSE_CMD_REG` would burn eFuses, so it ends the run with `chip.efuse_program` and writes nothing. The other registers keep what is written.
- **SPI1 and the flash.** A write of `SPI_MEM_CMD_REG` starts its one command and clears its bits. A write that starts more than one, such as `WREN` with a sector erase, runs none and ends the run with `chip.flash_command`, reason `start_bits`. A user command sends its command byte, the address when `SPI_MEM_USR_ADDR` is set, and the MOSI bytes from `SPI_MEM_W0_REG` on when `SPI_MEM_USR_MOSI` is set, and leaves the MISO bytes from `SPI_MEM_W0_REG` on when `SPI_MEM_USR_MISO` is set. Dummy cycles count toward `0xab`'s 3-byte dummy phase and have no effect on other commands. The flash is the 16 MB Boya BY25Q128ES, JEDEC ID `68 40 18`, Device ID `17`, with its quad enable bit set, backed by copy-on-write 4 KB pages so chip clones for rewind stay cheap. The fixed commands `RDSR`, `WREN`, `WRDI`, `RDID`, `RES`, `PP`, `SE`, `BE` and `CE` and the user commands for reads (`0x03`, `0x0b`, `0x3b`, `0x6b`, `0xbb`, `0xeb`), `RDID` (`0x9f`), release from power-down / device ID (`0xab`, BY25Q128ES Rev. 2.8 §7.3.7 and Table 8, returning `0x17` continuously after 3 dummy bytes or releasing with no dummy or MISO bytes), status reads (`0x05`, `0x35`, `0x15`), `WREN` (`0x06`), `WRDI` (`0x04`), page program (`0x02`, `0x32`), 4 KB sector erase (`0x20`), 32 KB block erase (`0x52`), 64 KB block erase (`0xd8`) and chip erase (`0x60`, `0xc7`) run, including ESP-IDF's 16-bit `ADDR` plus 1-byte MOSI erase encoding. Program and erase require `WEL` set from `WREN`; with `WEL` clear, a valid command is a no-op and leaves `WIP` clear. With `WEL` set, page program clears bits (`1` to `0`) and wraps inside its 256-byte page, erase sets its 4 KB sector, 32 KB block, 64 KB block or whole chip to `0xFF`, and any change moves the chip's code version so cached instruction decodes reload. `WIP` stays set in status register 1 for the BY25Q128ES Rev. 2.8 §8.7 (`-40 to 85 C`, `2.7 to 3.6 V`) typical duration in simulated time (0.55 ms for page program, 40 ms for 4 KB sector erase, 0.12 s for 32 KB block erase, 0.25 s for 64 KB block erase, 60 s for chip erase), and clears together with `WEL` when it finishes. While `WIP` is set, only status reads (`RDSR`, `0x05`, `0x35`, `0x15`) are allowed; any other SPI1 command or any cache fetch or load through the MMU ends the run with `chip.flash_command`, reason `busy`. A status write, the fixed `WRSR` or a user `0x01`, `0x31` or `0x11`, can set the status registers' protect and one-time lock bits, so it ends the run with reason `status_write` before any status bit changes, with or without `WREN`. An access past the flash's end (`past_end`), an address phase longer than 32 bits (`address_bits`), an invalid phase or byte count (`length`), an octal, DDR or unsupported write width (`mode`), or an unimplemented command such as deep power-down (`0xb9`), software reset (`0x66`, `0x99`) or suspend/resume (`0x75`, `0x7a`) (`unsupported`) ends the run with `chip.flash_command`. A chip with no flash refuses every read, program and erase with `past_end`, `RDID` reads `ff ff ff`, and `0xab` / `RES` reads `ff` there. A user command while `SPI_MEM_MISC_REG` has `CS0_DIS` set or `CS1_DIS` clear ends the run with reason `cs`. The register resets to `0x2`, so CS0 is on and CS1 is off, and the fixed commands do not look at those bits. Enabling `SPI_MEM_INT_ENA_REG`, auto-wait-idle (`SPI_MEM_WAITI_EN`), auto-suspend (`SPI_MEM_FLASH_PES_EN`), or manual suspend/resume (`SPI_MEM_FLASH_SUS_CMD_REG`) ends the run with `chip.unsupported_setting`, peripheral `SPI1`. The controller's other registers keep what is written.
- **The MMU and the cache.** The MMU's 512 entries, at `0x600c_5000`, each map one 64 KB page of the 32 MB space that the instruction bus sees at `0x4200_0000` and the data bus at `0x3c00_0000`. An entry holds a flash page number, bit 14 marks it invalid, and an entry with bit 15, PSRAM, maps nothing. The cache is functional: every access reads the flash through the MMU at once, and a store into either window raises `LoadStoreError`. A load from either window that the MMU maps to no flash, through an invalid entry, a PSRAM entry or a page past the flash's end, ends the run with `chip.unmapped_load`, and a fetch there with `chip.unmapped_fetch`. A chip with no flash maps no page. The cache controller's lock, unlock, sync, occupy and preload operations finish at the write that starts them, autoload reads done, and a freeze reads done while it is on. Its other registers keep what is written.
- **I2C0 and I2C1 as masters.** Two instances of one model: port 0 at `0x6001_3000` (signals 89 and 90, interrupt source 42) and port 1 at `0x6002_7000` (signals 91 and 92, interrupt source 43), each running a command list on SCL and SDA open drain. Its clock is the 40 MHz crystal over `I2C_SCLK_DIV_NUM` + 1 while `I2C_SCLK_ACTIVE` is set. `I2C_CONF_UPGATE` copies the timing registers into the timing a transfer runs with. SCL low, the SDA hold, the SDA sample and the start and stop setups and holds count their register plus one. `I2C_SCL_WAIT_HIGH_PERIOD` and `I2C_SCL_HIGH_PERIOD` count as stored, so a bit is `low + wait_high + high` cycles. `I2C_TRANS_START` starts the list one cycle of that clock after the store. No source gives that delay, so it is inferred. A bit drives SDA at the hold after SCL falls and releases SCL at the end of the low. The master reads SCL through the input matrix. A pad with no net reads its own output at once. A netted pad reads high at the first input that brings it high, and a target that holds SCL stretches the bit from that input. The sample is the sample length after that input, and SCL falls at the later of the release plus the wait and that input, plus the high period. A wait for SCL high that reaches `2^I2C_TIME_OUT_VALUE` cycles of that clock while `I2C_TIME_OUT_EN` is set raises `I2C_TIME_OUT_INT_RAW`, releases SDA, clears `I2C_BUS_BUSY` and ends the transfer with no `I2C_TRANS_COMPLETE_INT_RAW` (TRM v1.8, 27.4.8, 27.6 and Register 27.12, which states `I2C_SCLK` cycles). With `I2C_TIME_OUT_EN` clear, the wait does not time out. An event that moves a netted pad waits for its `Moved` halt before the next event, so each event reads the inputs of the edges before it. A write's ninth bit with the ACK check set and no ACK raises `I2C_NACK_INT_RAW`, makes the stop and clears `I2C_BUS_BUSY` without `I2C_TRANS_COMPLETE_INT_RAW`. While that NACK stop runs, command-register writes update the registers without disturbing the stop; while that NACK stop or a standalone `STOP` command started right after a NACK runs, and `COMD0` holds `STOP`, a `CONF_UPGATE` with unchanged `CTR` and timing registers is a no-op and `TRANS_START` is ignored. Reading `I2C_DATA_REG` from an empty RX FIFO returns 0 and sets `I2C_RXFIFO_UDF_INT_RAW`. A read command sends its `ack_val` bit as the ACK of every byte it reads, as IDF's `I2C_MASTER_NACK`, "nack for each byte read", says. A list's stop raises `I2C_TRANS_COMPLETE_INT_RAW`, source 42 on I2C0 or 43 on I2C1. An END command, as the ESP32-S3 TRM v1.8 describes it in 27.4.9 and 27.5.4, marks itself done, raises `I2C_END_DETECT_INT_RAW` and stops the list with SCL held low and `I2C_BUS_BUSY` set. IDF's driver splits a write or a read longer than the 32-byte FIFO this way, as Arduino's `Wire`, `Wire1` and Adafruit SSD1306's `display()` do. The next `I2C_TRANS_START` resumes the list from `I2C_COMD0`, one cycle after its store, with any command, and that command clocks from that cycle: SDA moves at the hold and SCL releases at the end of the low. The TRM says only that an END extends SCL low, so that timing is inferred. A list on an idle bus still starts with a repeated START or a STOP. `I2C_RX_FULL_ACK_LEVEL` is the ACK the master sends once the RX FIFO is full, as the TRM's Register 27.11 and 27.4.3 say. The model takes that as the ACK of the byte that fills the 32-byte FIFO, and a read command whose own ACK there differs ends the run with `rx_full_ack_level`. IDF clears the bit, and a read it splits never ends with a NACK on a full FIFO. A STOP in the first command makes the stop from the levels the pins already read. When both already read high it waits the setup and the hold and raises the transfer-complete interrupt with no edge. `I2C_CLK_EN` in `I2C_CTR_REG` gates only the register interface's APB clock, as Register 27.11 says, so it is kept and changes nothing. `SLV_TX_AUTO_START_EN`, `ADDR_10BIT_RW_CHECK_EN` and `ADDR_BROADCASTING_EN` set a slave, which the model does not run, so every write that changes one is listed with `chip.unmodeled_register`. A start while `I2C_SCLK_ACTIVE` is clear ends the run with `clock_off`. A start whose SDA hold is at least the SCL low, or whose SDA sample is at least `I2C_SCL_HIGH_PERIOD`, ends it with `timing`. `FILTER_CFG` is kept. The master does not delay a pulse it would filter, and a pulse shorter than the threshold while a transfer runs ends the run with `glitch`. These also end the run with `chip.unsupported_setting`: slave mode, a pad that is not open drain or not routed to the signal in both directions, LSB first, arbitration, sampling SCL's own level, the RC fast clock, a fractional divider, the non-FIFO mode, an FSM reset, a bus clear, power down, an interrupt enable outside the master's end, arbitration-lost, transfer-complete, timeout and NACK bits, an opcode the master does not run, a byte count of 0 on a read or a write, a TX FIFO that underflows or overflows, an RX FIFO that overflows, and a timing or command write while a transfer runs outside the stop cases above.
- **RMT, transmit only, channel 0.** TX channel 0 sends from its 48-word block of `RMTMEM` at `0x6001_6800`, with `MEM_TX_WRAP_EN` set. Each register starts at its reset value. - **PCNT.** Four units of two channels each at `0x6001_7000` (TRM v1.8, Chapter 36). Unit n reads its pulse and control signals through the GPIO matrix: signals `33 + 4n` (channel 0 pulse), `34 + 4n` (channel 1 pulse), `35 + 4n` (channel 0 control) and `36 + 4n` (channel 1 control). Each channel counts rising and falling edges on its pulse input as increment, decrement or hold (`CHm_POS_MODE`, `CHm_NEG_MODE`), modified by its control input's current filtered level (keep, invert or inhibit via `CHm_HCTRL_MODE` and `CHm_LCTRL_MODE`). With `FILTER_EN` set, each unit runs an APB-clocked glitch filter of `FILTER_THRES` (0 to 1023) APB cycles on all four inputs; a pulse shorter than the threshold is ignored, and valid transitions commit after the filter delay. Reaching `CNT_H_LIM` (> 0) or `CNT_L_LIM` (< 0) resets the signed 16-bit counter to 0. Enabled watchpoints (`THR_THRES1_EN`, `THR_THRES0_EN`, `THR_L_LIM_EN`, `THR_H_LIM_EN` and `THR_ZERO_EN`) latch into `PCNT_Un_STATUS_REG` and set bit n of `PCNT_INT_RAW_REG`; source 41 is high while `PCNT_INT_RAW_REG & PCNT_INT_ENA_REG` is nonzero, and `PCNT_INT_CLR_REG` clears both the raw bit and the unit's latched status bits. `PCNT_CTRL_REG` pauses and resets each unit (`PULSE_CNT_PAUSE_Un`, `PULSE_CNT_RST_Un`) and keeps `PCNT_CLK_EN`. PCNT runs behind SYSTEM's PCNT clock and reset bits (bit 10 of `CLK_EN0` and `RST_EN0`). These end the run with `chip.unsupported_setting`, peripheral `PCNT`: a load or store while the PCNT clock is off (`clock_off`) or held in reset (`held_in_reset`), a negative `CNT_H_LIM` (`h_lim`), a positive `CNT_L_LIM` (`l_lim`), reserved bits in `PCNT_CTRL_REG` (`ctrl`), reserved bits in `PCNT_INT_ENA_REG` (`interrupt`), or turning off PCNT's clock (`clock_off_while_running`) or changing the APB rate (`clock_change_while_running`) while a glitch-filter timer is pending.

- **The internal temperature sensor.** `SENS_SAR_TSENS_CTRL_REG` (`SENS+0x50`) and `SENS_SAR_TSENS_CTRL2_REG` (`SENS+0x54`) read the die temperature for `temperatureRead()` and ESP-IDF's `temperature_sensor` driver (TRM v1.8, 39.4). Die temperature is derived directly from the scene's ambient temperature (`world.temperature`, defaulting to 25 degC when the scene omits it), clamped to the TRM and IDF range of -40 to 125 degC; chip self-heating and conversion latency are not simulated. A rising `SENS_TSENS_DUMP_OUT` halts the core at that store so the host delivers the current ambient temperature, computes the 8-bit `SENS_TSENS_OUT` code by inverting TRM Equation 39.2 (`T = 0.4386 * out - 27.88 * offset - 20.52`) using the active `I2C_SARADC_TSENS_DAC` range in analog I2C block `0x69` register `0x6` (`5` -> offset -2, `7` -> -1, `15` -> 0, `11` -> 1, `10` -> 2) and the chip's eFuse `TEMP_CALIB` offset (9-bit sign-magnitude in 0.1 degC when `BLK_VERSION_MAJOR` is 1, 0 otherwise), rounds and clamps `out` to 0..=255, and sets `SENS_TSENS_READY`. Clearing `SENS_TSENS_DUMP_OUT` clears `SENS_TSENS_READY` while keeping `SENS_TSENS_OUT`, as IDF reads `OUT` after clearing `DUMP_OUT`. `SENS_TSENS_CLK_EN` and `SENS_TSENS_RESET` (bit 29 of `SENS_SAR_PERI_CLK_GATE_CONF_REG` and `SENS_SAR_PERI_RESET_CONF_REG`) and `RTC_CNTL_DIG_CLK8M_EN` (bit 10 of `RTC_CNTL_CLK_CONF_REG`) gate and reset the sensor. These end the run with `chip.unsupported_setting`, peripheral `SENS`: setting `SENS_TSENS_IN_INV` (`tsens_in_inv`), clearing `SENS_TSENS_CLK_INV` (`tsens_clk_inv`), setting `RTC_CNTL_TSENS_INT_ENA` (`interrupt`), or starting a dump with `SENS_TSENS_CLK_EN` or `RTC_CNTL_DIG_CLK8M_EN` clear (`tsens_clock_off`), `SENS_TSENS_RESET` set (`tsens_held_in_reset`), sensor power force off (`tsens_power`), `SENS_TSENS_CLK_DIV` 0 (`tsens_clk_div`), or an undocumented `I2C_SARADC_TSENS_DAC` code (`tsens_range`).
- **The RTC clock calibration.** A timer group's calibration finishes the moment `TIMG_RTC_CALI_START` rises, with the count of 40 MHz cycles its slow clock would give at its nominal rate: the 136 kHz RC slow clock, the 17.5 MHz RC fast clock over 256, or the 32.768 kHz crystal. A cycling calibration always reads ready, and none times out.
- **The rest of the boot path.** The permission controls of `SENSITIVE` start at 0 and keep what is written, and no access is checked against them. On a chip booted from flash, every register the captured state names and no model owns keeps what is written, from its captured value.
- **The peripheral clock gates and resets.** `SYSTEM_PERIP_CLK_EN0_REG`, `SYSTEM_PERIP_CLK_EN1_REG`, `SYSTEM_PERIP_RST_EN0_REG` and `SYSTEM_PERIP_RST_EN1_REG` start at their reset values on a bare-metal chip, and at the captured ones on a chip booted from flash. SPI2, SPI3, LEDC, GDMA, the SHA, AES and RSA accelerators, I2C0, I2C1, RMT, PCNT, UART0, UART1 and UART2 run their bits. Each runs while its clock bit is set and its reset bits are clear. A write that leaves one of its reset bits set puts it back to its reset values, and it stays there until they clear. The SHA accelerator is held by the digital signature and HMAC reset bits too, as IDF's `sha_ll_reset_register` says, and the AES and RSA accelerators are held by the digital signature reset bit too. A load or a store to SPI2, SPI3, LEDC, GDMA, the SHA, AES or RSA accelerators, I2C0, I2C1, RMT or PCNT, or to `RMTMEM`, while its clock is off, or while a reset holds it, ends the run with `chip.unsupported_setting`. So does a write that sets SPI2's or SPI3's reset or clears its clock while a transfer runs, or does that to GDMA while an SPI2, SPI3 or DMA-AES transfer uses it, or does that to AES or RSA while an operation runs, or sets I2C0's or I2C1's reset or clears its clock while a transfer runs, and a transfer started from GDMA while its clock is off. Both of those I2C writes end as `I2C0` or `I2C1` `reset_while_sending`. SPI2's and SPI3's cleared clock stays `clock_off_while_sending`. A write that sets RMT's reset or clears its clock while TX channel 0 sends ends the run, with `RMT` `reset_while_sending` or `clock_off_while_sending`. RMT's reset puts its registers and `RMTMEM` back to power-on and signal 81 low. A load or a store to a UART while its module clock is off, or while its reset holds it, still completes. The shifter stops, its TXD signal returns to mark, and a byte that had not finished is not logged. A byte that had finished stays logged. A peripheral reset returns that port to power-on, apart from its FIFO pointers, as the UART entry says. `SYSTEM_UART_MEM_CLK_EN`, bit 24 of `SYSTEM_PERIP_CLK_EN0_REG`, is the clock for every UART's RAM. It resets set, and a write that clears it is kept. A later FIFO access or frame, while the module is running and this bit is clear, ends the run as `mem_clock`, as the UART entry says. IDF's restart and panic paths set `SYSTEM_DMA_RST`, GDMA's reset, in `esp_system_reset_modules_on_exit`, so an `esp_restart()` or a panic while SPI2 or SPI3 sends from GDMA ends the run with `GDMA` `reset_while_sending`, in place of `chip.restart` or `chip.halted`. The console holds a panic's text, which IDF prints before that store. The model cannot tell where the board cut the transfer short, so the run does not go on. The reset bit of SYSTIMER puts that timer back to its power-on registers, count and alarms included, and it stays there while the bit is set. The reset bit of TIMG0 or TIMG1 does that for the group's two general timers, its watchdog and `TIMG_INT_ENA_TIMERS_REG`. `SYSTEM_WDG_RST` does it for the RTC watchdog. From the captured state, IDF's `esp_perip_clk_init` sets that bit, since `SYSTEM_WDG_CLK_EN` is clear there, and leaves it set, so the RTC watchdog stays at reset while the timer-group watchdogs keep running. The clock bits of SYSTIMER, TIMG0, TIMG1 and `SYSTEM_WDG` stay reported. The clock and reset bits of SPI0 and SPI1, the eFuse controller and the USB Serial/JTAG unit, and the bits IDF names `SYSTEM_TIMERS_*`, are kept and not run. IDF's headers leave `SYSTEM_TIMERS_*` undescribed and no driver gates a block with them, so a change is reported in case it gates a timer the model runs. Every write that changes one of those is listed with `chip.unmodeled_register`, as [Unmodeled registers](#unmodeled-registers) says. Every other bit gates or resets a peripheral the model does not keep, so it has no effect.
- **Writes the model keeps and does not run.** `RTC_CNTL_CLK_CONF_REG` picks the slow clock (apart from `RTC_CNTL_DIG_CLK8M_EN`, bit 10, which gates the temperature sensor, and `RTC_CNTL_DIG_CLK8M_D256_EN` and `RTC_CNTL_ENB_CK8M_DIV`, bits 9 and 7, which IDF's `periph_rtc_dig_clk8m_enable` toggles while calibrating `RC_FAST`), and SPI0's `SPI_MEM_USER_REG` to `SPI_MEM_USER2_REG` set the command the cache reads the flash with. A write keeps its word, and the RTC watchdog keeps its 136 kHz slow clock, and the cache reads the flash as before. Every write that changes one of those unrun bits is listed with `chip.unmodeled_register`, as [Unmodeled registers](#unmodeled-registers) says. A write of SPI0's `SPI_MEM_CMD_REG` that starts a command ends the run with `chip.flash_command`, and `RTC_CNTL_SLEEP_EN` in `RTC_CNTL_STATE0_REG` ends it with `chip.unsupported_setting`. Setting a pad hold bit in `RTC_CNTL_PAD_HOLD_REG`, `RTC_CNTL_DIG_PAD_HOLD_REG`, `RTC_CNTL_PWC_REG` (`RTC_CNTL_PAD_FORCE_HOLD`) or `RTC_CNTL_DIG_ISO_REG` (`RTC_CNTL_DG_PAD_FORCE_HOLD` or `RTC_CNTL_DG_PAD_AUTOHOLD_EN`) ends the run with `chip.unsupported_setting`, `RTC_CNTL` `pin_hold`, and writes nothing; writes that leave those bits clear stay quiet. SENS's `SENS_SAR_PERI_CLK_GATE_CONF_REG` and `SENS_SAR_PERI_RESET_CONF_REG` gate and reset the RTC peripherals, and the model runs their `SARADC` bit 30 and `TSENS` bit 29. A write that changes another bit is listed. So is a write that changes `SENS_I2C_SLAVE_ADDR0` or `SENS_I2C_SLAVE_ADDR1`, bits 0 to 21 of `SENS_SAR_SLAVE_ADDR1_REG`, slave addresses no conversion uses. That register's `SARADC_MEAS_STATUS` reads 0, an idle SAR, which `adc_oneshot_ll_start` polls for before an ADC1 start.
- **A reset.** A store of `RTC_CNTL_SW_PROCPU_RST` or `RTC_CNTL_SW_SYS_RST` to `RTC_CNTL_OPTIONS0_REG` resets the chip. Before IDF resets after a panic or a watchdog, it records why in `RTC_CNTL_STORE6_REG` as `hint | hint << 16 | 1 << 31`, and `esp_restart` leaves that register 0. A reset with the register 0, or holding the hint `ESP_RST_SW`, is one from `esp_restart`. The model does not run the boot ROM, so the chip stays in reset from that cycle. The core runs no further, each pad drives as at power-on, and the run reports `chip.restart`, a warning, and goes on to `stop_ps`. Any other reset ends the run with `chip.fault_restart`: a hint of a panic, a watchdog or a brownout, another value, or no register at all, as on a bare-metal chip, which keeps none. `RTC_CNTL_SW_APPCPU_RST` resets the APP CPU, as [The two cores](#the-two-cores) says, and reads 0.
- **Supply loss and power-on restart.** A hysteresis supply watch monitors `V(VCC) - V(GND)`: it falls low at or below 2.44 V (ESP-IDF v5.5.5 `CONFIG_ESP_BROWNOUT_DET_LVL_SEL_7`, the default brown-out detector threshold; ESP32-S3 Series Datasheet v2.2 Section 2.5.3 lists brown-out reset as a chip reset source without a numeric table or hysteresis figure) and rises high at 3.0 V (ESP32-S3 Series Datasheet v2.2 Section 5.2, Table 5-2 minimum recommended operating `VDD`). Once `V(VCC) - V(GND)` falls to or below 2.44 V, the chip stops executing instructions, stops all peripheral activity, drops unfinished serial frames and records, and releases every wired GPIO pad to `Drive::Off` with no pull-up or pull-down (leaving only pad leakage). A chip that starts unpowered at t = 0 and powers on once starts running when `V(VCC) - V(GND)` first reaches 3.0 V. Power-on restart is not simulated yet: when `V(VCC) - V(GND)` rises back to 3.0 V after a power loss, the run stops with `chip.power_on_restart`.

The core's own timer interrupts, `CCOMPARE0` to `CCOMPARE2`, and `WAITI` work as `orbe-xtensa` models them. A core in `WAITI` skips to its next timer match, the next SYSTIMER alarm, the next general-timer alarm, the end of a watchdog's stage, I2C0 or I2C1's next event, RMT's next threshold or end, a UART's next edge, sample or timeout, or the run's limit. A pad edge that raises the GPIO interrupt, and I2C0 or I2C1's transfer-complete interrupt, each wake it at the first cycle after the event.
A `j` to its own address while every interrupt `INTENABLE` enables is at or below the current interrupt level is a loop only an NMI or a watchdog leaves. When the interrupt matrix maps no source to that core's CPU interrupt 14, the NMI, and no watchdog runs, the run ends with `chip.halted` there. While the other core may run, the core waits at the loop instead, and the other core's next store outside SRAM and RTC memory that leaves a source mapped to its NMI lets it run on from the start of that store's instruction. The run ends with `chip.halted` once no core may run and no watchdog runs. ESP-IDF's panic handler ends in such a loop when the app is built to print and halt, after it disables the watchdogs, so such a panic does not run on to `stop_ps` with status `ok`. The panic text the handler printed last can still be in the console's FIFO, because the handler writes no `WR_DONE`, and those bytes are not in `serial.csv`.

The core runs the base ops `orbe-xtensa` models, the single-precision FPU, MAC16, the Boolean registers and `s32c1i`, and holds the `q` registers and the `cop_ai` user registers as plain state. `PRID` reads `0xcdcd` on the PRO CPU and `0xabab` on the APP CPU. `witlb` and `wdtlb` keep each 512 MB region's attribute for `ritlb1` and `rdtlb1` to read back, and no access is checked against it. `rer` reads 0 and `wer` writes nothing. An FPU op with `CPENABLE` bit 0 clear raises cause 32, and a `cop_ai` op with bit 3 clear raises cause 35, at the exception vector. `DBREAKA0`, `DBREAKA1`, `DBREAKC0` and `DBREAKC1` read back what was written. `DBREAKCn` bits 0 to 5 are the address mask, a set bit compared and a clear bit ignored, and bits 6 to 31 of the address are always compared. Bit 30 arms the watch for a load and bit 31 for a store. A load or a store that reaches a byte of that window ends the run with `chip.unsupported_setting`, `CPU` `watchpoint`, before the access. An `ee.*` vector op, or any other instruction the core does not model, ends the run with `chip.unsupported_instruction`.

## The SAR ADCs

ADC1 and ADC2 run one-shot conversions under SENS's two RTC controllers, the path IDF v5.5.5's `adc_oneshot_read` takes on the ESP32-S3, with Wi-Fi off. Channel n of ADC1 is GPIO n + 1, and channel n of ADC2 is GPIO n + 11, for n from 0 to 9, as IDF's `soc/esp32s3/include/soc/adc_channel.h` says. A conversion is always 12 bits: IDF's `adc_oneshot_ll_set_output_bits` writes nothing on the S3, because the chip supports no other width. The register names, places and reset values are IDF's `soc/esp32s3/register/soc/sens_reg.h` and `apb_saradc_reg.h`, and the analog I2C's are `soc/esp32s3/include/soc/regi2c_saradc.h`.

**What IDF writes.** `adc_oneshot_hal_setup`, in `hal/adc_oneshot_hal.c`, and `hal/esp32s3/include/hal/adc_ll.h` set the unit's `SARn_CLK_DIV` to 1, `SARn_DATA_INV` clear, the channel's two bits of `SENS_SAR_ATTENn_REG`, the channel as the one bit of `SARn_EN_PAD`, and the RTC controller: `SAR1_DIG_FORCE` clear, `MEASn_START_FORCE` and `SARn_EN_PAD_FORCE` set. For ADC2 they also set `SAR2_PWDET_CCT` to 4. For either unit they put ADC2's arbiter, `APB_SARADC_APB_ADC_ARB_CTRL_REG`, in its default, `ADC_ARBITER_CONFIG_DEFAULT`: fixed priority with no forced grant. `adc_oneshot_read` then writes `DREF` 4 and the unit's initial code through the analog I2C, as `adc_hal_calibration_init` and `adc_set_hw_calibration_code` do. `adc_oneshot_ll_start` clears and sets `MEASn_START_SAR`, after it polls `SARADC_MEAS_STATUS` to 0 for ADC1. IDF polls `MEASn_DONE_SAR` and reads `MEASn_DATA_SAR`. `sar_periph_ctrl_adc_oneshot_power_acquire` sets `FORCE_XPD_SAR` to 3, and IDF's start-up sets `SARADC_CLK_EN` in `SENS_SAR_PERI_CLK_GATE_CONF_REG`. IDF names attenuation 3 `ADC_ATTEN_DB_12`, and Arduino's 11 dB is the same setting. The model keeps SENS's reader, `MEASn_CTRL1`, `MEASn_CTRL2`, `MEASn_MUX`, attenuation and amplifier words, `SENS_SAR_POWER_XPD_SAR_REG`, `SENS_SAR_SLAVE_ADDR1_REG`, the gate and reset words, and the arbiter's word, each from its reset value. The arbiter's word is kept while APB_SARADC's clock is gated, as IDF leaves it on the S3, where `ADC_LL_NEED_APB_PERIPH_CLAIM` is 0. Every other SENS and APB_SARADC register is unmodeled.

**A conversion.** A store that raises `MEASn_START_SAR` starts one. The run stops at that store and reads the pad's voltage there, `V(pin) - V(GND)`, as [Behind the seam](#behind-the-seam) says, and the conversion holds it. `MEASn_DONE_SAR` reads 0 and `MEASn_DATA_SAR` keeps the unit's last code, 0 before the first, until 25 cycles of the SAR clock after the store. Both then read the new code until the next start. The SAR clock is RTC_FAST_CLK over `SARn_CLK_DIV`. RTC_FAST_CLK is XTAL_D2, 20 MHz, while `RTC_CNTL_FAST_CLK_RTC_SEL` is clear, and the RC fast clock, 17.5 MHz, over `RTC_CNTL_CK8M_DIV_SEL` + 1 while it is set (TRM v1.8, 7.2.4.4 and Register 10.25, and IDF's `SOC_CLK_RC_FAST_FREQ_APPROX`). A chip booted from flash holds the captured `RTC_CNTL_RTC_CLK_CONF_REG`, `0x30c8_069c`, so a conversion at IDF's divider of 1 lasts 25 cycles of 17.5 MHz, 1.43 µs, 686 ticks rounded up. A bare-metal chip keeps no such word and runs at 20 MHz, 600 ticks. The TRM (39.3.7.1) gives 25 cycles a sample for the digital controller's SAR clock and no count for the RTC controllers, so the 25 is inferred. It bounds the digital controller's divider at 2 or more (39.3.2) and gives no bound for the RTC controllers', and the model runs IDF's 1.

**The code.** The chip's analog error is what IDF's curve-fitting calibration corrects, so the model gives the code that calibration maps back to the voltage. IDF reads the calibration from the eFuse set when `BLK_VERSION_MAJOR` is 1, `esp_efuse_rtc_calib_get_ver` in `components/efuse/esp32s3/esp_efuse_rtc_calib.c`. Its `esp_efuse_rtc_calib_get_cal_voltage` adds the `ADCn_CAL_VOL_ATTENk` fields to nominal values into `digi`, the code the unit read at 850 mV in the factory, and `esp_efuse_rtc_calib_get_init_code` adds the `ADCn_INIT_CODE_ATTENk` fields into the initial codes, both with unsigned 32-bit sums. The number in `efuse.txt` is that raw field. `espefuse summary` prints it in parentheses; the meaning column and `adc_info` are sign-and-magnitude, so raw `0x81` is 129 here and `-4` there. `components/esp_adc/adc_cali_curve_fitting.c` reads a raw code in two steps. The first is linear, `v = raw * coeff_a / 65536` with `coeff_a = 65536 * 850 / digi`. The second subtracts an error polynomial in `v`, three terms at 0, 2.5 and 6 dB and five at 12 dB, with the coefficients and signs of `components/esp_adc/esp32s3/curve_fitting_coefficients.c`. In real numbers those two steps are `G(raw)`, increasing on 0 to 4095. The model's code for a voltage `x` mV is `G⁻¹(x)`, rounded to the nearest code and clipped to 0 and 4095, so IDF's `adc_cali_raw_to_voltage` of the code reads `x` within its integer truncation.

The synthetic set's calibration fields are all 0, and its block version is 1.3, so IDF reads the calibration from eFuse and takes each 0 as no offset from its nominal value. `digi` is 3200, 2400, 1700 and 900 for ADC1 at 0, 2.5, 6 and 12 dB, and 3240, 2410, 1720 and 915 for ADC2. The initial codes are 1850, 1940, 1940 and 2010 for ADC1, and 2020 at each attenuation for ADC2. Its codes clip at these voltages:

| Unit | Attenuation | Reads 0 below | Reads 4095 above |
| --- | --- | --- | --- |
| ADC1 | 0 dB | 2.1 mV | 1083.5 mV |
| ADC1 | 2.5 dB | 2.2 mV | 1437.9 mV |
| ADC1 | 6 dB | 2.3 mV | 1992.1 mV |
| ADC1 | 12 dB | 0.5 mV | 3245.5 mV |
| ADC2 | 0 dB | 2.1 mV | 1071.8 mV |
| ADC2 | 2.5 dB | 2.2 mV | 1430.9 mV |
| ADC2 | 6 dB | 0.3 mV | 1958.0 mV |
| ADC2 | 12 dB | never, 0 V reads 1 | 3187.3 mV |

The datasheet's calibrated ranges are 0 to 850, 1100, 1600 and 2900 mV (ESP32-S3 Series Datasheet v2.2, Table 5-6), each inside its row. At 12 dB IDF's own arithmetic overflows near the top of the range: `adc_cali_raw_to_voltage` multiplies `v²` by its third coefficient in 64 bits, which wraps from raw 3992 on ADC1, about 3230 mV, and from raw 3803 on ADC2, about 3124 mV. There it reads near 5 V. That is IDF's behaviour on the board too, and the model's code is still `G⁻¹` of the voltage.

A board's set names its own fields, and the model then gives that board's calibration curve. With `BLK_VERSION_MAJOR` other than 1, IDF reads no calibration: its start-up self-calibrates each initial code against internal ground, and curve fitting returns `ESP_ERR_NOT_SUPPORTED`. The model runs neither, so such a conversion ends the run.

**What ends the run.** These end it with `chip.unsupported_setting`, `SENS`, and the store writes nothing, as [diagnostics.md](diagnostics.md#chipunsupported_setting) lists by name. At the store: an inverted output, a multi-sample count, a cleared `SARn_CLK_GATED` or an ADC2 arbiter wait other than 1 in a reader word; a change of the amplifier words or `SENS_SAR_MEAS2_CTRL1_REG`, the power detector's, from reset; `SAR1_DIG_FORCE`, the digital controller; `SAR2_RTC_FORCE`; `SARCLK_EN`; and a change of a converting unit's reader, `MEASn_CTRL2`, `MEASn_MUX` or attenuation word, a new start among them, or of `FORCE_XPD_SAR`, `SARADC_CLK_EN` or `SARADC_RESET` while either unit converts. At a start: the ULP's control of the start or the pads; no channel, more than one, or one above 9; a channel whose GPIO has no net; `FORCE_XPD_SAR` other than 3; the SAR clock gated, or held in reset; a divider of 0; ADC2 with the arbiter's grant forced to another controller than the RTC's; a set IDF reads no calibration from; an initial code in the analog I2C other than the set's for the channel's attenuation; `DREF` other than 4; ADC1's `SAMPLE_CYCLE` other than 0; `ENCAL_GND` set; and the analog test mux on. A store that sets `RTC_CNTL_SARADC1_INT_ENA` or `RTC_CNTL_SARADC2_INT_ENA` ends it as `SENS` `interrupt`. `SAR2_PWDET_CCT` is kept and runs nothing: it sets the power detector, which the model refuses. The digital controllers, continuous and DMA conversion, the ULP, the power detector and Wi-Fi's arbitration of ADC2, and the internal channels are not modelled.

## Booting from flash

The boot ROM and the bootloader do not run. The chip starts with their result.

1. The ROM's sections land by address. The ROM is 384 KB at `0x4000_0000` on the instruction bus, and its last 128 KB also show at `0x3ff0_0000` on the data bus. A section the boot ROM copies into SRAM, its `.data`, lands in SRAM. The ROM is `rom`'s ELF, the one Espressif publishes for revision 0.
2. The captured state applies. It is `packages/socs/espressif/src/s3/boot/state.txt`: the core registers, 612 peripheral registers and 7,234 words of RAM, as a board's bootloader left them at `call_start_cpu0` after a software restart. `WINDOWSTART` keeps only the current frame, because the frames below it are the bootloader's, whose registers outside the window the state lacks, and the app never returns to them. The MMU's entries come from the captured table. Each watchdog's protect word applies as captured, so a watchdog the capture left locked stays locked until the firmware writes the key.
3. The app's segments load. A segment in a cache window is mapped by the MMU from its flash offset, rounded down to a page as the bootloader maps it, over the captured entries. Every other segment is copied into SRAM or RTC memory.
4. The PC is at the image's entry.

So the app runs from its first instruction on the board's clocks, watchdogs and cache state. SYSTIMER's count starts at its latched value registers, which this capture holds at 0, so the app's log times are not the board's. The state's volatile values, such as `CCOUNT` and the RTC time, are one boot's. The bootloader's own console lines and the ROM's are not in the run, which starts at the app's entry.

The capture followed a CPU reset, not a power-on: `RTC_CNTL_RESET_STATE_REG` holds reset reason `0x0c`, `RESET_REASON_CPU0_SW`. A CPU reset leaves the peripherals as the app before it set them. So the state holds that app's interrupt map, such as SYSTIMER's alarm 0 on CPU interrupt 2 and timer group 1's watchdog on 24, its timer group interrupt enables and its peripheral clock gates, where a power-on would hold reset values. IDF also branches on the reason. After `0x0c`, `esp_perip_clk_init` leaves the unused peripheral clocks as they were, where after a power-on it gates them, `rtc_init` skips the calibration it runs only at power-on, and `esp_reset_reason()` returns `ESP_RST_SW`. `hello_world` prints none of this, so its console matches the board's. An app that reads its reset reason, or relies on a peripheral at its reset value, runs a path the board runs only after a CPU reset. A capture after a power-on would remove the difference, and needs the board.

## Unmodeled registers

Peripheral space runs from `0x6000_0000` to `0x600d_1000`. `packages/socs/espressif/src/s3/blocks.rs` holds one table of its blocks, with each block's base from IDF's `reg_base.h`, and says of each whether the model runs it. The model runs UART0 to UART2, SPI0 to SPI3, GPIO, IO_MUX, the eFuses, RTC_CNTL, RTCIO, SENS but its touch registers, the analog I2C master, I2C0 and I2C1, RMT, PCNT, LEDC, both timer groups, SYSTIMER, SYSCON, USB Serial/JTAG, AES, SHA, RSA, GDMA, APB_SARADC, SYSTEM, SENSITIVE, INTERRUPT, EXTMEM, the MMU table and WCL. Every other block is one the model does not simulate, such as MCPWM0 and MCPWM1, I2S0 and I2S1, TWAI, SDMMC, LCD_CAM, USB OTG, Bluetooth and the Wi-Fi and Bluetooth radio, which is `RADIO` from `0x6002_f000` to `0x6003_8000`, where IDF names no block. A gap between IDF's blocks is `RESERVED`.

A register a model keeps works in any block, such as `WDEV_RND_REG` in `RADIO`. Any other access to a block the model does not simulate ends the run with `chip.unsupported_setting`, setting `unsimulated`, naming the block and what it is in a maker's words, such as `used MCPWM0, the motor-control PWM that ESP32Servo drives servos with`. A register the model does not keep in a block it runs reads 0, and a write to it is dropped. The run reports each such register once, at its first access, with `chip.unmodeled_register`. `rtc_sleep_pu`'s four radio force-up words, `call_start_cpu1`'s two APP-CPU debug-trace words, and the RTC pad words `gpio_config` reads and clears to 0 on GPIO0 to GPIO21 are not listed and do not end the run: with Wi-Fi and Bluetooth off, and with the pad in digital mode (`MUX_SEL` clear), none of them moves a pin, a clock or a reading. `SYSTIMER_RST`, `TIMERGROUP_RST`, `TIMERGROUP1_RST` and `SYSTEM_WDG_RST` are not listed because the model runs them. Any non-zero store to one of those RTC pad words (such as `MUX_SEL`, `RUE`, `RDE`, `DRV`, `FUN_IE`, `SLP_*` or touch bits) is listed, and so is every other register no model keeps in a block the model runs. It reports the registers the model keeps without running their effect, which [What it models](#what-it-models) lists, at every write that changes one. The warning names the address, the register as its block and offset, such as `RTCIO+0x0`, whether that access was a write, the PC, and the ELF symbol at or below the PC, or `null` for an app booted from flash. A byte or halfword access to a kept register reads, or merges into, its word.

A load from a cache window that the MMU maps to no flash ends the run with `chip.unmapped_load`. Any other load outside the chip's memories and peripheral space, or a store outside SRAM, RTC memory and peripheral space, raises `LoadStoreError`. The core takes the exception at its vector. A fetch outside the instruction-bus SRAM window, RTC fast memory, the ROM and the instruction cache window ends the run with `chip.unmapped_fetch`. An instruction the core does not model ends it with `chip.unsupported_instruction`.

## The Wi-Fi radio

An `esp32s3` in a netlist with [`network`](netlist.md#network) is built with its radio. It then keeps the 291 radio registers, the 45 words of the hardware TXOP table (`0x6003_4344` to `0x6003_43f4`) and the 250 words of the key table, that a stock Arduino-ESP32 3.3.12 station sketch touches through `esp_wifi_init`, `esp_wifi_start`, a scan and a join, which `packages/socs/espressif/src/s3/wifi.rs` lists: in FE2, FE, the analog I2C master past `ANA_CONFIG2_REG`, BT, the range from `0x6001_c000` up to NRX that IDF names no block for, NRX, BB, and the MAC in RADIO. Each reads the word last written, and 0 before the first write, except the MAC's status and W1C words below. Four reads also carry a done bit that the driver polls for: bits 24 to 26 of `I2C_MST+0x50`, bit 24 of `I2C_MST+0x4c`, bit 16 of `FE+0x174`, and bit 0 of `RADIO+0x4d14` once bit 1 is set. Each of those values, and each 0 before a write, was chosen so the driver proceeds, and is not yet read from hardware. The PHY sets `SENS_IOMUX_CLK_EN` while it reads the temperature sensor. On this chip that write is not listed, since the model runs RTC IO as if that clock were on, and clearing the bit still is. So `WiFi.mode(WIFI_STA)` returns true with no diagnostic. Any other radio register is refused or listed as on a chip without the radio. In a netlist without `network` the chip is built without it.

The chip is a station on the air, as [engine.md](engine.md#the-air) says, and its MAC sends and receives frames, so `WiFi.scanNetworks()` puts a probe request on the air on each channel it scans and finds the network on its channel from the Probe Response, and `WiFi.begin()` authenticates, associates and runs the 4-way handshake with it. The register meanings come from the driver's and the ROM's code, not from IDF's headers or a chip, so each is a guess until a board checks it:

- **Channel.** The station is tuned to the channel whose centre the RF PLL last started on: bit 8 of `I2C_MST+0xc4` starts it on the frequency bits 0 to 7 give, in half megahertz above 2400 MHz, as `set_chan_freq_sw_start` writes them. Before the first start, or on a frequency that is no channel's centre, it is tuned to none and a frame it sends ends the run.
- **Send.** A store that sets bit 31 of transmit queue `q`'s PLCP0 word, `0x6003_3d08 - 8q`, starts the queue, as `hal_mac_txq_enable` does. Bits 0 to 19 are the SRAM address of its first `lldesc_t`. Bits 0 to 11 of its PLCP1 word, `0x6003_42f8 - 0x4c q`, are the PSDU's length with the FCS, and bits 12 to 16 its rate as a `wifi_phy_rate_t`. The descriptors' buffers hold the MPDU and 4 bytes for the FCS. The frame starts DIFS, 50 us, after the store, with no backoff and no carrier sense, and takes its airtime at that rate. Its end is a stop with `record` set, where the chip hands it to the air.
- **Hardware TXOP.** When bits 24 to 27 of queue `q`'s control word `0x6003_4314 - 0x4c q` are nonzero (`mac_tx_set_txop_q`), bits 28 and 29 name hardware TXOP queue `txop_q` (0 to 2; 3 ends the run as `txop_queue`, and bits 30 and 31 as `txop_ctrl`). Each extra frame `idx` from 1 to that count comes from `0x6003_437c + 60 * txop_q - 4 * (idx - 1)` (`hal_mac_fill_hwtxop`), with its descriptor's SRAM offset in bits 0 to 19 and its PSDU length with FCS in bits 20 to 31. Each extra frame starts SIFS (10 us) after the previous frame's ACK using PLCP1's rate and key entry. An ACK timeout stops the burst early.
- **Done.** A group-addressed frame is done at its end, and an individually addressed one SIFS and an ACK later, acknowledged or not. The MAC then sets the queue's bit in `0x6003_3cb0`, which a store of that bit to `0x6003_3cac` clears (W1C, reads 0), sets bits 12 to 15 of the queue's status word, `0x6003_4320 - 0x4c q`, to 0, or to 5 when no station acknowledged a frame that waits for it, sets bits 28 to 31 to the count of earlier TXOP frames completed (`lmacProcessTxopQComplete`), and sets bit 7 of the event word `0x6003_3c3c`, which a store to `0x6003_3c40` clears (W1C, reads 0). The MAC interrupt, source 0 (`ETS_WIFI_MAC_INTR_SOURCE`), is high while an event bit is set there and in `0x6003_3c34`. Stores to `0x6003_3c34` whose bits outside 7, 15 and 24 are neither 0 nor `hal_init`'s fixed mask (`0x18a8_7960`) end the run as `events_enable`.

- **Filter.** Two slots, 0 for the station and 1 for the access point, each have a receiver address at `0x6003_3040 + 8n` with its mask at `0x6003_3060 + 8n`, and a BSSID at `0x6003_3000 + 8n` with its mask at `0x6003_3020 + 8n`. Bit 16 of each mask's second word enables it, as `hal_mac_set_addr` and `hal_mac_set_bssid` write them. A slot takes a frame whose Address 1 matches its receiver address, or whose Address 1 and BSSID are each its BSSID or broadcast. The radio drops a frame no slot takes. Bits 27 to 31 of `0x6003_3004`, which no blob function sets, end the run as `bssid_bits`. The bits of `0x6003_30d8` are not run. esp32-open-mac names the same words on the ESP32 (`esp32-wifi.yaml`, and its write-up "RX filter" of 2024-09-26).
- **Receive.** A frame a slot takes on the tuned channel goes into the receive list at its end. A store of an `lldesc_t`'s address to `0x6003_3088` makes it the next descriptor. `0x6003_308c` reads bits 0 to 19 of the next one's address, 0 once the list has run out, and `0x6003_3090` those of the last one filled. A store that sets bit 0 of `0x6003_3084` re-reads the last one's next link when the list has run out, and the bit reads 0 at once. The MAC writes the 48-byte `rx_ctrl` header of IDF's `wifi_pkt_rx_ctrl_t`, then the MPDU, then its FCS, into the next descriptor's buffer when the owner bit 31 is set. The header carries the RSSI, the rate as a `wifi_phy_rate_t`, the signal mode, the matching slots in bits 28 and 29, the MCS of an HT frame, the MAC clock in microseconds when the first bit of the frame body (the Timestamp field of a Beacon or Probe Response, IEEE 802.11-2020 9.4.1.10 and 11.1.3.2) arrived, the noise floor and the length with the FCS, and `rx_state` 0. The MAC then sets the descriptor's length, sets bit 30, clears bit 31 and moves to the next link. One tick later it sets bit 24 of the event word. A frame with no free descriptor is lost and not acknowledged.
- **ACK.** The MAC acknowledges a frame to one station that a slot's receiver address took and that found a descriptor, so the network does not log it lost.
- **TSF.** There are four TSF timers and four TBTTs, `n` from 0 to 3. A store that sets bit `n` of `0x6003_500c` copies timer `n`'s count in microseconds into `0x6003_5018` and `0x6003_501c`, as `tsf_hal_get_counter_value` and `hal_get_tsf_time` read them. A store that sets bit `4 + n` loads timer `n` with the count in `0x6003_5010` and `0x6003_5014`, as `tsf_hal_set_counter_value`, `hal_set_sta_tsf` and `hal_mac_tsf_reset` do, and the timer counts on from there. A store that sets bit `8 + n` latches bits 0 to 25 of `0x6003_5020` as TBTT `n`'s start, as `tsf_hal_set_tbtt_start_time` and `hal_set_sta_tbtt` do after they write that word. The load and latch bits read 0 at once. Timers 1 to 3 count from the chip's start until a load. Timer 0 counts only while bit 31 of `0x6003_5028` is set (`hal_enable_sta_tsf`, `hal_disable_sta_tsf`, `hal_mac_tsf_reset`) and freezes when bit 31 is cleared. Bits 27 and 28 are always set or cleared together, and setting only one ends the run as `tbtt_control`. Bit 29 (`tsf_hal_set_tbtt_soc_wakeup_enable`, `hal_set_sta_tsf_wakeup`) is kept while SoC light sleep itself is refused at `RTC_CNTL_SLEEP_EN`. Bit 1 of `0x6003_502c` (`hal_is_sta_tsf_active`) is set when TBTT 0 fires and cleared by writing bit 0 (`hal_clear_sta_tsf_active_state`, W1C, reads 0); any store setting bits 2 to 31 or setting bit 1 when inactive ends the run as `tsf_active`.
- **MAC clock.** `0x6003_5000`, which `hal_now` and `esp_wifi_internal_get_mac_clock_time` read, counts microseconds from the chip's start, the same count as the `rx_ctrl` timestamp. IDF documents that function as a 32-bit microsecond time (`esp_private/wifi.h`). `ic_update_sta_tsf` loads timer 0 with the access point's TSF plus the time since the first bit of the Timestamp field arrived.
- **Key table.** 25 entries of 10 words from `0x6003_4400`, 40 bytes apart, and their valid bits in `0x6003_3814`, read as last written, as `hal_crypto_set_key_entry` and `hal_crypto_clr_key_entry` write them. Word 0 and bits 0 to 15 of word 1 hold the peer's address. Word 1 holds the cipher in bits 18 to 20 (3 for CCMP), a pairwise key in bit 21, a group key in bit 23, the interface in bits 24 and 25 and the key ID in bits 30 and 31. Words 2 to 9 hold the key. The station's driver puts its pairwise key in entry 4 and its group key with key ID 1 in entry 0 (`esp_wifi_get_sta_hw_key_idx_internal`), and the supplicant installs every pairwise key with key ID 0 (`wpa_supplicant_install_ptk`). esp32-open-mac's `esp32` PAC names bits 21 and 23 the same way. `hal_crypto_set_key_entry` also sets bit 22 always, bit 27 unless the key ID is 3, bit 16 only for WEP-104 and bit 26 only for GCMP-256, and bits 21 to 23 to 3 in entries 4 to 24 and to 6 in entries 0 to 3, or to 7 for WEP. The model reads neither bit 22 nor bit 27. A store of any other word 1, including one that sets bit 17, 28 or 29, ends the run as `key_entry`, and a store that sets bits 25 to 31 of `0x6003_3814` as `key_valid`. A frame that uses a CCMP-128 entry whose words 6 to 9 are not 0 ends it as `tx_key_words` or `rx_key_words`.
- **CCMP.** The MAC seals a frame it sends with the Protected Frame bit set under the entry that bits 17 to 24 of the queue's PLCP1 word name, as `mac_tx_set_plcp1` writes them. An entry beyond 24 is not in use. `mac_tx_set_plcp1` also sets bit 25 with an HT rate and bit 29 from two flags of the driver's frame, which the model keeps and does not read. A store to PLCP1 that sets bits 26 to 28, 30 or 31, or bit 25 with a rate below 16, ends the run as `tx_plcp1`, and a frame with a rate of 16 or more without bit 25 as `tx_rate`. The driver fills the CCMP header with its own PN (`ccmp_encap`) and leaves 8 bytes for the MIC before the FCS (`ppProcTxSecFrame`). The MAC writes the ciphertext and the MIC over them. When that entry is not in use, the MAC sends nothing and is done 50 us after the store, with outcome 4 and 192 in bits 0 to 7 of the status word, which the driver hands to `lmacProcessTxseckiderr`. The MAC opens a protected frame it receives in place. An individually addressed frame takes the pairwise entry of the slot's interface whose address is the frame's Address 2. One whose CCMP key ID is not that entry's ends the run as `rx_key_id`, as whether the MAC compares them is not known. A group-addressed frame takes the interface's group entry with the CCMP header's key ID. The MAC header, the CCMP header and the MIC stay, for the driver's `ccmp_decap` to check the PN and strip them. A frame no entry takes lands as it came with `rx_state` 240, and one whose MIC fails with 241. The driver drops both. Both values are guesses: the driver counts 225 to 230 and 240 to 252 as security errors (`wDev_RxSecError`), and reads 245 as a TKIP MIC failure. The MAC runs CCMP only while bits 0, 1 and 8 of the interface's word at `0x6003_3800 + 4n` are set, as `hal_crypto_enable` sets them. Its bit 9, which `hal_crypto_enable` sets when `ieee80211_get_spp` says both sides protect the A-MSDU Present bit, keeps that bit in the AAD, a guess. `hal_crypto_init` and `hal_crypto_disable` write `0x30000`, and `hal_crypto_enable` adds bit 28 for WEP and bit 31 for SMS4, which the model does not read. A store of a word no `hal_crypto_*` function writes there, such as one without bits 16 and 17, a nonzero word for interface 2 or 3, or a bit of `0x6003_3810` outside 6 to 21, ends the run as `crypto_control`, and a store to `0x6003_3840` of anything but 0 or 25 as `crypto_init`. esp32-open-mac's write-up "Reverse engineering WPA crypto acceleration on ESP32" (2025-03-07) describes the same flow on the ESP32. A cipher other than CCMP-128 ends the run by name, `tx_wep`, `tx_tkip`, `tx_sms4` or `tx_gcmp`, or `rx_` and the same, and so does a protected Management frame (`tx_mfp`, `rx_mfp`), a QoS frame with an HT Control field, and a protected frame for an interface whose CCMP is off.
- **Retries.** The driver numbers each frame itself, and on an ACK timeout sends the same buffer again with the Retry bit it set, so the MAC sends what the buffer holds.
- **Power interrupt.** The power interrupt is source 2 (`ETS_WIFI_PWR_INTR_SOURCE`). Its enable word `0x6003_5110` has bit `4 - n` for TBTT `n` (`tsf_hal_set_tbtt_intr_enable`) and bit `8 - n` for timer `n`'s alarm (`tsf_hal_set_timer_intr_enable`). Raw status is `0x6003_5114` (`pwr_hal_get_intr_raw_signal`), masked status (`raw & enable`) is `0x6003_5118` (`hal_pwr_interrupt_get_event`, `wDev_ProcessFiq`), and `0x6003_511c` is write-1-to-clear (`hal_pwr_interrupt_clr_event`, `hal_enable_sta_tbtt`) and reads 0. The line is high while a bit is set in `0x6003_5118`. While bit 26 and bit 31 of `0x6003_5028` are set, TBTT 0 sets bit 4 of raw status and bit 1 of `0x6003_502c` at the first count of timer 0 that is at least the ahead time after the store that armed it, last changed its settings, or the microsecond after the TBTT it last raised, and equal to its latched start modulo the beacon interval, less the ahead time. So it raises the bit once each beacon interval. A store that latches the start, writes `0x6003_5030` or loads timer 0 changes the settings. The interval is bits 0 to 15 of `0x6003_5030` in TU and the ahead time its bits 16 to 31 in microseconds, as `hal_set_sta_tbtt` writes them. A TBTT already due at the store that arms it raises the bit at that store's tick. The interrupt the bit raises is taken at the same tick however the run is split. `wdev_process_tbtt` then runs the driver's TBTT work, `pm_on_tbtt`. A store that sets the interrupt bit of TBTT 1 to 3 ends the run as `tbtt_intr`, one of a timer's alarm as `tsf_timer`, and any store to `0x6003_5114` or `0x6003_5118` as `pwr_raw` or `pwr_events`.
- **Beacon filter.** `pm_set_beacon_filter` writes the station's AID into bits 16 to 26 of slot 0's BSSID word, `0x6003_3004`, and turns the filter on by setting bits 0 to 2 of `0x6003_30a0` and bit 15 of `0x6003_3c34`. While it is on, a Beacon slot 0's BSSID takes whose TIM does not set the AID's bit in its Partial Virtual Bitmap lands nowhere. One tick later the MAC sets bit 15 of the event word instead, which `wdev_process_beacon_filter` hands to `pm_on_beacon_rx` with no frame. A Beacon whose TIM sets the bit lands as any frame does, so the driver sees the access point holds frames for it. A Beacon with no TIM ends the run as `beacon_filter_tim`, and one whose TIM says group frames are held as `beacon_filter_group`, since whether the filter passes it is not known. A store that sets only some of bits 0 to 2 ends it as `beacon_filter`, and one that sets bits 3 to 31 as `beacon_filter_bits`.
- **RF power.** For modem sleep, `esp_phy_disable` runs `rom_phy_xpd_rf` (`&= 0x27ff_ffff`, writing `0x2040_0000`), clearing `RTC_CNTL_PLL_I2C_PU` (bit 31), `RTC_CNTL_CKGEN_I2C_PU` (bit 30), `RTC_CNTL_RFRX_PBUS_PU` (bit 28) and `RTC_CNTL_TXRF_I2C_PU` (bit 27) of `RTC_CNTL_ANA_CONF_REG` while leaving bit 29 and `RTC_CNTL_SAR_I2C_PU` (bit 22) set, and the wake's `rom_open_i2c_xpd` sets bits 27 to 31 again (`0xf840_0000`). The station receives only while bits 31, 30, 29 and 28 are all set, keeping its channel through power-down. A frame the MAC would send while any of bits 31, 30, 29 or 27 is clear ends the run as `tx_rf_off`, clearing any of bits 27 to 31 while a frame is not done ends it as `rf_off_tx`, clearing bit 22 ends it as `sar_i2c_off`, and setting any other bit ends it as `ana_conf`.
- **Not run.** A store that turns a coexistence timer on, bit 31 of `0x6003_50a8 + 8n`, ends the run as `coex_timer`, one that forces it, bit 28 (`coex_hw_timer_force`), as `coex_force`, and one that sets bit 29, which no blob function sets, as `coex_timer_bits`. The bits `coex_hw_timer_set` writes, 0 to 27 and 30, are kept. A store that sets a bit no blob function sets ends the run by name: bits 12 to 31 of `0x6003_500c` as `tsf_control`, bits 26 to 31 of `0x6003_5020` as `tbtt_start`, bits 16 to 24 and 26 to 31 of `0x6003_5024` as `tbtt_wake_ahead`, bits 0 to 25 and 30 (or only one of 27 and 28) of `0x6003_5028` as `tbtt_control`, bits 18 to 31 of `0x6003_5058` as `tsf_rtc_tick`, and bit 0 and bits 9 to 31 of `0x6003_5110` as `pwr_intr`.
- **Coexistence words.** `0x6003_5080` (bits 0 to 15, `hal_set_rx_beacon_time`), `0x6003_5084` (bit 1, `hal_coex_pti_init`; bit 0 is external coexistence, refused as `extern_coex`), `0x6003_5088` (bit 0 W1C, reads 0, `hal_clear_rx_beacon_pti`), `0x6003_508c` (bits 0 to 7, `hal_set_rx_beacon_time`), `0x6003_5090` (bits 0 to 3, `hal_set_rx_beacon_pti`), `0x6003_5094` (bits 8 to 15, `hal_set_wifi_default_pti` and `hal_set_rx_beacon_pti`), and `0x6003_509c` (bits 16 to 31, `set_chan_freq_hw_init` and `hal_coex_set_wait_time`) refuse any other bits by name (`coex_beacon_time`, `coex_pti`, `coex_beacon_pti`, `coex_wait_time`). The timer word `0x6003_50c0` reads as last written.
- **Debug words.** `0x6003_3094`, `0x6003_3098`, `0x6003_3318` and `0x6003_3320` read 0. `wdev_record_rx_linked_list` only copies them into the driver's debug record.

The MAC sends one frame at a time: a queue started while a frame is on the air or not yet done ends the run, as do a rate the model does not run, such as a short guard interval, a descriptor chain outside SRAM, and a length that does not match the descriptors'. A received frame that does not fit one descriptor's buffer ends the run as `rx_length`, and a descriptor outside SRAM as `rx_descriptor`.

The stock station joins and leases 192.168.1.100 over DHCP in protected frames, then goes into power save: it wakes at each TBTT, every 102.4 ms, powers its RF for about 3.4 ms around the beacon, and powers it down again. It prints its address at about 4.226 s, once lwIP has probed for an address conflict. At about 8.995 s it looks up `pool.ntp.org` and asks the network for the time over SNTP, and it prints the date at about 9.006 s. It then dozes on with no fault, through a run of 60 s.

## Behind the seam

Each GPIO with a net is one output and one watch, in [`Esp32s3::PINS`](netlist.md#esp32-s3) order, followed by one internal supply watch with hysteresis on `V(VCC) - V(GND)` (falling at 2.44 V, rising at 3.0 V; not listed in `logic.vcd`). A pad's pull-down is its output's pull-down beside its drive, as [mcu.md](mcu.md#pull-downs) says: the pull-down alone is `Off` with it, and both pulls are `PullUp` with it. A store that changes the drive of a pad with a net, or the pulls of one that does not drive, stops the core before its next instruction. That stop is at the store's cycle, and the run lands there, as [engine.md](engine.md#active-chips) says. The drive of a pad with no net is never stamped, and a `FUN_WPD` store on it is kept, as the GPIO entry above says. A watch flip sets the level that pad's `GPIO_IN` bit reads from the flip's time on, and latches the edge its `INT_TYPE` takes. The run converts ticks to picoseconds by the clocked-core rule in [engine.md](engine.md#active-chips), at 480 MHz.

A GPIO from GPIO1 to GPIO20 with a net is also a sample, `V(pin) - V(GND)`, in output order. A store that starts an ADC conversion or raises `SENS_TSENS_DUMP_OUT` stops the core before its next instruction, at the store's cycle, as a drive change does, and the halt asks for the samples. The engine gives the chip the solved voltages and `world.temperature` (defaulting to 25 degC when the scene omits it) at that time, as [mcu.md](mcu.md) says for a chip's samples, and the conversion takes its pad's voltage or the ambient temperature. The code is fixed then, so a run split anywhere between the start and the read of the code reads the same code at the same tick.

Each SPI2 or SPI3 transfer is a `Spi` record, as [engine.md](engine.md#records) says, that starts at the store of `SPI_USR` and ends at the transfer's end, a stop of the core. Its phases, lanes, data, clock, CS and what it reads on MISO are the transfer's. The bytes the targets answer reach the chip at that stop, before the core runs past it. Its nets are those of the pads the matrix routed CS, SCLK and D0 to D3 to when the transfer started, the lowest-numbered pad for a signal routed to several, and none for a signal on no pad with a net. In `link.csv` its `pin` is the name of the CS pad, such as `GPIO12`, or `SPI2` or `SPI3` when CS is routed to none of the part's [pins](netlist.md#esp32-s3). A store that starts a transfer bounds the core at the transfer's end, and the run lands there. A store that SPI2 or SPI3 refuses stops the core before the store writes.

Each RMT transmission is one `Pulses` record for each pad with a net that carried the channel when it started. The record starts at the `TX_START` store and ends at the transmission's end, a stop of the core. Its idle level is `IDLE_OUT_LV`, and its levels are the words' levels and durations in picoseconds. In `link.csv` its `pin` is that pad, such as `GPIO0`. A `ws2812` whose `DIN` sits on another net, behind a series resistor, takes none. Until a record lands, `leds` shows the latch before it, as [engine.md](engine.md#records) says. When the run ends inside a transmission, the chain takes the levels sent up to the end.

A fault ends the run at the stop that reports it. The run keeps every row and every byte before that time, and the diagnostic is the error that ends it.

## The examples

`packages/engine/tests/circuits/esp32s3-blink` runs `packages/engine/tests/firmware/esp32s3/blink.c` and `packages/engine/tests/firmware/esp32s3/start.S`. The program disables the watchdogs, routes GPIO21 to its `GPIO_OUT` bit, and prints its pin and its period. It then sleeps in `WAITI` while the `CCOMPARE1` interrupt toggles GPIO21 every 4,000,000 cycles, 100 ms, eight times. The interrupt notes the level `GPIO_IN` read before each edge and SYSTIMER after it. The program prints those, and the SYSTIMER span from the first edge to the last. The text it prints is in a comment at the top of `blink.c`.

`packages/engine/scripts/esp32s3-firmware.sh` rebuilds the ELF from those sources with `xtensa-esp32s3-elf-gcc`, GCC 14.2.0 from crosstool-NG esp-14.2.0_20260121. Another compiler builds other bytes. The script files the ELF in `packages/engine/tests/circuits/esp32s3-blink/blobs/` under its SHA-256 and writes that hash and its length into the netlist. With `--check` it compares a fresh build with the committed blob.

`packages/engine/scripts/esp32s3_blink.py --check <run>` checks a run folder apart from the engine. The expected text comes from `blink.c`, and the check first holds it to the program's closed form: edge k reads the level edge k - 1 left, and the SYSTIMER span is 7 × 4,000,000 × 2 / 5 counts. `traces/serial.csv` must hold that text byte for byte, as `u1`'s `USB_SERIAL_JTAG`, each line at one time on a cycle boundary. In `traces/logic.vcd`, GPIO21 must change eight times, rising first and alternating. Edge k must sit at cycle k × 4,000,000 + 18. The 18 is the cycles from the `CCOMPARE1` match to the store that changes the pin. ## Differential check against QEMU

`scripts/diff-esp32s3.sh` (implemented in `scripts/diff_esp32s3.py`) is a by-hand pre-release differential check on Linux. It does not run in PR CI or nightly. It boots each covered ESP32-S3 app in both Espressif's QEMU (`qemu-system-xtensa -machine esp32s3 -nographic -display none -nic none`) and `orbe-run`, normalizes only the expected hardware-identity differences, and exits non-zero with a unified diff on any mismatch, panic, abort, watchdog reset, unexpected reboot, or timeout.

### Cache and user-space setup

The script installs no system packages. It caches downloaded artifacts in `${ORBE_DIFF_SIM_CACHE:-${XDG_CACHE_HOME:-$HOME/.cache}/orbe-diff-sim}` and verifies every download against a pinned SHA-256:

- **QEMU:** Espressif QEMU release `esp-develop-9.2.2-20261109` (`qemu-xtensa-softmmu-esp_develop_9.2.2_20261109-<arch>-linux-gnu.tar.xz` for `x86_64` and `aarch64`).
- **Second-stage bootloaders:** Arduino-ESP32 `3.3.12` `esp32s3-libs-3.3.12.zip`, from which `bootloader_dio_80m.elf` and `bootloader_qio_80m.elf` are verified and converted into ESP32-S3 flash images (`bootloader_{dio,qio}_80m.bin`).
- **User-space shared libraries:** If `libSDL2-2.0.so.0` or `libslirp.so.0` is absent from the system and `$CACHE/prefix/lib`, the script compiles fail-loud stub shared libraries into `$CACHE/prefix/lib` with `cc` (headless `-display none -nic none` never invokes either library, and any unexpected call aborts loudly).

For each app, the script builds a merged flash image (4 MB or 16 MB, matching the app image header's flash-size nibble) with the bootloader at `0x0` (flash-size header byte updated and SHA-256 recomputed), `partitions.bin` at `0x8000`, `app.bin` at `0x10000`, and `0xFF` elsewhere.

### Normalization and comparison

- Strips QEMU's ROM and second-stage bootloader banner up through `entry 0x...` (and the bootloader's `W (<n>) rtcinit: o_code calibration fail` line before app start), since `orbe` starts at `call_start_cpu0`.
- Replaces IDF log timestamps (`I (123)` / `W (123)` / `E (123)` -> `I (<T>)` / `W (<T>)` / `E (<T>)`).
- Drops `efuse_init: Chip rev:` and `spi_flash: detected chip:` lines, and replaces `silicon revision vX.Y` with `silicon revision v<REV>` only on the ESP-IDF `hello_world` chip-info line (`This is esp32s3 chip with <N> CPU core(s), ..., silicon revision vX.Y, <M>MB embedded|external flash`) so app text containing `silicon revision` is still compared (QEMU reports `v0.0` and `issi` flash; `orbe`'s captured board state reports `v0.2` and `boya` flash).
- Any panic, `Guru Meditation Error`, `abort()`, `Backtrace:`, watchdog trigger/reset, unexpected second `ESP-ROM:` banner, non-zero `orbe-run` exit, or timeout fails the check.
- One-shot apps must match line by line after normalization.
- Periodic apps (`esp32s3-stock-serial` at 100 ms, `esp32s3-stock-servo` at 200 ms, `esp32s3-hello` at 1000 ms) must match line by line on their prefix and overlapping tick sequence, and both QEMU (wall-clock arrival times over a Unix-domain serial socket) and `orbe` (`t_ps` in `traces/serial.csv`) must keep their mean tick period within ±25% of the sketch's nominal period.

### Covered apps

Run `scripts/diff-esp32s3.sh --list` to print the current table. The check covers 15 apps:

- Stock Arduino-ESP32 UART0 sketches under `packages/scene/tests/fixtures/`: `esp32s3-stock-serial`, `esp32s3-stock-blink`, `esp32s3-stock-crypto`, `esp32s3-stock-nvs`, `esp32s3-stock-eeprom`, `esp32s3-stock-littlefs`, `esp32s3-stock-preferences`, `esp32s3-stock-analogwrite`, `esp32s3-stock-fade`, `esp32s3-stock-servo`, `esp32s3-stock-ledcdetach`, `esp32s3-stock-ledcreattach`, `esp32s3-stock-wire`, and `esp32s3-stock-pcnt`.

- For `esp32s3-stock-analogwrite`, `fade`, `servo`, `ledcdetach`, `ledcreattach`, and `pcnt`, QEMU does not model LEDC electrical output or PCNT pulse inputs, so only serial output and pacing are compared.
