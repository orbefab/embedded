# The viewer

The viewer draws a scene in 3D from the messages a session sends, and turns a person's clicks into the CLI's own commands. It computes no electrical value.

- `packages/viewer` is the viewer: React Three Fiber, three.js, drei and postprocessing, in TypeScript. Its bench pieces come from maker-sandbox, MIT, Copyright 2026 Alwurts, and each file adapted from it says so in its first line.
- `apps/viewer` is the page. On a live session it runs the viewer on the session's WebSocket. Otherwise it runs a Block from a registry in a Web Worker: `?block=<id>` names the Block, and with no `block` the page runs `nano-button-led`. Vite builds it to static files in `apps/viewer/dist`.

The two are packages in the repo's pnpm workspace, pinned by `pnpm-lock.yaml`.

## Run it

```bash
pnpm install --frozen-lockfile
scripts/wasm.sh .scratch/wasm/pkg
cargo build -p orbe
target/debug/orbe registry build . .scratch/wasm/registry
pnpm --filter @orbe/viewer-page dev
```

Open `/`. The page runs `nano-button-led` in orbe-wasm's Worker, the same Block as `/?block=nano-button-led`. It opens paused at t = 0. Press Play, then hold the button, and `@led1` lights. Press `T` to switch between the 3D view and the top view.

The 3D view orbits with the left button or one finger, pans with the right button, and zooms with the wheel or a pinch. The top view looks straight down, with the part frame's +X to the right and +Y up the screen. It pans with the left or right button or one finger, zooms with the wheel or a pinch, and does not orbit.

The site's pages, including a Block's embed, pass `pageScroll`. A wheel then scrolls the page and zooms only with Ctrl or ⌘ held, and the stage says "Ctrl + scroll to zoom". One finger scrolls the page, and the stage says "Use two fingers to move the view". Two fingers orbit and zoom, or pan and zoom in the top view. The viewer's own page does not pass it, so a wheel and one finger still move the view.

The dev server and `vite preview` serve each part's GLB from `parts/` at `/parts/<id>/<id>.glb`, and the registry and the package the page reads from `.scratch/wasm`, as [Run a Block in the page](#run-a-block-in-the-page) says. The build leaves both out.

## Watch a live session

`orbe show` opens the page on a session that runs, and `orbe open --headed` is `orbe open` and then `orbe show`. When that `show` fails, the command fails with `show`'s error and exit code, the session stays open, and the hint says to run `orbe show` again or `orbe close`. The page is built into `orbe`, so build it before `orbe`:

```bash
pnpm install --frozen-lockfile
pnpm --filter @orbe/viewer-page build
cargo build
cd blocks/nano-button-led
../../target/debug/orbe open --headed
```

`orbe`'s build embeds `apps/viewer/dist` when it holds a page. Without one, `orbe` still builds, and `show` fails with `io_error` "this orbe was built without the viewer page" and a hint with these commands. `ORBE_VIEWER_DIR=<folder>` serves a built page's folder in place of the embedded one.

- The first `show` makes the session's process listen on 127.0.0.1, on a port the system picks, with a fresh 256-bit token. Each later `show` gives the same URL, `http://127.0.0.1:<port>/#t=<token>`. The token sits in the fragment, so the browser never sends it in a request for the page.
- `show` opens the URL in the default browser with `xdg-open`, or `open` on macOS. `--no-browser`, on `show` or with `open --headed`, prints the URL and opens no browser. Tests and scripts always pass it.
- Every request must carry `Host: 127.0.0.1:<port>`, which turns away DNS rebinding. The WebSocket at `/session?t=<token>` also needs the token and `Origin: http://127.0.0.1:<port>`, checked once on the upgrade. Anything else gets 403. The process logs no request.
- The server answers `GET` and `HEAD` with the page's files, and `/parts/<id>/<id>.glb` with each part model the scene message names, from the project's `parts/` folder, or, for a Block, from the `parts/` beside `blocks/`. It serves no other file. It serves at most 32 connections at once, pages and their requests together, and closes any more at once.
- Several pages can watch one session. Closing a page leaves the session running. `orbe close` sends each page `closed` with the reason, then closes its socket. A page whose socket drops without one says the connection dropped. The process also ends after an hour with no command, but that hour counts only while no page watches and `play` is not running, so it never ends a page's session or a session that plays.

One thread owns the session. CLI commands, the pages' commands and `play`'s ticks reach it on one queue, so a page's `press` runs between two commands, never inside a `step`, and lands at `now` like a CLI `press`. A page sends only `press`, `release`, `set`, `play` and `pause`, each parsed by the CLI's own command table. The page shows the state, the time and a Play/Pause button, one slider for each world quantity the scene declares, and one slider for each live param of the scene's parts, such as a potentiometer's `position`. A scene with neither shows no slider. A param slider sends `set @pot1.position <value>`, as the CLI does, so its change lands at `now` and shows in the CLI's next `pause` or `step` through what it caused, such as an edge on the LED's pin. Its knob turns with the value each frame carries. The page lists a refused command as the CLI prints its error, and says why the session ended.

- A slider's thumb steps through the values of the quantity's `scale` in the scene message, plus the value the scene starts it at. A param's thumb steps by a hundredth of its range, rounded down to a power of ten, from one step inside each bound, so a position steps from 0.01 to 0.99. Light steps through 0, 1, 2, 3, 5, 10, 20, 30, 50 and so on to 100000 lx. Temperature steps by 0.5 °C from -40 to 125, and humidity by 1 %RH from 0 to 100.
- A `set` restarts the solve, so a slider sends one `set` per change a person makes. A pointer, a finger or a pen sends when it lets go. The keyboard sends 300 ms after the last key is let go, so five quick presses or a held arrow send one `set`. Leaving the thumb sends at once. A value the frame already shows sends nothing.
- The number beside the thumb takes any value in the range. Enter sends it once. A value out of range or not a number is shown below the slider, as `orbe set` words it, and sends nothing. Escape or leaving the field drops it.
- From the send until the reply, and then until the next frame, the thumb and the number hold the sent value. A refused `set` returns them to the frame's value. Otherwise they show the frame's value, so a `set` from the CLI or another page shows too.
- Once the session stops or faults, every slider is off and the panel says why. The fault shows below the controls and the panel below the fault, in one column.

- A frame reads the probe, the pin levels and the switch contacts at `now`, and never lands a step, so a session gives the same replies with a page watching or without one. The session sends a frame after each command that changes what a frame shows, including serial text that arrived, and during a long `step` at most one every 16 ms of wall time.
- `orbe play` advances time in ticks of 16 ms of wall time, each by the wall time since the last tick, up to 16 ms, at speed 1. An engine slower than real time plays in slow motion. A tick's frame carries `ratio`, the simulated time over the wall time of that tick. A `step` that runs, `pause`, the 2-hour stop or a fault ends play. A `step` refused before it runs, such as `past_stop`, leaves play running. The CLI's next `pause` or `step` lists what the ticks ran. `from_ps` is the start of the stretch that was held. A `step` lists those changes first, at most 20, then what it did, at most 20, and then clears the list. A page's `pause` leaves the list. `pause` always says `playing` is false, and includes the changes when any were held. A test file refuses `play` and `pause`.

`scripts/check-headed.sh` builds the page and `orbe`, then drives a live session of the first target in headless Chromium with `@playwright/test` (`apps/viewer/e2e/headed.spec.ts`). It runs `orbe open --headed --no-browser` in a runtime folder of its own, plays, holds `@btn1` until `@led1` lights, and checks that `orbe get @led1` reads the current the viewer glows at. It then opens the light divider in `packages/session/tests/light-divider` (`apps/viewer/e2e/world.spec.ts`). It moves the light slider with the keyboard, a mouse drag and the number field, counts the `set`s the page sends on its WebSocket, one per change, and checks that each round value lands exactly on the frame and that `orbe get @ldr.a` reads the divider voltage for that light. It also checks that an `orbe set` shows on the paused page. Last it opens `e2e/knob`, a Nano that lights its LED while a potentiometer on A0 reads above half scale (`apps/viewer/e2e/knob.spec.ts`). It turns the knob with the `pot1.position` slider's field and keys and with `orbe set @pot1.position`, and checks that the page sends one `set` per change, that the 3D shaft turns to the position, that the LED follows and that `orbe pause` lists the page's turn. It closes each session however it ends. It never opens a desktop browser. It finds Chromium as `check-viewer-e2e.sh` does. It runs the `orbe` that `cargo build` just wrote, in cargo's target directory, so `CARGO_TARGET_DIR` is the binary under test. `--renders <dir>` saves screenshots. An unknown argument, or `--renders` with no directory, exits 2 and names the argument. `scripts/check.sh web` runs it.

## Run a Block in the page

With `?block=<id>`, the page loads the Block `id` from a registry that `orbe registry build` wrote, and runs it in orbe-wasm's Worker, the scene reader and the session `orbe` runs, compiled to WebAssembly. With no `block` query it loads `nano-button-led` the same way. [wasm.md](wasm.md) describes the package. The page needs no `orbe` process and no server beyond static files.

```bash
pnpm install --frozen-lockfile
scripts/wasm.sh .scratch/wasm/pkg
cargo build -p orbe
target/debug/orbe registry build . .scratch/wasm/registry
pnpm --filter @orbe/viewer-page dev
```

Then open `/?block=nano-button-led`. The dev server and `vite preview` serve `.scratch/wasm/registry` at `/registry/` and `.scratch/wasm/pkg` at `/orbe-wasm/`, the folders the page reads by default. `?registry=<url>` and `?wasm=<url>` name others, each relative to the page.

- `loadBlock` in `packages/viewer/src/registry.ts` reads `index.json`, picks the Block's newest version, and fetches its record, each file and each part it names, at the version it names. It checks each against [registry.md](registry.md#verify-what-you-fetch): the record's and each file's size and SHA-256, the folder hash, the path rules and the `files/<sha256>` URLs. One mismatch refuses the whole Block. Each part's files sit at `parts/<id>/<path>`, where the Worker reads its catalog. A part from another registry is refused.
- `workerSource` starts the Worker, sends it the files, then the viewer's commands. The Worker has no server, so the source points each part model the scene names at an object URL of that model's bytes from the registry.
- `close` on a source terminates its Worker and revokes the object URLs, or closes its socket. A page calls it when it shows another session or unmounts. Its listeners get nothing more, and commands reject. A scene the Worker sent before `close` is dropped when it arrives, so it makes no object URL.
- A Block that does not load or open, a Worker that fails, or a message that is not a JSON object with a string `type` ends the session, and the page says why, such as "the Block did not load: the registry has no no-such-block" or the refusal `orbe open` prints. The source then frees itself as `close` does.

The page loads the package at run time from its URL, so the page's build holds no WebAssembly, and neither does the page built into `orbe`.

`scripts/check-block.sh` builds the page, the package and the registry into those folders, then drives every Block under `blocks/` in `?block=` mode in headless Chromium with `@playwright/test` (`apps/viewer/e2e/block.spec.ts`). Each one opens paused at t = 0, plays in the Worker past one second, and shows what it does: a button lights `@led1` while it is held and the LED goes dark on release, the fade's LED changes brightness, and the light comparator's slider lights `@led1` at 10 lx and turns it off at 300 lx. No command is refused and the page logs no error. A Block the registry lacks still ends the session with why. It needs what [wasm.md](wasm.md#build) needs, and finds Chromium as `check-viewer-e2e.sh` does. `--renders <dir>` saves screenshots. An unknown argument, or `--renders` with no directory, exits 2 and names the argument. `scripts/check.sh web` runs it.

## The messages

`packages/viewer/src/protocol.ts` types every message, and its comments give each field's units. It is generated from the message types in `packages/session` (`viewer.rs`, `reply.rs` and `live/frame.rs`), so change those and run `scripts/bless.sh`, which rewrites it. `scripts/check.sh fast` fails while the committed file differs from what they generate. The scene's own fields, the instances, parts and wires that `packages/scene` reads, are typed by hand in `packages/viewer/src/view.ts`. A session sends one `scene` message per `open` and a `frame` message after each change. The viewer sends a `Command` back. A `SessionSource` carries them both ways: `websocketSource` to the session process, or `workerSource` to orbe-wasm's Worker. Both share `channelSource`, which keeps the latest scene and frame for a late subscriber and pairs each reply with its command. The frame it gives a late subscriber carries the serial text already delivered, bounded to 4096 bytes, with `trimmed` when earlier bytes were dropped. The page uses `websocketSource` when its URL's fragment holds `t=<token>`, and `workerSource` otherwise. With no `block` query it runs `nano-button-led`. `registry` and `wasm` name the folders, by default `registry/` and `orbe-wasm/` beside the page. `orbe show` puts a token in the fragment, and the server it starts does not serve those folders.

- **`scene`** lists the scene's instances, each with its children to any depth and its placement, or `null` for a part the scene does not place. An instance that is not simulated carries the reason, its own or its nearest marked ancestor's. `parts` holds one entry per part id: the GLB's URL, the anchors, the pins, `view`, `joints`, `controls`, the brightness reading, the colour tints, a board's `strips`, and the part file's `not_simulated` entries. Those entries name features the engine leaves out, such as light or temperature, not a dropped part, and the viewer does not read them yet. `wires` lists every wire with its kind, and `channels` names the refs that each frame array follows. `world` lists each world quantity the scene declares, in table order, with its unit as the CLI writes it, its range, the value the scene starts it at, and its `scale`: `linear` with a `step`, or `log`, the round values 0, then 1, 2, 3 and 5 times each power of ten. A scene that declares none omits `world`. `params` lists each live param of the scene's parts, by its ref, such as `@pot1.position`, with its unit as the part file writes it, its bounds `above` and `below`, and the value the scene starts it at. A scene with none omits `params`. A joint in `parts` may turn about `turn`, in degrees, and may follow a param `by`: at the middle of the param's range the node sits where the model draws it, and it moves half of `range` toward each end. `not_simulated` lists each pin whose net reaches no simulated pin and has a reason, the one `orbe check` gives for a wire to it, such as `@nano.A6`. Each entry carries its `why`, and its `ref` is the one hover shows for the pin.
- **`frame`** holds the pin levels, the LED currents, the switch contacts and the addressable LEDs' colours at `t_ps`, in the order of `channels`. An LED's current is its mean since the frame before. An addressable LED's colour, in `pixel_rgb`, is the red, green and blue its first LED last latched, each 0 to 255, and black before its first latch. A page joining restarts that mean, so every page then gets a frame with each LED's present current, the one `orbe get` reads. It also carries the count of diagnostics. Its `state` is the session's, or `stepping` on a frame sent while a `step` runs, which no reply says. A faulted session's frame carries `fault`, the diagnostic that faulted it as `orbe snapshot` prints it, and the viewer shows it below its controls. A frame from a `play` tick carries `ratio`. When the scene declares a world, the frame carries `world`, one value per entry of the scene's `world`. Each is the value from `t_ps` on, or from where the quantity's last `set` lands when that is later. A `set` can land after `now`, such as at 1 ps on a session paused at t = 0, and the next frame shows it all the same. A change the scene schedules shows once `t_ps` reaches it. A scene that declares none omits `world`. When the scene has live params, the frame carries `params`, one value per entry of the scene's `params`, read as `world` is. A frame carries `serial` when UART text is new since the previous frame this feed sent, or when the frame is what a viewer that just joined should show. `serial.from` is the UTF-8 byte index where `serial.text` starts in the session's serial text, the same text `serial contains` searches. The session keeps one serial text and does not record which USART a byte came from, so the field names no port. `serial.text` is at most 4096 UTF-8 bytes. A continuation longer than that is the next unread bytes now and the rest on later frames, and `serial.replace` is absent. `serial.replace` is true when `text` is not an append onto bytes already sent at `from`. That is when the session's text was shortened or replaced, including after `open`, or when this frame is the bounded log a viewer that just joined should show. `serial.trimmed` is true when `text` leaves out earlier bytes the session still has, which is a joined view of a log longer than 4096 bytes. It is absent when `text` starts at the first byte the page should still show. A page holds at most 4096 bytes. When it drops older bytes it was sent, or when `trimmed` is true, it shows the words "earlier output trimmed" where those bytes were left out. A frame with no new serial, and a join of an empty log, omits `serial`.
- **Over the WebSocket or to the Worker**, the viewer sends each command with an `id` of its own, as `{"id": 1, "cmd": "press", "ref": "@btn1"}` or `{"id": 2, "cmd": "set", "quantity": "light", "value": 50}`. The session answers that page alone with `{"type": "reply", "id": 1, "reply": ...}`, where `reply` is the envelope `orbe press @btn1 --json` prints: `ok`, `session`, `t_ps`, `state`, then `data` or `error`. The last message is `{"type": "closed", "reason": ...}`.
- The session's channels are the board pins `snapshot` shows that a chip pin drives and a wire reaches, a breadboard's holes aside, every LED whose part data has a brightness reading, every switch with `controls.press`, and every addressable LED, a part with a reading `"of": "rgb"`, in `pixels`.

Lengths, positions and directions in the messages are in the part frame: mm, +Z up, with the seating plane at z = 0.

## How it draws a scene

- Every instance is a group named by its ref, such as `@nano.j2`, placed by its parent's layout in the parent's part frame. A part with children draws its own GLB, if it has one, and then each child's.
- One turn at the root, `TO_THREE` in `build.ts`, maps the part frame into the viewer's world, which is mm with +Y up. Part (x, y, z) lands at world (x, z, -y).
- The tilted camera starts 40 degrees off straight down and 35 degrees toward the front left, with a 30 degree field of view. A connector's opening faces -X in the part frame, so it faces the camera. The view frames the whole scene. The top view frames a scene whose span is under 16 mm as 16 mm, so a small scene stays readable.
- The stage is a hemisphere, a fill light, and a key light at intensity 1.9 that casts a shadow map. Metal takes the room image at strength 0.42 and plastic at 0.18. The floor is a grid that fades into the page's stage colour. The renderer does not tone-map. A material's metal and roughness are the GLB's. A GLB that leaves them out is rough metal. Bloom reads a pixel only where the nearest surface is an LED's glow mesh at or above intensity 1, or the clear lens over one. A depth pass of those meshes, on a render layer of their own, masks the frame, and the mask takes the camera's near and far planes each time they change. There a pixel starts to bloom as its luminance goes from 1 to 1.2. An LED below intensity 1 does not bloom, and nothing else does, from any camera. The hover outline uses another layer, so a hover changes no bloom. The perspective camera's near plane is `max(0.1, distance / 200)`, so the shadow plane's 0.3 mm clearance stays wider than the depth step when the view pulls back.
- The viewer loads each GLB URL once. It refuses a GLB with more than one root node, or whose root carries anything other than glTF's -90 degree turn about X. It removes that turn and scales the GLB by 1000, so the GLB's nodes sit in the part frame in mm.
- An LED's `view.glow` node glows by its current over `readings.brightness.full`, with no upper clip. The glow colour is the node's colour scaled to luminance 1, and the lit surface under it fades to black as the intensity goes from 0 to 1. At the full current the node's luminance is 1, where its bloom starts. A current above that full value pushes the same meshes further over the threshold. An addressable LED's `view.glow` node glows by the colour its first LED latched, by the name of its reading `"of": "rgb"`. The intensity is its brightest channel over 255, so a channel at 255 blooms, and the glow colour is the latched red, green and blue, as linear light, scaled to luminance 1. The same glow and bloom path draws it.
- A `view.tint` node takes the colour of the choice its param picks. A 5 mm or 3 mm LED bakes its colour into the model and has no tint. A `view.recolour` node set with rule `iec60062-4-band` shows the resistance in the 4-band colour code.
- The joint that `controls.press.joint` names slides its node by `range` along `slide` while the frame says the switch is closed.
- `jumper` wires are drawn. `trace` and `contact` wires are not. A part the scene plugs into a breadboard arrives placed, with a `contact` wire from each leg to its hole. Each end sits on a lead's anchor, and an end on a breadboard hole sits on the hole's mouth. A pin on two leads, such as a switch's `a` or the Nano's `GND`, uses the lead nearest the other end.
- The viewer lays out each unplaced part in a row to the right of the placed ones. It writes nothing back.
- A part the viewer cannot draw as its data says, such as one whose `view` names a node its GLB lacks, shows its GLB as loaded, with no tint, glow or press. It is listed in red at the bottom of the canvas and in the console, and its hover gives the reason. The rest of the scene still draws. A wire that reaches no lead is listed the same way. A resistance with no 4-band code, outside 0.1 ohm to 99 Gohm, keeps the GLB's band colours, with one console warning.
- A GLB whose root node has a mesh is refused, because the viewer draws only the root's children. A child with no placement is refused, with its ref.

## Clicks and hover

- A primary-button `pointerdown` on a part with `controls.press` sends `press @<ref>` and captures the pointer. Another mouse button sends nothing. That pointer's `pointercancel` or lost capture, its `pointerup`, or the window losing focus, sends `release @<ref>`, once. A press ends once the pointer's primary button (a mouse's left button, a pen's tip, a finger's contact) is up, on a `pointerup` or, in a chord, on the `pointermove` that reports it. Another pointer lifting does not release it, and while one press is held, no other starts.
- A command the session refuses, or whose send fails, is listed in red at the bottom of the canvas and in the console. A release clears the held press even then, and the viewer never resends it. A new `scene` clears the list.
- A new `scene` drops a held press without a release, because it follows an `open`, which restarts the session.
- A click on any other part sends nothing, even when that part holds a pressable child. A click on the Nano's reset button presses `@nano.sw_reset`. A click on the board around it does nothing.
- Hover shows the ref under the pointer, and outlines that part in orange. A lead shows the outermost label that reaches it, such as `@nano.D13` on header `j2`'s pin 1, or else its own pin, such as `@led1.anode`. Any other mesh shows its instance, such as `@nano.r_l`. On a part whose data has `strips`, such as a breadboard, the hole within 1.27 mm of the point under the pointer shows its pin and the strip it sits in, such as `@bb.b20` and `strip bb.a20 to bb.e20`.
- Hover also gives the reason for an instance that carries `not_simulated` and for a pin in the scene's `not_simulated`, such as `@nano.3V3`'s "It is the CH340G's 3.3 V output. The engine has no USB-serial chip, so the pin supplies nothing." A pin takes its reason only from the scene's list, because a lead of a part that is not simulated can still sit on a simulated net. The viewer does not yet draw these parts or pins differently.
